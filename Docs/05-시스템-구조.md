# 05. 시스템 구조

> 근거: [SA문서 §5 시스템 구조도](reference/SA문서.md) · 루트 `CLAUDE.md` §5, §7, §8

## 전체 시스템 구조도

```mermaid
flowchart TB
    client["Client<br/>Swagger UI / Postman"]
    gw["gateway-service :8080<br/>JWT 검증 · 권한 확인 · 라우팅"]
    eureka["eureka-server :8761<br/>Service Registry"]
    slack["Slack<br/>Incoming Webhook"]

    subgraph bizLayer["Business Services (각자 독립 스키마)"]
        ordersvc["order-service :8084<br/>주문 · Saga 오케스트레이터"]
        companysvc["company-service :8083<br/>업체 · 상품"]
        deliverysvc["delivery-service :8085<br/>배송 · 배송경로"]
        hubsvc["hub-service :8082<br/>허브 · 경로 · 재고"]
        usersvc["user-service :8081<br/>회원 · 인증(JWT 발급)"]
    end

    client -->|"REST + JWT"| gw
    gw -.->|"인스턴스 조회"| eureka
    gw --> ordersvc
    gw --> companysvc
    gw --> deliverysvc
    gw --> hubsvc
    gw --> usersvc

    ordersvc -.->|"업체 · 상품 조회"| companysvc
    ordersvc -.->|"배송 생성 · 취소 · 삭제"| deliverysvc
    ordersvc -.->|"재고 할당 · 복원"| hubsvc
    companysvc -.->|"허브 확인 · 재고 초기화"| hubsvc
    hubsvc -.->|"상품 확인 (입고)"| companysvc
    companysvc -.->|"관리자 확인"| usersvc
    deliverysvc -.->|"경로 조회"| hubsvc
    deliverysvc -.->|"담당자 확인"| usersvc
    deliverysvc -.->|"관리 업체 확인 (조회 권한)"| companysvc
    usersvc -.->|"소속 허브 확인"| hubsvc
    ordersvc -->|"HTTPS"| slack
```

- 실선은 Gateway를 통한 외부 요청 라우팅, 점선은 서비스 간 내부 Feign 호출이다.
- 모든 서비스는 Eureka에 등록되고, Gateway와 Feign은 `lb://서비스명`으로 대상 인스턴스를 찾는다.
- 인증·인가는 Gateway에서 처리하고, 각 서비스는 `X-User-*` 헤더로 사용자를 식별해 소유자 검증만 한다.

## 서비스 내부 구조 (Layered Architecture)

```mermaid
flowchart TB
    p["Presentation<br/>Controller · Request/Response DTO"]
    a["Application<br/>UseCase Service · 트랜잭션 경계 · Saga 오케스트레이션"]
    d["Domain<br/>Entity · VO · 도메인 규칙(상태 전이) · Repository 인터페이스"]
    i["Infrastructure<br/>JPA/QueryDSL 구현 · FeignClient · Slack Client · Config"]
    p --> a --> d
    i -.->|"Repository 인터페이스 구현 (의존성 역전)"| d
```

- 의존은 Presentation → Application → Domain 방향. Infrastructure는 Domain의 Repository 인터페이스를 구현한다(의존성 역전).
- **Entity는 Controller 밖으로 노출하지 않고**, 계층마다 DTO를 분리한다.
- 상태 전이 규칙은 **Entity 메서드**에 둬서 도메인 계층에서 검증한다 (위반 시 409 `INVALID_STATUS_TRANSITION`).

## 주문 생성 Saga

order-service가 순서를 지휘하는 **오케스트레이션** Saga다. 동기 Feign 중심 스택이고 Kafka는 고도화 단계이며, 주문 → 재고 → 배송이 직선 흐름이기 때문이다.
내부적으로는 실패한 단계까지 **역순으로 하나씩 보상**하고, 클라이언트에는 **최종 에러 하나만** 응답한다.

순서: `orderId 선발급` → 업체·상품 조회(I-07, I-08) → 요청업체 관리자 본인 확인 → 재고 할당(I-05) → 배송 생성(I-09) → 주문 저장 → 커밋 후 Slack 비동기 발송

```mermaid
sequenceDiagram
    autonumber
    actor C as Client
    participant G as Gateway
    participant O as order-service
    participant CO as company-service
    participant H as hub-service
    participant D as delivery-service
    participant S as Slack

    C->>G: POST /api/v1/orders (JWT)
    G->>O: 인증 후 라우팅 (X-User-* 헤더)
    O->>O: orderId 선발급
    O->>CO: 공급·수령업체, 상품 조회 (I-07, I-08)
    CO-->>O: hubId, address, managerId, 상품 정보
    O->>O: 요청업체 관리자 본인 확인 (MASTER 제외)
    O->>H: 재고 할당 (I-05, orderId, productId, quantity)
    H->>H: 공급업체 허브 재고 행 잠금 후 차감
    alt 공급업체 허브 재고 부족
        H-->>O: 409 STOCK_INSUFFICIENT
        O-->>C: 409 주문 실패 (변경된 데이터 없음)
    else 할당 성공
        H-->>O: 200 출고 허브, 수량
        O->>D: 배송 생성 (I-09, orderId, 공급·요청업체, 각 허브, 요청업체 주소·업체명)
        D->>H: 공급업체 허브 → 요청업체 허브 경로 조회 (I-03, 같은 허브면 생략)
        H-->>D: 예상 거리·소요시간
        D->>D: 배송 + 경로 기록 저장 (로컬 트랜잭션)
        alt 배송 생성 실패 또는 타임아웃
            D-->>O: 5xx / timeout
            O->>D: [보상] 배송 삭제 (I-13, orderId)
            O->>H: [보상] 재고 복원 (I-06, orderId)
            O-->>C: 503 주문 실패
        else 배송 생성 성공
            D-->>O: 201 deliveryId
            O->>O: 주문 저장 (로컬 트랜잭션)
            alt 주문 저장 실패
                O->>D: [보상] 배송 삭제 (I-13, orderId)
                O->>H: [보상] 재고 복원 (I-06, orderId)
                O-->>C: 500 주문 실패
            else 저장 성공
                O-)S: Webhook 발송 (커밋 후 비동기)
                O-->>C: 201 Created
            end
        end
    end
```

### 실패 지점별 처리

| 단계 | 실패 상황 | 처리 | 응답 |
| --- | --- | --- | --- |
| ① 업체·상품 조회 | 없음 / 타임아웃 | 아무것도 변경하지 않았으므로 즉시 실패 | 404 / 503 |
| ② 재고 할당 | 재고 부족 | 롤백 후 즉시 실패 | 409 |
| ② 재고 할당 | 타임아웃 (차감 여부 모름) | 재고 복원(I-06). 할당 내역이 없으면 no-op이라 안전 | 503 |
| ③ 배송 생성 | 실패 / 타임아웃 | 배송 삭제(I-13) → 재고 복원(I-06). 둘 다 orderId 기준 멱등 | 503 |
| ④ 주문 저장 | DB 오류 | 로컬 롤백 → 배송 삭제(I-13) → 재고 복원(I-06) | 500 |
| ⑤ Slack 발송 | 실패 | 주문 유지, 에러 로그만 (`@TransactionalEventListener(AFTER_COMMIT)` + `@Async`) | 201 |
| 보상 자체 실패 | 보상 API 호출 실패 | 최대 3회 재시도, 그래도 실패하면 orderId 포함 ERROR 로그 → 수동 재처리 | - |

### 재고 할당·복원 (hub-service, I-05 / I-06)

| API | 처리 순서 |
| --- | --- |
| I-05 할당 | ① 상품 재고 행 `FOR UPDATE` → ② `order_id`로 기존 할당 조회, 있으면 그대로 반환 → ③ 없으면 수량 검사(부족 시 409) 후 차감 + `ALLOCATED` 저장 |
| I-06 복원 | ① 락 없이 `order_id`로 할당 조회, 없으면 0 반환 → ② 해당 재고 행 `FOR UPDATE` → ③ `ALLOCATED`면 복원 후 `RESTORED`, 이미 복원됐으면 0 |

> 락 순서는 항상 **재고 행 → 할당 내역**. 순서를 바꾸면 교착 위험.

## 상태 전이

### 주문

| 상태 | 의미 | 규칙 |
| --- | --- | --- |
| `ORDERED` | 주문 완료 | 생성 시 |
| `CANCELED` | 주문 취소 | 허브 이동 시작 전 + 업체 배송 출발 전에만 가능. 취소 시 공급업체 허브 재고 복원 |

- 주문 삭제(O-06)는 MASTER만, **취소 또는 배송 완료된 주문만** 가능 (그 외 409 `ORDER_NOT_DELETABLE`).

### 배송 (업체 간 배송)

배송 구조: **공급업체 → 공급업체 허브 → (허브 이동) → 요청업체 허브 → 요청업체**

```mermaid
stateDiagram-v2
    [*] --> HUB_WAITING : 주문 생성 (공급·요청업체 허브가 다름)
    [*] --> DEST_HUB_ARRIVED : 주문 생성 (같은 허브, 허브 이동 없음)
    HUB_WAITING --> HUB_MOVING : 허브 이동 구간 MOVING (D-07)
    HUB_MOVING --> DEST_HUB_ARRIVED : 허브 이동 구간 ARRIVED (D-07)
    DEST_HUB_ARRIVED --> OUT_FOR_DELIVERY : 업체 배송 출발 (D-05)
    OUT_FOR_DELIVERY --> DELIVERED : 배송 완료 (D-05)
    HUB_WAITING --> CANCELED : 주문 취소
    DEST_HUB_ARRIVED --> CANCELED : 주문 취소 (허브 이동 없이 시작한 경우만)
    DELIVERED --> [*]
    CANCELED --> [*]
```

| 배송 상태 | 의미 | 변경 방식 · 전제 조건 |
| --- | --- | --- |
| `HUB_WAITING` | 공급업체 허브에서 출발 대기 | 주문 생성 시 자동 (두 허브가 다를 때) |
| `HUB_MOVING` | 허브 간 이동 중 | 허브 이동 구간을 `MOVING`으로 바꾸면 자동 (D-07). 허브 이동 담당자 배정 필수 |
| `DEST_HUB_ARRIVED` | 요청업체 허브 도착 | 허브 이동 구간을 `ARRIVED`로 바꾸면 자동 (D-07). 같은 허브면 생성 시 바로 이 상태 |
| `OUT_FOR_DELIVERY` | 요청업체로 배송 중 | D-05. `DEST_HUB_ARRIVED` + 업체 배송 담당자 배정 필수. `out_for_delivery_at` 기록 |
| `DELIVERED` | 배송 완료 | D-05. `delivered_at` 기록 |
| `CANCELED` | 주문 취소 | I-11. `HUB_WAITING`, 또는 허브 이동 구간 없이 `DEST_HUB_ARRIVED`인 경우만 |

- 허브 이동을 마치고 도착한 배송은 **취소할 수 없다.** 재고는 공급업체 허브로 복원되는데 실물은 요청업체 허브에 있어 불일치가 생기기 때문이다.
- 조건을 어기는 전이는 409 `INVALID_STATUS_TRANSITION`.

### 허브 이동 구간 (`p_delivery_routes`)

```mermaid
stateDiagram-v2
    [*] --> WAITING : 배송 생성 (허브가 다를 때 1건)
    WAITING --> MOVING : D-07 (허브 이동 담당자 배정 필수)
    MOVING --> ARRIVED : D-07 (실제 거리·소요시간 입력)
    WAITING --> CANCELED : 주문 취소
    ARRIVED --> [*]
    CANCELED --> [*]
```

구간이 1개뿐이므로 구간 상태가 배송 상태와 1:1로 연동된다: `WAITING` ↔ `HUB_WAITING`, `MOVING` ↔ `HUB_MOVING`, `ARRIVED` ↔ `DEST_HUB_ARRIVED`, `CANCELED` ↔ `CANCELED`.
