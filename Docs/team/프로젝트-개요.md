## 2. 핵심 설계 결정 요약

### 2-1. 인증·인가 구조
- **인증은 Gateway에서만** 해요. Gateway가 JWT를 검증한 뒤 `X-User-Id`, `X-Username`, `X-User-Role`, `X-Delivery-Manager` 헤더를 넣어서 하위 서비스로 보내요. 클라이언트가 같은 이름의 헤더를 보내도 먼저 제거해요.
- 하위 서비스는 이 헤더를 믿고, **소유자 검증 같은 비즈니스 인가만** 해요.
- 권한은 `MASTER` / `USER` 두 단계예요. 배송담당자는 별도 권한이 아니라 USER의 `is_delivery_manager = true` 속성이에요.
- Gateway는 매 요청마다 I-01로 사용자 존재와 권한을 다시 확인하고, 그 결과를 **userId 기준 60초 동안 캐시**해요.
- MASTER 전용 API는 컨트롤러에 `@MasterOnly`를 붙이면 common의 인터셉터가 403을 반환해요.

### 2-2. 도메인 규칙 (서비스 담당자 영역)
- **재고**: 상품은 공급업체 소속 허브에만 존재해요(상품당 재고 행 1개). 할당·복원 기록은 `p_stock_allocations`가 맡아요. 잠금 순서는 항상 "재고 행 → 할당 내역"이에요.
- **주문 Saga**: order-service가 지휘하는 **오케스트레이션** 방식이에요.
  `orderId 선발급 → 업체·상품 조회 → 본인 확인 → 재고 할당 → 배송 생성 → 주문 저장 → 커밋 후 Slack`
  실패하면 역순으로 보상하고, 모든 내부 API는 orderId 기준으로 멱등이에요.
- **배송**: `HUB_WAITING → HUB_MOVING → DEST_HUB_ARRIVED → OUT_FOR_DELIVERY → DELIVERED`. 같은 허브면 생성 즉시 `DEST_HUB_ARRIVED`예요. 담당자는 MASTER가 수동으로 배정해요.
- **금액**: `total_price = unit_price × quantity`를 서버가 계산해 저장해요(오버플로 시 400).

### 2-3. 인프라 규칙
- PostgreSQL 1대, **서비스별 스키마 + 전용 계정**. 각 계정은 자기 스키마에만 권한이 있어요.
- 외부 공개 포트는 Gateway 8080, Eureka 8761뿐이에요(postgres 5432는 개발 편의). 비즈니스 서비스는 포트를 열지 않아서 `--scale`로 늘릴 수 있어요.
- Feign 타임아웃: 기본 1초/3초, I-05·I-09는 read 5초, I-03은 read 2초. **바깥 호출의 타임아웃이 안쪽보다 길게** 유지해요.
- 비밀 정보(JWT secret, DB 비밀번호, Slack URL)는 `.env`로만 관리하고 Git에 올리지 않아요.

## 3. 공통 인프라 구현 현황 (2026-10-13 기준)

### 3-1. 완료 기준 6가지 (모두 로컬 검증 완료)
1. `docker compose up` 한 번으로 전체 기동 + Eureka 등록 (빈 캐시 첫 빌드 약 4분)
2. 회원가입 → 로그인 → 토큰 발급
3. 토큰으로 Gateway를 거쳐 U-03 호출 시 `@CurrentUser`로 사용자 정보 수신
4. 토큰 없음·위조 → 401, 일반 사용자가 U-08 호출 → 403
5. 외부에서 `/internal/**` 호출 차단
6. 클라이언트가 보낸 `X-User-Role: MASTER` 헤더 무시

추가로 소프트 삭제, 삭제된 username 재사용, 60초 캐시 만료 후 401까지 확인했어요.

## 4. 학습 정리

### 4-1. 모놀리스와 무엇이 다른가
| 모놀리스 | 이 프로젝트(MSA) |
| --- | --- |
| 앱 하나, DB 하나 | 서비스 5개 + Gateway + Eureka, DB는 스키마로 분리 |
| 다른 기능은 메서드 호출 | 다른 서비스는 **Feign HTTP 호출** |
| Spring Security가 로그인 확인 | **Gateway 필터**가 확인하고 헤더로 전달 |
| JOIN으로 다른 테이블 조회 | 서비스 간 FK·JOIN 금지, **UUID 참조 + Feign으로 존재 확인** |
| 트랜잭션 하나로 롤백 | 서비스마다 트랜잭션이 따로라 **Saga 보상**으로 되돌림 |

### 4-2. Spring Cloud 3종
- **Eureka**: 서비스들의 주소록이에요. 각 서비스가 기동하면 "나 여기 있어"라고 등록하고, 다른 서비스는 이름(`user-service`)으로 주소를 찾아요. 인스턴스가 여러 개여도 이름 하나로 찾을 수 있어서 수평 확장이 가능해요.
- **Gateway**: 유일한 정문이에요. 경로를 보고 어느 서비스로 보낼지 정하고(`lb://user-service`), 그 전에 인증을 해요.
- **OpenFeign**: 인터페이스만 선언하면 HTTP 호출 코드를 만들어 줘요. LoadBalancer와 함께 Eureka에서 주소를 찾아 호출해요.

### 4-3. JWT
- 로그인 성공 시 user-service가 `sub`(userId), `username`, `role`, `iat`, `exp`를 담아 **HS256으로 서명**한 토큰을 발급해요.
- Gateway는 같은 비밀키로 서명을 검증해요. 내용을 바꾸면 서명이 맞지 않아 401이에요.
- 토큰 내용은 암호화가 아니라 인코딩이라 누구나 읽을 수 있어요(jwt.io). 그래서 비밀번호 같은 값은 넣지 않아요.

### 4-4. 4계층 구조와 의존성 역전(DIP)
```
presentation (Controller, 요청/응답 DTO)
      ↓
application  (Service, 트랜잭션, Command/Result DTO)
      ↓
domain       (Entity, enum, Repository "인터페이스")
      ↑ 구현
infrastructure (JPA 구현체, Feign, JWT 발급기 등)
```
- domain은 아무것도 의존하지 않아요. infrastructure가 domain의 인터페이스를 구현해요.
- 예: `UserRepository`(domain 인터페이스) ← `UserRepositoryImpl`(infrastructure, JPA 사용). `TokenIssuer`(application 인터페이스) ← `JwtTokenIssuer`(infrastructure).
- 장점: 기술(JPA, JJWT)을 바꿔도 domain·application 코드는 그대로예요.

### 4-5. 필터 체인
- 요청이 컨트롤러에 닿기 전에 줄지어 선 검문소예요. 각 필터는 **통과**(`chain.filter(...)` 호출)하거나 **차단**(그 자리에서 401 등을 응답)해요.
- `AuthenticationFilter`의 `getOrder()`는 `-1`이라 라우팅(실제 전송) 필터보다 먼저 실행돼요. 그래서 **인증이 항상 전송보다 먼저** 일어나요.

### 4-6. WebFlux와 Mono
- Gateway는 모든 요청이 지나가는 병목이라, 기다리는 동안 스레드를 붙잡지 않는 WebFlux(논블로킹)를 써요.
- **Mono = 나중에 0개 또는 1개의 값이 도착하는 상자**예요. 조립만 해 두고, 프레임워크가 구독할 때 실행돼요.

| 명령형 코드 | Mono 코드 | 의미 |
| --- | --- | --- |
| `User u = call();` | `Mono<User> m = call();` | 값이 아니라 "값이 올 예정"을 받음 |
| `u2 = convert(u)` | `.map(u -> convert(u))` | 값이 오면 변환 |
| `if (u == null) u = 기본값` | `.defaultIfEmpty(기본값)` | 값 없이 끝나면 기본값 |
| `try { … } catch (e) { … }` | `.onErrorResume(e -> …)` | 에러 나면 대체 |
| `return next(u);` (또 비동기) | `.flatMap(u -> next(u))` | 다음 비동기 작업을 이어 붙임 |
| `void` 메서드 | `Mono<Void>` | 값 없이 "끝났다"는 신호만 |

**`AuthenticationFilter.filter()` 흐름**
1. 클라이언트가 보낸 `X-User-*` 헤더 제거 (WebFlux 요청은 불변이라 `mutate()`로 수정본 생성)
2. `/internal/**`면 403 응답하고 끝
3. 회원가입·로그인·Swagger면 토큰 검사 없이 통과
4. `Bearer` 토큰을 꺼내 서명·만료 검증, 실패 시 401
5. `UserClient`로 사용자 재확인(60초 캐시) → 조회 실패 503 / 탈퇴 401 / 토큰 권한 ≠ DB 권한이면 401 `TOKEN_ROLE_MISMATCH`
6. 통과하면 **DB 기준 값**으로 `X-User-*` 헤더를 넣고 다음 필터로

### 4-7. Docker Compose 네트워크
- **이름이 곧 주소**: 같은 네트워크의 컨테이너는 서비스 이름(`postgres`, `eureka-server`)으로 서로를 찾아요.
- **localhost는 자기 자신**: 컨테이너 안의 `localhost`는 그 컨테이너 자신이에요. 그래서 yml에 `${DB_HOST:localhost}`로 써서 IDE에서는 localhost, Docker에서는 `postgres`를 쓰게 했어요.
- **`ports:`는 바깥으로 여는 문**: 이걸 적은 Gateway·Eureka·Postgres만 호스트에서 접근할 수 있어요.
- **기동 순서**: `depends_on: condition: service_healthy`로 DB가 준비된 뒤에 서비스를 띄워요.

### 4-8. AutoConfiguration (common이 자동 적용되는 원리)
**왜 필요한가**: 각 서비스의 메인 클래스는 자기 패키지(`com.sparta.logistics.hub`)만 스캔해요. common은 `com.sparta.logistics.common`이라 스캔 범위 밖이에요. `scanBasePackages`를 서비스마다 적는 방법도 있지만, 한 명이 빠뜨리면 예외 처리기나 `@CurrentUser`가 **조용히** 동작하지 않아요. AutoConfiguration을 쓰면 **"common을 의존하기만 하면 적용된다"** 가 보장돼요.

**동작 순서**
```
common/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  └─ com.sparta.logistics.common.config.CommonAutoConfiguration   (한 줄)

hub-service 기동
 ① @SpringBootApplication의 컴포넌트 스캔: com.sparta.logistics.hub.** 만
 ② @EnableAutoConfiguration: 클래스패스의 모든 jar에서 imports 파일을 찾음
      spring-boot-autoconfigure.jar → DataSource, JPA, MVC …
      spring-cloud-*.jar            → Eureka Client, Feign …
      common.jar                    → CommonAutoConfiguration   ← 우리 것
 ③ 사용자 설정을 먼저 등록하고, AutoConfiguration은 그 다음에 처리
```
Spring Boot가 JPA를 자동 설정하는 것과 **똑같은 경로**예요.

**`CommonAutoConfiguration`이 하는 일**
| 코드 | 역할 |
| --- | --- |
| `@AutoConfiguration(after = HibernateJpaAutoConfiguration.class)` | JPA 설정이 끝난 뒤 처리. `JPAQueryFactory`가 `EntityManager`를 필요로 하기 때문 |
| `@EnableJpaAuditing(auditorAwareRef = "headerAuditorAware")` | `BaseEntity`의 생성·수정 시각과 작성자를 자동 기록. 작성자는 `X-User-Id` 헤더에서 읽음 → 서비스 담당자가 `created_by`를 직접 넣을 필요 없음 |
| `@Import(GlobalExceptionHandler.class)` | 스캔 범위 밖이라 명시적으로 등록. 없으면 에러가 Spring 기본 형식으로 나감 |
| `WebMvcConfigurer` Bean | `CurrentUserArgumentResolver`(= `@CurrentUser`의 정체), `MasterOnlyInterceptor`(= `@MasterOnly`의 정체) 등록 |
| 나머지 Bean | `JPAQueryFactory`, Feign 헤더 전파·에러 변환, Swagger의 Authorize 버튼 설정 |

**`@CurrentUser`가 값을 만드는 과정** (`CurrentUserArgumentResolver`)
1. 컨트롤러 호출 직전, Spring MVC가 등록된 ArgumentResolver들에게 "이 파라미터 처리할 수 있어?"(`supportsParameter`)라고 물어요.
2. `@CurrentUser`가 붙어 있고 타입이 `UserContext`면 이 Resolver가 "내가 할게"라고 답해요.
3. `resolveArgument`가 `X-User-Id`, `X-User-Role` 등 헤더를 읽어 `UserContext`를 만들어요. 헤더가 없으면(= Gateway를 안 거침) 401이에요.

`@RequestBody`, `@PathVariable`도 내부적으로 각자의 ArgumentResolver가 처리해요. 우리는 하나를 추가한 것뿐이에요.
