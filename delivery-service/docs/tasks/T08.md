## 왜 (요약, 상세는 결정 로그 27)
1. SA 6.3은 배송 생성 안에서 담당 건수가 가장 적은 사람을 고른다. 16에서 동시 편차가 작다고 보고 잠금을 생략했다.
2. 같은 허브 동시 50건이 담당자 5명 중 2명에게 모두 몰렸다(`[0, 50, 0, 50, 0]`).
3. 허브 잠금으로 편차는 0이 됐지만 잠금을 기다리는 생성 요청이 DB 커넥션을 쥔다. 처음 측정의 "허브당 초당 약 28건 상한"은 재측정에서 재현되지 않았고, 같은 조건 재측정에서는 조회 병목을 걷어 낸 뒤 생성 240/초에서 잠금 대기로 무너졌다(결정 로그 28, 아래 "성능 고도화 단계").
4. 팀 결정: 주문 완료 뒤 배차하는 구조로 바꾼다(배달앱의 주문 접수 → 배차와 같다).

## 성능 고도화 단계
같은 허브에 생성 트래픽을 올려 실패 지점을 찾고, 지표로 원인을 짚어 개선한 뒤 같은 조건으로 다시 올린다. 이 절이 포트폴리오용 정본이고, 값의 근거는 아래 "작업 기록"의 해당 측정이다. 개발 순서(허브 잠금 → 비동기 배정 → 인덱스)와 단계 순서는 다르다. 측정 환경을 정리한 뒤 같은 조건으로 단계를 다시 쌓았다(2026-10-19~20).

- 공통 조건: 과거 배송 30만 건(구간 약 88만, `delivery-load.sql`), 같은 허브(서울, 배송담당자 2명), 예열 2회(초당 10+10) → 60초 쉼 → 측정이 만든 배송만 삭제(`KEEP_LOAD=1`) → 1분 측정, 같은 조건 2회. Docker CPU 8개·메모리 7.8GiB, zipkin 정지, 측정 전 쉬는 상태 CPU 합계 확인
- 실패 기준: 생성 p95 500ms 초과, 또는 실패·못 보낸 요청(k6 dropped)이 1% 초과. 두 회차 중 하나라도 넘으면 실패로 본다
- 도구: `load-test/version-compare.sh`(조건별 이름, `READ_FIXED`로 조회 고정), `load-test/assignment-stats.sh`(배정 지연·편차)

### 보조 자료(단계 표의 근거와 측정 방법)
- 빈 DB 대조군(작업 기록 "동기 락 재측정", "배치 창 비교 4차"): 데이터가 없으면 동기·비동기 모두 80+80까지 p95 10ms대. 데이터 영향은 조회에 먼저 나타났다(D-01 p95 5ms → 35ms)
- 예전 측정 비재현(작업 기록 "재측정 2번"): `lock-40b·c`(40+40에서 0% 성공)는 빈 DB·30만 건 모두 재현되지 않았다. "허브당 초당 28건 상한"은 통합 테스트 처리 시간에서 거꾸로 계산한 추정이었다. 처음 가설(락이 병목)을 같은 조건 재측정으로 반증하고 실제 병목(조회)을 찾은 과정이다
- 배치 창(작업 기록 "배치 창 비교 4차"): 신호가 겹치는 부하(160+160, 빈 DB)에서 창 200ms가 배정 실행을 약 1/30, postgres CPU를 약 절반으로 줄이고 배정 지연을 약 200ms 늘렸다
- 측정 방법의 근거: Mac 저하(카메라·발열) 때 같은 조건 p95가 3배 달랐고 40+40이 무너졌다(배치 창 1·2차 무효). 그래서 2회 측정, 쉬는 상태 확인, 같은 날 연달아 측정을 규칙으로 둔다. Docker를 잘못 끈 판(재측정 2번 1차)은 버렸다

## 측정 재현(그래프·캡처용)
이력서·포트폴리오용 그래프는 정리가 끝난 뒤 두 버전을 다시 띄워 같은 날 연달아 측정하고 그 값으로 만든다. window-0(19:12)과 async-40(18:25)은 같은 조건인데 p95가 약 3배 달랐다. 따로 잰 값을 섞으면 비교가 흔들린다.

| 비교 대상 | 돌아갈 지점 |
|---|---|
| 동기 잠금(허브 advisory lock) | 태그 `perf/sync-lock` (bc3177b, `feat/delivery-assignment-lock`) |
| 비동기 배치 배정 | T08 커밋 후 태그 `perf/async-batch` |

- 태그는 로컬에만 있다. 브랜치를 지우기 전에 `git push origin perf/sync-lock`으로 원격에 올린다.
- 버전을 바꿀 때는 DB 볼륨부터 새로 만든다. 비동기 버전의 V3 마이그레이션(`manager_id` NULL 허용, `managing_hub_id`)은 Flyway가 되돌리지 않아 동기 버전과 스키마가 맞지 않는다. `script/run.sh --reset`로 띄우고 모든 서비스가 뜬 뒤 시드(`delivery-e2e.sql`, `delivery-load.sql`)를 넣는다. 서비스가 다 뜨기 전에 넣으면 테이블이 없어 한 트랜잭션 전체가 롤백되고 로그인이 401로 실패한다.
- 절차는 지금 측정과 같다. 예열 2회(초당 10+10, 1분) → `reset-delivery-data.sh` → 측정(초당 40+40, 1분). 셸에 남은 `CREATE_RATE` 같은 환경 변수를 먼저 지운다.
- Prometheus·Grafana(`localhost:3000`, `logistics-overview` 대시보드)는 기본 `docker-compose.yml`에 들어 있어 지금까지의 측정도 켠 상태에서 했다. 다시 잴 때도 같은 조건이다.
- Grafana는 캡처 범위를 측정 시작~끝으로 맞춘다. 수집 주기가 15초라 1분 측정은 점이 4개뿐이다. 응답 시간 시계열은 k6 요청별 기록(`*.csv.gz`)으로 10초 단위 그래프를 그리는 편이 정확하다. Grafana는 Hikari·CPU·스레드처럼 서버 쪽 지표를 보여 줄 때 쓴다.
- Prometheus에는 볼륨이 없다. 컨테이너를 다시 만들면 이전 측정 지표가 사라지므로 캡처는 측정 직후에 한다.
- 배정 지연(`assigned_at - created_at`)은 지표로 내보내지 않는다. `load-test/assignment-stats.sh`의 DB 집계로 따로 그린다. 동기 버전은 생성 시 배정이라 지연이 0이다.
- 결과 원본(`load-test/results/`)은 `.gitignore` 대상이다. 정리 전까지 다른 곳에 복사해 둔다.
