# T09 주문 확정 뒤 배정하고 배정 결과를 order가 알린다

- 브랜치: `feat/delivery-T09` (`origin/dev` 97ed81f 기준. T08은 merge 커밋 #25로 dev에 들어갔다. 2026-10-20 dev로 옮기며 dev의 I-18과 겹친 내부 API 번호를 I-19~I-21로 바꿨다, 결정 로그 29)
- 상태: 구현·테스트 끝(커밋 전). 부하 측정(단계 4, 주문 경로)과 order 담당 리뷰가 남음
- 기간: 2026-10-20 ~
- 범위: 배정 시작을 "배송 저장"에서 "주문 확정"으로 옮긴다. 후보가 없으면 2번 더 시도한 뒤 MASTER에게 수동 지정을 요청한다. 배정이 끝나면 order가 담당자에게 DM을 보낸다. delivery·order 코드, 새 내부 API, 계약 문서, ADR 0016 갱신, 확정 단계 추가 비용 측정
- 범위 밖: 메시지 큐 도입(흐름을 포트 뒤에 두어 나중에 구현만 바꾼다), 발송 보장(Outbox·재처리. ADR 0016 7번 그대로), 프런트 표시
- 관련: 결정 로그 27 → 29, [ADR 0016](../../../docs/decisions/0016-delivery-manager-slack-dm.md), [T06](T06.md)(I-15), [T08](T08.md)

## 왜 (요약, 상세는 결정 로그 29)
1. order는 I-09 응답을 받은 뒤에 주문을 커밋한다. 배정은 배송 커밋 직후 수 ms 안에 끝나므로 배정 완료 알림이 주문 커밋보다 먼저 올 수 있다.
2. 주문 저장이 실패할 배송에도 담당자가 먼저 배정되어 보상 전까지 담당 건수에 섞인다.
3. 순서를 "주문 확정 → 배정 → 알림"으로 고정하면 두 문제가 함께 사라지고, 중복 방지 표시가 필요 없다.

## 흐름
```
order    I-09 호출 ─▶ 응답 ─▶ 주문 커밋 ─▶ ① 주문 확정 요청
delivery  배송 저장(미확정, 배정 안 함)     ─▶ 확정 커밋 ─▶ 배정
                                                 ├─ 성공 ─────────────▶ ③ 배정 완료 알림
                                                 └─ 후보 없음 ─▶ 대기, 주기 작업 2번 더
                                                                 └─ 그래도 없음 ─▶ ② 담당자 없음 알림
                                                                     MASTER가 D-04로 지정 ─▶ ③ 배정 완료 알림
order    ② MASTER에게 Slack(수동 지정 요청)    ③ 주문 ORDERED면 담당자에게 DM
```
- Slack은 order만 보낸다(ADR 0016). 주문 커밋 직후 DM 리스너는 지운다. 채널 Webhook 주문 알림은 그대로다.
- ③이 도착할 때 주문은 반드시 커밋돼 있다. 배송이 취소됐으면 배정·알림을 하지 않는다.
- ①은 한 방향 요청이다. order는 확정 커밋 응답(수 ms)만 받고 배정을 기다리지 않는다.
- 2번은 후보 0명만 센다. user 장애는 세지 않고 계속 자동 재시도한다. 수동 지정 필요로 넘긴 배송은 자동 배정이 건너뛴다.

## 장애별 처리
| 상황 | 처리 |
|---|---|
| ① 확정 요청 실패(delivery 장애·타임아웃) | 주문은 되돌리지 않는다. 멱등이라 order가 몇 번 다시 보낸다. 그래도 실패하면 로그 |
| 확정을 끝내 못 받은 배송 | delivery 주기 작업이 오래된 미확정 배송을 order에 물어 확정 또는 정리 |
| ① 응답만 유실 | 다시 보내도 결과가 같다(멱등) |
| user 장애로 배정 불가 | 대기 유지, 자동 재시도. 2번에 세지 않는다 |
| ②·③ 요청 실패(order 장애) | 재전송하지 않는다(ADR 0016 7번). MASTER는 "수동 지정 필요" 배송을 목록으로 찾는다(프런트 협업) |

## 정할 것 ⏳
- 확정 신호 유실 안전망: 오래된 미확정 배송을 delivery 주기 작업이 order에 물어 확정하거나 정리한다. 기준 시간과 order 조회 API
- ① 확정 요청을 어느 스레드에서 보낼지: 처리 단계 마지막(Saga에 보임, `order-creation` 4개 점유 증가) / 커밋 후 리스너 / 별도 스레드
- 재시도 2번의 간격(지금 주기 작업 30초면 약 1분 뒤 MASTER 알림), 시도 횟수와 "수동 지정 필요"를 어디에 남길지(배송 또는 구간 컬럼)
- ② MASTER에게 보내는 곳: 기존 채널 Webhook(누가 MASTER인지 몰라도 됨) / MASTER 개인 DM(user에 MASTER 목록·이메일 API가 없어 새로 필요)
- 새 내부 API 번호·경로: ① 주문 확정(order → delivery), ② 담당자 없음, ③ 배정 완료(delivery → order), 안전망 조회(delivery → order)
- ③ DM 메시지의 업체명: `Order`에 없다. company 재조회 / 주문에 저장 / 메시지에서 제외
- DM 발송 뒤 주문 취소: 취소 DM을 T09에 넣을지 다음 태스크로 미룰지
- 배정 작업이 취소된 배송의 구간을 건너뛰는지 코드 확인
