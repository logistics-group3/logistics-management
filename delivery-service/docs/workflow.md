# delivery 작업 규칙

delivery-service 담당자가 작업을 태스크 단위로 나누고 기록하는 규칙이다. 팀 공통 규칙([Git 작업 가이드](../../docs/guides/git-workflow.md), 루트 `AGENTS.md`)이 먼저이고, 이 문서는 그 안에서 delivery만의 방식을 더한다. 코드 규칙은 [`../AGENTS.md`](../AGENTS.md)에 있다.

## 1. 왜 태스크 단위인가
기능마다 브랜치를 따면(`feat/delivery-entity`, `feat/delivery-query` ...) 브랜치가 많아지고 작업 흐름이 흩어진다. 그래서 며칠 분량의 작업 묶음을 태스크 하나로 정하고, 태스크 하나를 브랜치 하나로 진행한다. 세부 작업은 커밋으로 나눈다.

`dev`에는 squash로 합치므로 `dev` 이력에는 태스크마다 커밋 하나만 남는다. 커밋 단위의 세부 기록은 PR의 Commits 탭과 태스크 문서(`tasks/T{nn}.md`)에 남긴다.

## 2. 태스크
- 번호는 `T01`, `T02`처럼 붙인다. `#1`은 GitHub가 이슈·PR 번호로 링크하므로 쓰지 않는다.
- 목록은 [`tasks/README.md`](tasks/README.md)에 두고, 태스크마다 `tasks/T{nn}.md`를 만든다.
- 태스크 하나는 PR 하나로 리뷰할 수 있는 크기로 정한다. 기준은 2~3일 분량, 커밋 10개 안팎이다. 이보다 커지면 다음 태스크로 나눈다.

## 3. 브랜치·커밋·PR
| 대상 | 형식 | 예 |
|---|---|---|
| 브랜치 | `feat/delivery-T{nn}` (`dev`에서 따고 `dev`로 squash) | `feat/delivery-T01` |
| 커밋 | `type(delivery): 요약 (T{nn})` | `feat(delivery): 배송·구간 엔티티 추가 (T01)` |
| PR 제목 | `type(delivery): T{nn} 태스크 제목` | `feat(delivery): T01 배송 도메인 기반 구축` |

- 커밋 하나에 세부 작업 하나를 담고, 커밋마다 빌드가 깨지지 않게 한다(공통 규칙).
- 커밋할 때 태스크 문서의 "작업 기록"에 그 커밋 항목을 같은 커밋에 함께 넣는다. 커밋 해시는 squash 후 바뀌므로 적지 않고 커밋 요약으로 찾는다.
- PR 본문 상황(S)에 태스크 문서 링크를 건다.

## 4. 태스크 문서 형식
```markdown
# T01 배송 도메인 기반 구축

- 브랜치: feat/delivery-T01
- 상태: 진행 | 리뷰 | 완료
- 기간: 2026-10-15 ~
- 범위: 이 태스크가 끝내야 하는 것
- 범위 밖: 다음 태스크로 넘기는 것
- 관련: SA 절, ADR, 협업 로그 ID

## 세부 작업
- [x] 끝난 세부 작업 (커밋 요약)
- [ ] 남은 세부 작업

## 작업 기록
### 2026-10-15
- `feat(delivery): 배송·구간 엔티티 추가 (T01)`
  - 무엇을: Delivery, DeliveryRoute 엔티티와 상태 enum
  - 왜: 상태 전이를 엔티티 메서드에서 검증하기 위해(SA 2.5)
  - 확인: `./gradlew :delivery-service:test` 통과
```

- "작업 기록"은 날짜별로 쌓는다. 하루 정리를 쓸 때는 그날 날짜 항목을 보면 된다.
- 막혔던 문제는 `docs/troubleshooting.md`에, 되돌리기 어려운 결정은 `docs/services/delivery/decisions/`에 쓰고 여기서는 링크만 건다.

## 5. 다른 문서와의 관계
| 문서 | 역할 | 갱신 |
|---|---|---|
| `domain/delivery.md` | 배송 도메인을 누구나 이해할 수 있게 설명(용어, 상태, 배정, 흐름, ERD, 권한) | 설계가 바뀔 때 |
| `domain/delivery-api.md` | 제공·사용 API의 요청·응답 상세 | API를 정하거나 바꿀 때. `docs/services/delivery/README.md` 2절 계약 요약도 같은 PR에서 고친다(`docs-check`는 README만 검사한다) |
| `domain/delivery-decision-log.md` | 대화하며 결정에 이른 과정 | 결정이 날 때(6절) |
| `docs/services/delivery/decisions/` | 확정된, 되돌리기 어려운 결정(ADR) | 결정 로그의 결론이 확정될 때. 로그에서는 ADR 링크만 건다 |
| `tasks/T{nn}.md` | 태스크의 범위와 커밋 단위 누적 기록 | 커밋할 때 |
| `docs/services/delivery/notes.md` | 기능 하나의 핵심 요약(`impl-service` 스킬). 상세는 `domain/`, `tasks/`를 링크하고 다시 쓰지 않는다 | 기능 하나를 끝냈을 때 |
| `docs/progress/feat-delivery-T{nn}.md` | 지금 상태와 다음 단계(인계 메모, 팀 규칙) | 단계가 바뀔 때. 상세는 태스크 문서 링크로 대신한다 |
| `docs/services/delivery/README.md` | 다른 서비스에 보이는 계약과 구현 현황 | API·테이블을 바꿨을 때(`script/docs-check.sh`가 검사) |

## 6. 결정 로그 쓰는 법
- **언제**: 대화에서 설계 결정이 나면 그 응답 안에서 바로 쓴다. 나중에 몰아서 쓰면 컨텍스트 압축 때 "왜"와 "어떻게"가 빠진다.
- **무엇을**: 선택지 중 하나를 고른 것, 이전 결론을 뒤집은 것, SA와 다르게 가기로 한 것. 단순 확인이나 오타 수정은 쓰지 않는다.
- **형식**: 맨 아래에 `## N. 주제`를 추가하고 **왜 → 어떻게 → 결론**으로 쓴다. "한눈에 보기" 표에도 한 줄을 추가한다. 이전 결론이 바뀌면 그 항목 결론에 `→ N`을 붙인다.
- **안전망**: 개인 훅을 쓰면 컨텍스트가 기준을 넘을 때 "기록 안 된 결정을 정리하라"는 알림이 한 번 오고, 압축 직후에는 결정 로그와 인계 파일을 다시 읽으라는 알림이 온다. 훅은 개인 설정이라 저장소에 없다.

## 7. 테스트 기준
팀 [테스트 규칙](../../docs/agents/rules/test.md)이 먼저이고, delivery에서는 아래 기준을 보탠다.

- **기준**: "이 테스트가 없으면 잡지 못하는 버그가 무엇인가"에 답할 수 있는 테스트만 쓴다.
- **쓰는 것**

| 대상 | 방식 | 예 |
|---|---|---|
| 상태 전이 | 단위(Spring 없음). 팀 규칙상 필수 | 3구간·2구간 흐름, 앞 구간 도착 전 다음 구간 출발 불가, 취소는 `PICKUP_WAITING`에서만 |
| 멱등성 | 통합(`PostgresIntegrationTest`) | 같은 orderId로 I-09 재호출·동시 호출 시 배송 1건 |
| 자동 배정 | 통합 | 담당 건수 최소, 동점이면 userId 순, 같은 배송 안 연속 배정 반영 |
| Saga 분기 | 서비스 단위(목) | I-14 빈 목록이면 `DELIVERY_MANAGER_NOT_FOUND`, Feign 실패 전파 |
| 권한 필터 검색 | 통합 | 배송담당자는 담당 구간이 있는 배송만 조회 |

- **쓰지 않는 것**: getter, 단순 DTO 변환, 컨텍스트 로드만 하는 테스트, 서비스 호출을 넘기기만 하는 컨트롤러 테스트.
- 팀 규칙의 "서비스 public 메서드마다 성공 1개와 실패 케이스"는 실패 케이스를 의미 있는 분기(보상, 권한, 멱등)로 골라 채운다.
