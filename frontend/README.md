# SPARTA LOGISTICS 운영 콘솔

실제 Gateway API로 주문 O-01~O-06과 배송 D-01·D-02·D-05를 테스트하는 로컬 웹 UI다. 회원가입 U-01·로그인 U-02·내 정보 U-03, 업체 C-01·C-04, 상품 P-01, 배송담당자 지정 U-07, 대시보드와 기준 정보 조회를 함께 제공한다.

`/guide`는 멘토·튜터용 테스트 가이드다. 로그인 전에도 열리고, 발제 필수 기능별 시나리오의 절차·기대 결과와 계정 버튼(그 계정으로 로그인한 뒤 시나리오 화면으로 이동)을 보여 준다. 처음 보는 사람용 요약은 [멘토·튜터 테스트 안내](../docs/guides/mentor-test.md)에 있다.

## 실행

저장소 루트에서 실행한다. Node.js 24, npm, Python 3, Docker Desktop이 필요하다.

```bash
npm --prefix frontend ci
script/ui-test.sh up
script/ui-test.sh seed
script/ui-test.sh frontend
```

첫 빌드는 시간이 걸린다. `seed`는 Gateway 로그인과 허브 조회가 준비될 때까지 최대 30회, 실패 사이에 2초를 두고 재확인한다. 포트가 사용 중이면 기존 프로세스를 종료하지 말고 대상을 확인한다.

| 용도 | 주소 |
|---|---|
| 웹 UI | http://127.0.0.1:5174 |
| Gateway API | http://127.0.0.1:18080/api/v1 |
| Swagger | http://127.0.0.1:18080/swagger-ui.html |
| Eureka | http://127.0.0.1:18761 |
| PostgreSQL | 127.0.0.1:15432 |
| Config Server | http://127.0.0.1:18888 |
| Zipkin(분산 추적) | http://127.0.0.1:19411 |
| Grafana(메트릭 대시보드, 로그인 없이 보기) | http://127.0.0.1:13000 |
| Prometheus(수집 대상) | http://127.0.0.1:19090/targets |

실제 Gateway 매핑은 `docker compose -p logistics-ui-test --env-file .env.ui-test port gateway-service 8080`으로 확인한다. 프런트의 기본 프록시는 이 테스트 Gateway다. 다른 환경을 사용하려면 `frontend/.env.local`의 `GATEWAY_URL`을 바꾸고 Vite를 다시 실행한다.

## 회원가입부터 시작하기

http://127.0.0.1:5174/signup 에서 새 계정을 만든다. 로그인 화면의 회원가입 링크로도 이동할 수 있다.
아이디는 소문자·숫자 4~10자, 비밀번호는 8~15자이며 대문자·소문자·숫자·특수문자를 포함한다. 비밀번호 확인, 이름, Slack 가입 이메일, 소속 유형·소속명을 입력한다. Slack 멤버 ID 입력칸은 없으며 이메일은 필수다. 서버도 멤버 ID 없이 가입하도록 user V3가 적용돼야 한다.
가입 성공 후 아이디가 채워진 로그인 화면으로 이동한다. 비밀번호는 저장하거나 다음 화면으로 전달하지 않는다. 중복 아이디와 입력 오류는 화면에서 확인한다.

새 회원은 서버의 기존 계약대로 USER·배송담당자 아님으로 생성된다. 소속명을 입력하는 것은 기존 업체·허브의 담당자 권한을 부여하는 것과 다르다.
가입 직후 업체 관리에서 업체를 등록하면 C-01이 로그인한 USER를 담당자로 자동 연결한다. 본인 업체는 이름·주소·허브를 수정하고 상품을 등록할 수 있다.
MASTER는 업체 등록 시 담당자를 선택하고, 업체 상세의 `업체 정보·담당자 변경`에서 다른 사용자로 변경한다. 사용자 상세에서는 배송 담당자 지정·해제와 담당 허브를 설정한다. 계정의 MASTER/USER 역할 변경은 제공하지 않는다.
배송담당자 지정 시 사용자 소속도 해당 허브로 바뀌고, 이후 생성하는 배송의 자동 배정 후보가 된다. 기존 배송 구간은 자동 재배정되지 않는다. 변경된 사용자로 다시 로그인하거나 내 프로필을 새로고침해 지정 상태를 확인한다.

### 새 계정으로 주문까지

1. 회원가입 후 로그인한다. 대시보드의 `내 업체 등록부터 시작하세요` 안내 또는 업체 관리 → 업체 등록으로 이동한다.
2. 업체명·주소를 입력하고 `서울특별시 센터`를 선택한다. 일반 USER의 담당자는 본인으로 자동 연결된다.
3. 주문 관리 → 새 주문 등록에서 공급업체 `스파르타 서플라이`, 수령업체 `방금 등록한 내 업체`를 선택한다. 준비된 상품·수량으로 주문한다.
4. 공급업체도 새로 만들려면 다른 이름으로 업체를 한 곳 더 등록하고, 업체 상세의 `이 업체에 상품 등록` 또는 상품 관리 → 상품 등록에서 상품·단가를 추가한다. 두 업체를 같은 허브로 선택한다.
5. 직접 등록한 상품으로 주문하고 상세의 가격·배송·요청사항을 확인한다.

### 관리자로 담당자 연결

1. 아래 `uimaster` 계정으로 로그인한다.
2. 업체 관리 → 업체 상세 → `업체 정보·담당자 변경`에서 이름·아이디로 사용자를 찾아 저장한다. 새 회원이 선택지에 없으면 `사용자 목록 새로고침`을 누른다.
3. 사용자 관리 → 사용자 상세 → `배송 담당자로 지정`을 체크하고 담당 허브를 선택해 저장한다.
4. 해당 사용자로 로그인한 뒤 본인 업체 주문 또는 배정된 배송의 구간 처리를 확인한다. 기존 배송 재배정은 이번 UI 범위에 포함하지 않는다.

[Slack 이메일·Webhook·개인 DM 차이](../docs/learning/junhyun/qna/2026-10-15-slack-webhook-email-and-dm.md)를 별도로 정리했다. MASTER는 사용자 상세의 `Slack DM 알림`에서 이메일을 설정·해제한다. 저장 성공은 연락처 저장을 뜻하며 Slack 계정 조회·발송 성공과는 구분한다.
서버 설정과 실제 검증 상태는 [Slack DM 실행 안내](../docs/guides/slack-dm.md)에 있다. 현재 로컬은 `uidriver`에 승인된 본인 이메일 하나를 연결했고 그 주소에만 DM을 허용한다. Webhook은 꺼져 있다. 새 주문에 배정되면 본인 Slack DM을 받는다.

## 테스트 계정

아래는 전용 테스트 DB에 생성하는 공개 예제 계정이다. 공통 비밀번호는 `UiLocal!2026`이다. 외부 공개 환경에 사용하지 않는다.

| 아이디 | 역할 | 테스트할 내용 |
|---|---|---|
| `uimaster` | MASTER | 전체 주문·배송 조회, 주문 생성·수정·취소·삭제, 모든 배송 구간 처리 |
| `uiuser` | USER / 한빛 리테일 담당자 | 본인 주문 조회·생성·수정·취소. MASTER 삭제 버튼 없음 |
| `uidriver` | USER / 서울 허브 배송담당자 | 배정된 배송 조회와 구간 출발·도착 |
| `uiviewer` | USER / 새봄 유통 담당자 | 다른 업체 담당자 권한과 본인 주문 범위 |
| `uidrvgg` | USER / 경기 북부 센터 배송담당자 | 경기 북부에서 출발하는 집하·허브 간 이동 구간 처리, 다른 허브 배송 조회 차단(403) |
| `uidrvbs` | USER / 부산광역시 센터 배송담당자 | 부산에 도착한 허브 간 배송의 수령업체 배송 구간 처리 |

시드는 사용자 6명, 허브 17개(기존 Flyway), 업체 7개, 상품 6개, 주문·배송 12건을 준비한다. 멘토 가이드용으로 발제 예시 업체(경기 건조식품 가공 → 부산 수산 도매, 마른오징어 가공품)와 롤백 시나리오용 대전 업체 2곳을 만든다. 대전 허브에는 배송담당자를 두지 않는다. 새 배송담당자는 서울 허브에 두지 않아 기존 E2E의 `uidriver` 자동 배정이 바뀌지 않는다.
기존 시드를 다시 실행하면 사용자가 변경한 주문 상태를 유지하고, 나중에 추가된 참조 데이터만 만든다. 실제 식별자는 Git에서 제외한 `.local/ui-test-data.json`에 저장된다(`scenario`에 가이드용 업체·상품과 `rollbackHubId`).

## 직접 해보기

1. 회원가입부터 확인하려면 위 가입 화면에서 계정을 만든다. 준비된 업무 흐름을 확인하려면 `uimaster`로 로그인한다. 대시보드의 실제 건수와 주문·배송 메뉴가 보이면 성공이다.
2. 주문 관리 → 새 주문 등록에서 공급업체 `스파르타 서플라이`, 수령업체 `한빛 리테일`, 상품·수량을 선택한다. 제출 후 주문 상세와 연결된 배송이 보인다.
3. 요청사항을 수정하고 저장한다. 상세를 닫았다 다시 열어 수정값을 확인한다.
4. 집하 대기 주문을 취소하고 삭제한다. 주문·배송 목록에서 사라지는지 확인한다.
5. 다른 주문을 만든 뒤 배송 상세에서 집하 출발 → 도착 → 업체 배송 출발 → 도착을 누른다. `배송 완료`가 되면 MASTER로 주문 삭제를 테스트한다.
6. 로그아웃 후 `uiuser`·`uidriver`로 바꿔 조회 범위와 버튼 권한을 비교한다. 화면에 표시한 권한과 별개로 서버가 최종 인가한다.
7. 브라우저를 새로고침하면 재로그인한다. JWT는 메모리에만 있으며, 미완료 주문의 키·본문은 사용자별 sessionStorage에 보존된다.

## 검증

백엔드와 프런트를 모두 확인하는 공통 기준은 [전체 빌드·검증](../docs/guides/full-build.md)이다. Gradle에는 이 프런트 빌드가 포함되지 않는다.

```bash
npm --prefix frontend run test
npm --prefix frontend run build
npm --prefix frontend run lint
npm --prefix frontend run format:check
npm --prefix frontend run test:e2e
./gradlew build
script/docs-check.sh
script/error-codes-check.sh
```

E2E는 실행 중인 UI·테스트 서버와 시드가 필요하며 로컬 Google Chrome을 사용한다. `frontend/test-results/`에 화면 증거, `frontend/playwright-report/`에 보고서가 생성된다. 인증 토큰을 포함할 수 있는 네트워크 trace는 저장하지 않는다. E2E가 생성한 주문은 각 정상 시나리오 마지막에 취소 또는 배송 완료 후 삭제한다.
실제 DM이 활성화돼 있으면 E2E·시드는 실행을 거부한다. `.env.ui-test`의 `SLACK_DM_ENABLED=false`를 저장한 뒤 `script/ui-test.sh up`으로 컨테이너에 반영하고 자동 검증한다. E2E는 UI 프록시가 전용 DB로 연결되는지도 확인한다.

[검증 기록](../docs/reviews/logistics-test-ui.md)에서 실제 실행 결과와 검증 범위를 확인한다.
[Slack DM 검증 기록](../docs/reviews/slack-dm.md)은 이메일 UI를 포함한 최신 41개 단위·15개 E2E·729개 백엔드 테스트와 실제 DM 1건의 범위를 구분한다.

## 중지·재실행

```bash
script/ui-test.sh status
script/ui-test.sh down     # 테스트 컨테이너만 중지·제거, DB 볼륨 유지
script/ui-test.sh up       # 같은 DB로 다시 실행
```

프런트는 실행 터미널에서 Ctrl+C로 중지한다. 소스 변경은 Vite가 반영하고, 백엔드 변경은 테스트 스택의 `up`으로 다시 빌드한다. `.env.ui-test`는 최초 한 번 별도 DB/JWT 비밀값을 생성한다. 기존 개발 환경의 `.env`, `logistics-management` 프로젝트와 DB 볼륨은 사용하지 않는다. 테스트 스택에서는 Slack Webhook을 항상 비운다.

## 구현 구조와 이유

| 위치 | 책임 |
|---|---|
| `src/app/` | 인증, 메뉴·레이아웃, 경로 연결 |
| `src/features/` | 주문, 배송, 대시보드, 기준 정보, 멘토 테스트 가이드(`TestGuide.tsx`) 화면 |
| `src/shared/test-guide.ts` | 가이드의 실행 주소·테스트 계정·시나리오(기대 결과는 실제 서버 동작 기준) |
| `src/shared/api.ts` | Gateway 호출, 오류, 401 처리, 손실 없는 금액 파싱 |
| `src/shared/order-request.ts` | 사용자별 미완료 주문 보존과 실패 분류 |
| `src/shared/delivery-rules.ts` | 담당자·구간 순서에 맞는 다음 액션 표시 |
| `src/shared/catalog-rules.ts` | 업체·담당자 요청 범위와 정확한 원화 가격 검증 |
| `src/components/ui/` | 공통 버튼과 키보드 초점이 유지되는 Radix 다이얼로그 |

- 조회 상태는 TanStack Query로 관리한다. 변경 후 주문·배송 캐시를 함께 갱신해 상세와 목록의 상태를 맞춘다. 쓰기 요청은 자동 재시도하지 않는다.
- 주문 생성 전에 원문·키를 저장한다. 응답을 못 받았다는 이유만으로 새 키를 만들면 서버에서 이미 만든 주문이 중복될 수 있다. 같은 키 재확인은 최초 응답을 반환하므로 이후 화면은 GET으로 현재 상태를 읽는다.
- Java long 원화 값은 `lossless-json`으로 문자열을 유지하고 BigInt로 표시·미리 계산한다. 상품 등록 요청도 BigInt를 정확한 JSON 정수로 직렬화한다. JavaScript Number를 거치며 마지막 자릿수가 바뀌는 것을 막는다.
- API는 기존 `/api/v1/**`만 사용한다. 브라우저에서 내부 API나 각 서비스 포트로 직접 접근하지 않는다.
- 기술 선택과 대안은 [ADR 0015](../docs/decisions/0015-logistics-test-ui.md)에 있다.

## 현재 범위와 연동 조건

- 같은 허브 주문(집하·업체 배송 2구간)과 다른 허브 간 주문(집하·허브 간 이동·업체 배송 3구간)을 모두 실제 서비스로 연동한다. 다른 허브 간 주문 제한은 hub I-03(PR #9)이 dev에 들어온 뒤 실제 주문·구간 처리를 확인하고 해제했다(2026-10-16). 화면은 다른 허브를 고르면 3구간 안내만 보여 준다.
- 업체 등록·수정·담당자 변경, 상품 등록, 사용자 배송담당자·허브 지정까지 화면에 연결했다. 업체·상품 삭제, 상품 수정, 계정 역할 변경·비활성화, 배송지 수정·기존 구간 재배정은 후속 범위다.
- 업체·상품 생성 API에는 멱등키 계약이 없다. 응답 미확정 시 자동 재시도를 막고 목록에서 등록 여부를 먼저 확인하도록 안내한다. 새로 등록하기 전에 결과를 확인한다.
- 주문 결과가 미확정이면 원래 키로만 확인한다. 복구 대기·키 충돌은 새 주문으로 우회하지 않는다. 서버의 생성 진행 조회·자동 복구 API는 아직 없다.
- 미완료 요청은 같은 탭에서 유지된다. 탭을 닫으면 sessionStorage가 사라지므로, 결과 미확정 안내가 있으면 탭을 유지한다. 서버 멱등키만으로 서로 다른 새 키의 중복 주문까지 막지는 못한다.
- 배송 취소·출발 동시성 검토 등 기존 서비스 연동 항목은 [주문 연동 계약](../docs/services/order/integration-contract.md)을 따른다. UI 검증은 서버의 추가 동시성 보장을 뜻하지 않는다.
