# 0016. 주문 커밋 후 배송담당자 이메일로 Slack DM 발송

- 상태: 제안 (사용자가 구현과 Slack 앱 설정을 요청함, 서비스 간 계약은 팀 리뷰 대상)
- 날짜: 2026-10-15
- 갱신: 2026-10-16 (구현·실연동 검증), 2026-10-20 (발송 시점을 배정 완료로 변경, 아래 "갱신: 발송 시점")
- 결정자: Junhyun An 작업

## 맥락

사용자는 운영 UI를 커밋한 뒤 배송담당자 이메일 기반 Slack DM과 기존 Slack 앱 설정을 요청했다.
구현 전 채널 Webhook은 목적지가 고정되어 있고, 주문 생성 이벤트에는 배송 ID가 없었다. 회원은 slackId만 저장하며 기존 내부 배송 조회 I-10은 담당자 목록을 반환하지 않았다.

## 결정

1. user에 `slackEmail`(최대 254자)을 추가한다. 2026-10-16 사용자의 후속 요청으로 신규 U-01과 가입 화면은 Slack 이메일만 필수 입력으로 받고 멤버 ID를 받지 않는다. V2는 nullable 이메일을 추가하고 V3는 slack_id의 NOT NULL만 해제해 기존 값을 보존한다. MASTER의 기존 U-06으로 이메일을 설정·변경·해제한다. 기존 데이터·초기 MASTER는 이메일이 없을 수 있다.
2. 기존 I-01·I-10·I-14의 응답 필드 구성은 유지한다. 이메일로 가입한 신규 사용자는 I-01·I-14의 slackId가 null일 수 있다. 새 내부 읽기 API I-15(`/internal/deliveries/{deliveryId}/notification-recipients`)와 I-16(`/internal/users/{userId}/notification-contact`)를 사용한다. I-15는 배송·주문 ID, 상태, 중복 없는 담당자 ID를 반환한다. I-16은 사용자 ID·배송담당 여부·Slack 이메일을 반환한다.
3. OrderCreatedEvent에 deliveryId를 추가한다. 별도 AFTER_COMMIT 리스너와 비동기 DM 송신 포트로 기존 Webhook과 실패를 격리한다. 완료된 멱등키 재요청에는 이벤트가 다시 발생하지 않는다.
4. 비동기 작업은 현재 배송의 WAITING·MOVING 구간 담당자를 조회한다. 완료·취소·삭제 배송, 해제·탈퇴 사용자, 이메일 미설정은 발송을 건너뛴다. 한 이벤트에서 동일 담당자·동일 이메일의 시도는 한 번으로 제한한다. 조회 직후 재배정·취소가 일어나는 경쟁까지 원자적으로 막는 계약은 아니다.
5. Slack Web API는 이메일 조회 → DM 열기 → 메시지 발송 순으로 사용한다. 봇 스코프는 users:read.email, im:write, chat:write와 이 앱의 설정 UI가 의존 권한으로 요구한 users:read다. 토큰과 이메일은 로그에 남기지 않고 HTTP 응답의 ok=false도 실패로 처리한다.
6. 토큰·워크스페이스 ID·활성화 플래그·선택 수신자 허용 목록을 서버 환경 변수로 받는다. 기본은 비활성화한다. 자동 테스트는 Slack HTTP 대역을 사용하며 실제 발송은 수신자와 테스트 메시지 범위를 확인한 뒤 별도로 검증한다.
7. Slack POST를 자동 재전송하지 않는다. 응답 유실은 발송 여부가 불확실할 수 있다. 전송 실패·큐 포화는 주문 성공이나 보상을 바꾸지 않는다. Outbox·자동 재처리·재시작 후 발송 보장은 이번 범위에 포함하지 않는다.

## 검토한 대안

- Webhook payload에 이메일 추가: Webhook의 채널은 설치 때 정해져 수신자를 이메일로 바꿀 수 없다.
- slackId에 이메일을 저장: 기존 수령인 Slack ID 계약과 의미가 달라진다. 별도 이메일 필드를 두고 신규 가입에서만 필수로 검증한다.
- 기존 내부 응답에 이메일·담당자 필드 추가: 다수 소비자의 계약에 영향을 주므로 목적이 드러나는 별도 읽기 API를 둔다.
- 배송 생성 직후 DM: 이후 주문 저장이 실패할 수 있다. 주문 생성 알림은 주문 커밋을 기준으로 한다.
- DM 실패 시 주문 롤백: 이미 커밋한 업무 결과를 외부 알림 장애로 바꾸지 않는다.

## 결과

기존 서비스 계약은 유지하면서 필요한 연락처·담당자 조회를 추가한다. user·delivery·order와 UI·설정을 함께 검토해야 한다.
새 API와 연락처 필드는 협업 로그와 서비스 문서에 인계한다. 실제 Slack 워크스페이스는 디스이스스파르타, 앱은 Logistics Order Noti다.
기존 incoming-webhook 권한과 #물류주문알림 선택을 유지한 채 사용자가 추가 4개 권한을 승인해 재설치했다. Bot Token은 Git에서 제외된 `.env.ui-test`에만 저장했다.
2026-10-16 실제 주문 201 → I-15 → I-16 → Slack DM 접수 1건을 확인했다. 테스트 주문은 취소·논리 삭제했고, 테스트 배송담당자 이메일은 수동 테스트용으로 유지했다. 이후 토큰 노출 대응으로 Bot Token을 폐기·교체했다. 기존 Webhook도 무효화된 것을 확인해 사용자 승인으로 URL과 기존 버전의 기본 개발 주문 컨테이너만 갱신했다. 추가 메시지는 보내지 않았다.
설정·실패 판단·검증 범위는 [Slack DM 실행 안내](../guides/slack-dm.md)와 [검증 기록](../reviews/slack-dm.md)에 둔다.

## 갱신: 발송 시점 (2026-10-20, delivery T09)

delivery가 구간 담당자 배정을 배송 생성에서 떼어 비동기로 바꾸면서(delivery 결정 로그 27) 주문 커밋 직후에는 담당자가 없을 수 있게 됐다. 결정 3·4의 발송 시점을 바꾼다. 상세는 delivery 결정 로그 29, 계약은 order·delivery 협업 창구(I-19~I-21, ORDER-003)에 있다.

- 바뀐 것(결정 3): 주문 커밋 직후 DM 리스너를 지운다. order는 주문을 커밋한 뒤 delivery에 배송 확정(I-19)을 보내고, delivery는 확정 뒤에 배정한다. 배송의 모든 구간에 담당자가 정해지면(자동 배정 또는 MASTER D-04) delivery가 order에 배정 완료(I-20 `ASSIGNED`)를 알리고, order가 주문이 `ORDERED`이고 배송이 같을 때 DM을 보낸다. 확정 뒤에만 배정하므로 알림이 올 때 주문은 반드시 커밋돼 있다.
- 바뀐 것(결정 4): 수신자 조회(I-15)·연락처(I-16)·중복 제거·생략 조건은 그대로다. 메시지의 업체명은 주문에 저장돼 있지 않아 배정 시점에 company I-07로 다시 읽고, 실패하면 이름 없이 보낸다.
- 추가: 후보가 없는 상태가 확정 뒤 60초를 넘으면 delivery가 수동 지정으로 넘기고 I-20 `MANUAL_REQUIRED`를 보낸다. order는 기존 채널 Webhook으로 MASTER에게 수동 지정을 요청한다(MASTER 목록·이메일 API가 없어 개인 DM은 쓰지 않는다).
- 그대로인 것: Slack 호출은 order만 한다. 자동 재전송·발송 보장은 범위 밖이다(결정 7). I-20 요청 실패도 delivery가 다시 보내지 않는다. 상태를 읽은 직후 취소되는 경쟁은 막지 않는다(결정 4).
