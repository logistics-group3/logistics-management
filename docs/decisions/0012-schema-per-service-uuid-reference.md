# 0012. 데이터 분리: 서비스별 스키마, FK 없음, UUID 논리 참조

- 상태: 제안
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-03, 원문 상태 "확정"
- SA v2.0과의 차이: 없음. SA 3.4 DB 분리 전략, 설계 결정 4·8·12와 같다.

## 맥락
- 서비스가 다른 서비스의 테이블을 직접 읽으면, 스키마를 바꿀 때 모두 같이 바꿔야 하는 "분산 모놀리스"가 된다.
- 한편 로컬 PC에서 데이터베이스 5개를 띄우면 메모리·설정 부담이 크다.

## 결정
- PostgreSQL 컨테이너 1개에 서비스별 스키마와 전용 계정을 둔다.
- 서비스 간에는 FK 없이 UUID로만 참조하고, 존재 여부는 Feign으로 확인한다.

## 검토한 대안

| 선택지 | 장점 | 단점 |
|---|---|---|
| 공유 DB + 공유 스키마 | 조인·FK·로컬 트랜잭션 사용 가능 | 서비스 경계가 데이터에서 무너짐 |
| **DB 1개 + 서비스별 스키마·계정 (채택)** | 권한으로 경계 강제, 운영 부담 적음 | DB 장애·부하는 같이 나눔 |
| 서비스별 DB 인스턴스 | 완전한 독립, 독립 확장 | 로컬·비용 부담, 이번 범위에 과함 |

## 결과

### 이유
- 서비스 계정에 자기 스키마 권한만 주면, 다른 서비스 테이블을 실수로 조인하는 것을 DB가 막는다. "논리적 분리"를 약속이 아닌 권한으로 강제한다.
- 여러 서비스가 만드는 ID가 충돌하지 않도록 모든 PK를 UUID로 한다. 주문 ID를 저장 전에 미리 발급할 수 있어 Saga 멱등키로도 쓴다([order 0001](../services/order/decisions/0001-order-creation-orchestration-saga.md)).
- 운영 환경에서는 스키마별로 다른 DB로 나눌 수 있도록, 코드에서는 처음부터 다른 DB처럼 다룬다.

### 트레이드오프
- 서비스 간 참조 무결성을 DB가 보장하지 않는다. 쓰기 전에 Feign으로 존재를 확인하고, 주문에는 상품명·단가를 스냅샷으로 저장한다.
- 서비스를 넘나드는 트랜잭션이 없으므로 보상이 필요하다([order 0001](../services/order/decisions/0001-order-creation-orchestration-saga.md), [order 0002](../services/order/decisions/0002-order-cancel-before-departure.md)).
- UUID는 인덱스가 커지고 순서가 없어 삽입 성능이 떨어질 수 있다. 이번 데이터 규모에서는 문제가 아니고, 필요하면 시간 순서 UUID(v7)로 바꿀 수 있다.

## 면접 답변
> "Database per Service를 로컬에서 현실적으로 구현하려고 DB 인스턴스는 하나, 스키마와 계정은 서비스별로 나눴습니다. 경계를 권한으로 강제하고, 참조는 UUID와 Feign 검증으로, 일관성은 보상으로 맞춥니다."

- **Q. FK가 없으면 고아 데이터는 어떻게 막나요?** 쓰기 시점 검증(Feign)과 삭제 시 연관 처리([company 0002](../services/company/decisions/0002-delete-stops-stock-sales.md))로 막고, 보상 실패는 ERROR 로그로 남겨 수동 처리합니다. 완벽하게 막을 수는 없고, 그것이 MSA의 비용이라고 설명합니다.
- **Q. 다른 서비스 데이터가 필요한 조회는요?** 필요한 값은 요청에 담아 넘기거나(order → delivery), 스냅샷으로 저장합니다. 조회가 많아지면 CQRS나 이벤트 기반 복제가 다음 단계입니다.
- **Q. MSA에서 트랜잭션을 어떻게 보장했나요?** 보장하지 않고 최종 일관성을 택했습니다. 서비스 안은 로컬 트랜잭션, 서비스 간은 Saga 보상과 멱등성으로 맞춥니다. (원문 부록 B)
