# 0008. 공통 인프라 브랜치의 선별 통합

- 상태: 제안 (통합 브랜치에서 구현·검증, main 반영은 팀 리뷰 대상)
- 날짜: 2026-10-14
- 결정자: 사용자 요청으로 작성한 통합 후보

## 맥락
팀원들이 같은 공통 인프라 범위를 서로 다른 브랜치에서 구현했다. main은 Initial commit뿐이다. 공통 계약이 다른 구현을 전체 병합하면 설정·인증·DB 접근 방식이 충돌한다.

## 결정
- junhyun의 Java 17 toolchain, 루트 멀티 모듈, Config Server, common-core/common 분리, Spring Security Gateway, 인증, Flyway 및 테스트를 기반으로 사용한다.
- haneol의 공용 사용자 헤더 추출 방식으로 역할 검사에서도 완전한 사용자 컨텍스트를 검증한다.
- KEJ의 반복 논리 삭제 방어로 최초 삭제 Audit을 보존한다.
- KMH의 환경 변수 DB 초기화 방식을 psql 인용 처리와 함께 적용한다.
- seungkeun의 public 스키마 접근 제거를 적용해 서비스별 스키마 격리를 보완한다.
- 원본 checkout·컨테이너를 보존하기 위해 호스트 포트와 Compose 프로젝트를 분리해서 검증한다.

## 검토한 대안
- haneol의 DB 컨테이너 5개·자동 설정 polling: 현재 SA와 다르거나 별도 개인 제안이므로 제외한다.
- KEJ의 전체 AutoConfiguration 전환: 현재 스캔 구조가 작동하며 전환 비용에 비해 이익이 작아 보류한다.
- KMH의 이전 SA·UUID Audit·사용자 관리 선구현: 현재 설계 또는 공통 인프라 범위와 달라 제외한다.
- seungkeun의 생성 전용 감사 Entity·알림 비동기 기반: 사용 대상이 고도화 범위이거나 현재 요구를 충족하지 않아 제외한다.
- 정렬 허용 목록·QueryDSL helper: 아이디어는 유효하지만 현재 검색 API가 없어 보류한다. 실제 검색 API를 구현할 때 API별 허용 필드를 검증해야 한다.
- 자동 MASTER 생성: 기존 명시적 승격 스크립트를 유지한다.

## 결과
서비스 간 헤더·응답·DB 계약을 유지하며 실제 사용 중인 공통 동작을 보완한다. 후보 브랜치의 개인 결정 기록을 팀의 최종 합의로 승격하지 않는다. DB 초기화는 새 볼륨에서만 실행되므로 기존 DB 비밀번호 변경과 Flyway 도입 전 DB 이행은 별도 검토가 필요하다. 출처와 검증 결과는 `docs/reviews/base-setting-integration.md`에서 관리한다.
