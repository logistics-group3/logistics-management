# 시나리오 테스트 안내

저장소를 받은 뒤 발제 필수 기능을 화면에서 차례로 확인하는 방법이다. 개발 DB와 분리된 전용 테스트 환경을 띄우고, 운영 콘솔의 "시나리오 테스트 가이드" 화면에서 계정 버튼 하나로 시나리오를 시작한다.

## 1. 준비물
- Docker Desktop(메모리 8GB 이상 권장. 서비스 8개와 DB·Zipkin·Prometheus·Grafana가 함께 뜬다)
- Node.js 24, npm, Python 3

## 2. 실행
저장소 루트에서 차례로 실행한다.

```bash
npm --prefix frontend ci     # 처음 한 번
script/ui-test.sh up         # 전용 테스트 스택 빌드·기동(첫 빌드는 몇 분 걸린다)
script/ui-test.sh seed       # 테스트 계정·업체·상품·주문 준비(다시 실행해도 중복되지 않는다)
script/ui-test.sh frontend   # 운영 콘솔(이 터미널은 켜 둔다)
```

브라우저에서 http://127.0.0.1:5174/guide 를 연다. 로그인하지 않아도 가이드가 보인다.

| 화면 | 주소 |
|---|---|
| 시나리오 테스트 가이드 | http://127.0.0.1:5174/guide |
| 운영 콘솔 | http://127.0.0.1:5174 |
| Swagger | http://127.0.0.1:18080/swagger-ui.html |
| Grafana(메트릭) | http://127.0.0.1:13000 |
| Zipkin(분산 추적) | http://127.0.0.1:19411 |
| Prometheus(수집 대상) | http://127.0.0.1:19090/targets |

## 3. 가이드 화면 쓰는 법
- **테스트 계정 표**: 계정 6개(관리자, 업체 담당자 2명, 허브별 배송담당자 3명)와 각 계정으로 확인할 내용이 있다. 공통 비밀번호는 `UiLocal!2026`이다. 전용 테스트 DB에만 있는 공개 예제 계정이다.
- **시나리오 카드**: 발제 필수 기능 가이드 항목별로 절차와 기대 결과를 적었다. "uiuser로 시작" 같은 버튼을 누르면 그 계정으로 로그인하고 시나리오 화면을 바로 연다. 다른 계정으로 로그인돼 있으면 바꿔서 로그인한다.
- **확인 표시**: 카드 왼쪽 동그라미를 누르면 확인 완료로 표시된다. 이 브라우저에만 저장된다.
- **로그인 화면**: "테스트 계정 입력"을 펼치면 계정 버튼으로 아이디·비밀번호를 채운다.

기대 결과는 2026-10-16 실제 서버로 확인한 동작이다. 롤백 시나리오(배송담당자가 없는 대전 허브 주문 → 404, 주문이 남지 않음), 권한 차단(403), 발제 예시의 경기 → 부산 허브 간 배송(구간별 담당자 처리)도 포함한다.

## 4. 준비되는 데이터
`script/ui-test.sh seed`가 공개 API로 만든다. 식별자는 `.local/ui-test-data.json`(Git 제외)에 남는다.

| 데이터 | 내용 | 쓰는 시나리오 |
|---|---|---|
| 계정 | `uimaster`, `uiuser`, `uiviewer`, `uidriver`(서울), `uidrvgg`(경기 북부), `uidrvbs`(부산) | 권한 비교 |
| 업체·상품 | 서울 허브: 스파르타 서플라이(상품 4개), 한빛 리테일, 새봄 유통 | 주문·배송, 업체 권한 |
| 발제 예시 | 경기 북부: 경기 건조식품 가공(마른오징어 가공품), 부산: 부산 수산 도매 | 허브 간 배송(집하 → 허브 간 이동 → 업체 배송 3구간, 구간별 담당자) |
| 롤백용 | 대전: 대전 사무용품 공급(서류 보관함), 대전 오피스 리테일. 대전 허브에는 배송담당자를 두지 않는다 | 실패 시 롤백 |
| 주문 | 서울 허브 주문 12건(주문 완료, 집하 중, 집하 완료, 배송 완료, 취소) | 조회·필터·정렬 |

## 5. 현재 범위
가이드 화면 마지막 절에 같은 내용이 있다.
- 허브 간 이동은 출발 허브에서 도착 허브로 바로 가는 P2P 1구간이다. 중계 허브 경로는 계산하지 않는다(발제의 P2P 기준). 경로 272건은 hub-service의 Flyway V3가 적재한다.
- 재고는 SA v2.0에서 설계 검토 피드백으로 고도화로 옮겨 구현하지 않았다.
- 주문 생성은 수령업체 담당자 또는 관리자만 한다(SA 1.5 #11). 회원가입은 Slack 멤버 ID 대신 가입 이메일을 받는다(ADR 0016).
- 테스트 스택은 Slack Webhook·DM을 끈 상태로 실행된다.

## 6. 끄기와 문제 해결
```bash
script/ui-test.sh status   # 컨테이너 상태
script/ui-test.sh down     # 테스트 스택 중지(DB 볼륨은 남는다)
```
- 5174·18080 등 포트가 이미 쓰이면 다른 실행을 먼저 확인한다. 테스트 스택은 개발 스택(`script/run.sh`, 8080·3000·9090)과 포트가 겹치지 않지만, 두 스택을 동시에 띄우면 메모리가 부족할 수 있다.
- `seed`가 "실제 DM이 활성화된 동안 시드를 실행할 수 없다"로 멈추면 `.env.ui-test`의 `SLACK_DM_ENABLED=false`를 확인하고 `script/ui-test.sh up`을 다시 실행한다.
- 서비스가 막 뜬 직후에는 Gateway가 잠시 503을 줄 수 있다. 30초쯤 뒤 다시 시도한다.
- 실행 방법의 정본은 [frontend README](../../frontend/README.md), 검증 명령은 [전체 빌드·검증](full-build.md)이다.
