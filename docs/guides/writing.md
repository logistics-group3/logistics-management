# 문서 작성 가이드

저장소의 문서, 코드 주석, 커밋·PR 본문, 에이전트가 남기는 기록에 모두 적용한다. 무엇을 어디에 쓰는지는 [문서 지도](../README.md)를 본다.

## 1. 사실 기반으로 쓴다
- 실제 코드와 실행 결과를 기준으로 쓴다. 추측으로 빈칸을 채우지 않는다.
- 확인하지 않은 내용은 "미확인"이라고 적는다. 원인을 찾지 못했으면 "원인: 미확인"으로 쓰고 추측을 사실처럼 쓰지 않는다.
- "완료", "통과"라고 쓸 때는 실행한 명령과 결과를 함께 적는다. 예: `./gradlew build` 성공, 테스트 98개 통과.
- 버전마다 다른 내용은 근거(공식 문서 주소, 실행 결과)를 함께 적는다.
- 사실, 관찰, 추측, 결정을 한 문장에 섞지 않는다. 결정이면 누가 언제 정했는지 적는다.

## 2. 간결하게 쓴다
- 첫 문장에 결론을 쓴다. 설명은 "결론 → 이유 → 이 프로젝트에서는 → 더 깊이" 순서로 쓴다.
- 한 문장에는 한 가지만 쓴다. 문단은 세 문장 안쪽으로 쓴다.
- 여러 항목을 같은 기준으로 비교하면 표로 쓴다. 순서가 있는 절차는 번호 목록으로 쓴다.
- 같은 내용을 두 곳에 쓰지 않는다. 기준 위치 한 곳에 쓰고 다른 곳은 링크한다. 사본을 두면 한쪽만 고쳐져 어긋난다.
- 수치는 단위와 함께 쓴다. "빠르다" 대신 "17초"처럼 쓴다.

## 3. 톤
- 한국어 평서체로 쓴다.
- AI 말투(과한 공감, 감탄, "좋은 질문입니다" 같은 서두, 장황한 요약)와 이모지를 쓰지 않는다.
- 문서만 읽어도 이해되게 쓴다. "위에서 말한", "아까" 같은 대화 맥락에 기대지 않는다.

## 4. 문서가 커질 때
- 한 파일이 300줄을 넘거나 주제가 둘 이상 섞이면 주제별 파일로 나누고, 상위 `README.md`에 목차를 둔다.
- 결정 기록은 한 결정에 한 파일이다. 서비스 결정이 많아지면 `docs/services/{service}/decisions/`처럼 디렉터리로 나눈다.
- 학습 노트는 사람별 폴더에 쓰고, 많아지면 주제별 하위 폴더로 나눈다.
- 지난 내용은 지우지 않고 상태를 바꾼다. 결정이 바뀌면 이전 ADR을 `대체됨 (NNNN)`으로 표시한다. 협업 로그는 `DONE`으로 닫는다.

## 5. 코드 주석
- `Note:` 주석 규칙은 `docs/agents/coding-conventions.md` 3절을 따른다. 한두 문장으로 무엇을 하는지와 왜 볼 만한지를 쓴다.
- 주석으로 이름을 보충해야 하면 이름을 먼저 고친다.
