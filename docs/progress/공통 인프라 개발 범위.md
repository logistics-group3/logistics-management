## 1. 포함 범위

| 영역 | 범위 |
| --- | --- |
| 프로젝트 뼈대 | Gradle 멀티 모듈, Spring Boot·Cloud 버전 고정, 서비스 5개는 빈 모듈(실행되고 Eureka에 등록되는 데까지), 패키지 구조 규칙 |
| eureka-server | 전체 |
| gateway-service | 라우팅, JWT 검증 필터, 클라이언트가 보낸 `X-User-*` 헤더를 지우고 새로 넣기, `/internal/**` 차단, 회원가입·로그인은 인증 없이 통과, 권한 재확인(60초 캐시) |
| user-service (인증 부분만) | 회원가입(U-01), 로그인·JWT 발급(U-02), 내부 사용자 조회(I-01). 사용자 관리 API(U-03부터 U-08)는 제외 |
| common 모듈 | BaseEntity(Audit 필드 + 논리 삭제), AuditorAware, 공통 응답·페이지 응답, 에러 코드 + 전역 예외 처리, `@CurrentUser`(헤더에서 사용자 정보 꺼내기), Feign 호출 시 헤더 전달 |
| 인프라 | docker-compose(postgres + 스키마 생성 SQL + eureka + gateway + user), Dockerfile 템플릿, `.env.example` |

user-service의 인증 부분을 넣는 이유

- 토큰이 있어야 Gateway를 실제로 테스트할 수 있다.
- Gateway가 권한을 다시 확인할 때 user-service 내부 API(I-01)를 부른다.

## 2. 제외 범위

수요일부터 서비스 담당자가 맡는다.

- 도메인별 Entity·CRUD·검색
- 서비스별 FeignClient
- 주문 생성 시 실패를 되돌리는 처리(Saga·보상 트랜잭션)
- 허브 초기 데이터(17개 허브, 허브 간 경로)
- Slack 연동

## 3. 시간이 남으면

- QueryDSL 공통 설정
- Swagger(springdoc) 공통 설정
- 서비스마다 같은 설정을 반복하지 않아도 된다.

## 4. 완료 기준

수요일 리뷰 때 아래 6가지가 되는지로 비교한다.

- [ ]  `docker compose up` 한 번으로 전체가 뜨고, Eureka 대시보드에 서비스가 등록된다.
- [ ]  회원가입 → 로그인 → 토큰 발급이 된다.
- [ ]  토큰으로 Gateway를 거쳐 샘플 API를 부르면, 서비스에서 `@CurrentUser`로 사용자 정보를 받는다.
- [ ]  토큰이 없거나 위조면 401, 일반 사용자가 관리자 전용 API를 부르면 403이 나온다.
- [ ]  외부에서 `/internal/**`을 부르면 막힌다.
- [ ]  클라이언트가 `X-User-Role: MASTER` 헤더를 직접 넣어도 무시된다.

## 5. 화요일 전에 팀이 먼저 맞출 규칙

각자 만든 결과물을 비교하고 하나로 바꿔 끼우려면 겉으로 드러나는 규칙은 같아야 한다. 이게 안 맞으면 수요일 리뷰 시간이 형식 맞추는 데 다 쓰인다. "확정" 칸을 채우고 시작한다.

| 항목 | SA 초안 기준값 | 확정 |
| --- | --- | --- |
| 루트 패키지명 | `com.sparta.logistics.{서비스명}` | com.sparta.logistics |
| 모듈명·포트 | eureka-server 8761, gateway-service 8080, user 8081, hub 8082, company 8083, order 8084, delivery 8085 | eureka-server 8761, gateway-service 8080, user 8081, hub 8082, company 8083, order 8084, delivery 8085, config server,  front 3000(나중에) |
| 버전 | Java 17, Spring Boot 3.x, Spring Cloud는 Boot와 호환되는 버전 | Java 17, Spring Boot `3.5.16` , Spring Cloud 등은 알아서 골라보시죠 |
| API 경로 규칙 | 외부 `/api/v1/...`, 서비스 간 `/internal/...` | SA 문서 기반으로  |
| 응답·에러 형식 | 성공 `status`, `message`, `data` / 에러 `status`, `code`, `message`, `path`, `timestamp` (SA 6.1) | 문서 기반으로 |
| 에러 코드 이름 | `USER_NOT_FOUND`처럼 대문자 스네이크 케이스 (SA 6.1 공통 에러 코드) | 대문자 스네이크 |
| JWT 항목 | `sub`(userId), `username`, `role`, `iat`, `exp` / HS256, 60분 | 문서대로 |
| 헤더 이름 | `X-User-Id`, `X-Username`, `X-User-Role`, `X-Delivery-Manager` | `X-User-Id`, `X-Username`, `X-User-Role`, `X-Delivery-Manager` |
| 브랜치·커밋 규칙 | 미정 | 일단 기본사항 구축때는 /{이름}/base-setting |

## 6. 시간이 부족할 때 대안

네 명이 영역을 하나씩 나눠 맡고(Gateway / user 인증 / common / 인프라) 수요일에 서로 리뷰한다. 각자 전부 만들어 보는 것보다 배우는 건 조금 줄지만, 하루 안에 끝낼 가능성이 훨씬 높다.
