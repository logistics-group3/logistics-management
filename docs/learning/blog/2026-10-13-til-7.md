오늘의 학습 키워드 -
---

- **Gradle 멀티 모듈** — 하나의 Gradle 프로젝트 안에 서비스별 모듈을 두는 구조다. 공통 설정은 루트 `build.gradle`의 `subprojects`에 한 번만 쓰고, 각 모듈에는 자기 의존성만 남긴다. 모듈 하나의 build.gradle이 7~16줄이 됐다.
- **Gradle toolchain** — 셸의 JAVA_HOME과 상관없이 컴파일, 테스트, bootRun을 특정 JDK로 고정하는 설정이다. 내 PC 기본 JDK는 21이지만 프로젝트는 17로 돌아간다. foojay resolver를 같이 넣으면 JDK 17이 없는 팀원 PC에서는 Gradle이 자동으로 내려받는다.
- **서비스 디스커버리(Eureka)** — 서비스가 기동하면서 자기 이름, IP, 포트를 등록하고, 호출하는 쪽은 주소 대신 이름(`lb://user-service`)으로 찾는다. 하트비트는 30초, 90초 동안 신호가 없으면 목록에서 빠진다. 그래서 서비스를 막 띄운 직후에는 Gateway가 아직 목록을 못 받아 503이 날 수 있다.
- **Config Server** — 서비스 설정을 한곳(config-repo)에 모아 두고 기동할 때 내려주는 서버다. 공통 설정은 `application.yml`, 서비스 전용 설정은 `{서비스명}.yml`에 둔다.
- **docker compose healthcheck** — `depends_on`에 `condition: service_healthy`를 걸어야 postgres가 실제로 접속을 받을 수 있을 때 서비스가 뜬다. `service_started`는 컨테이너가 시작만 됐다는 뜻이다.
- **HandlerMethodArgumentResolver** — 컨트롤러 파라미터를 채우는 확장 지점이다. Gateway가 넣어 준 헤더를 컨트롤러마다 파싱하지 않고 `@CurrentUser UserContext user` 한 줄로 받게 만들었다.
- **JPA Auditing(AuditorAware)** — Entity 저장 직전에 생성자, 수정자를 자동으로 채운다. 요청 헤더의 X-Username을 쓰고, 회원가입처럼 헤더가 없는 요청은 `SYSTEM`으로 기록한다.
- **API Gateway 인증 위임** — Gateway가 토큰을 검증하고 사용자 정보를 헤더로 넣어 주면, 서비스는 그 헤더를 믿고 역할만 확인하는 구조다. 서비스 포트를 외부에 열지 않는 것이 전제다.
- **Spring Security WebFlux** — Gateway는 Netty 기반이라 서블릿용 `SecurityFilterChain`이 아니라 `SecurityWebFilterChain`을 쓴다. 인증 정보도 ThreadLocal이 아니라 `ReactiveSecurityContextHolder`(Reactor Context)에 담긴다.

오늘 들었던 의문점 간단히 조사
---

**클라이언트가 X-User-Role: MASTER 헤더를 직접 넣으면 어떻게 될까?**

- 서비스는 Gateway가 넣은 X-User-* 헤더를 검증 없이 믿는다. 그런데 Gateway에 인증 필터가 없던 시점에 직접 요청해 보니, 위조 헤더 하나로 MASTER 전용 API가 200으로 열렸다.
- 해결은 순서에 있었다. Gateway가 요청을 받자마자 클라이언트가 보낸 X-User-* 헤더를 전부 지우고, 토큰 검증이 끝난 뒤 검증된 값으로 다시 넣는다. 로그인, 회원가입처럼 인증 없이 통과하는 요청도 헤더는 먼저 지운다.
- Gateway 필터라고 하면 `GlobalFilter`가 먼저 떠오르지만, GlobalFilter는 라우트가 매칭된 요청에만 실행된다. 라우트가 없는 `/internal/**`은 필터를 거치지 않는다. 그래서 라우트 매칭 전에 모든 요청에 실행되는 `WebFilter`에서 헤더 제거와 `/internal` 차단을 처리했다.
- 지금은 USER 토큰에 `X-User-Role: MASTER`를 붙여도 403이 나오고, `/me`를 호출하면 위조한 `X-Username: evil`이 아니라 실제 사용자 이름이 나온다.

**그래서 우리는?**

- 헤더를 믿는 구조를 쓰는 대신, Gateway가 "가장 먼저 지우고, 검증 후 다시 넣는다"를 지킨다.
- 서비스 포트는 compose에서 외부에 공개하지 않는다. 이게 깨지면 헤더 위조가 그대로 통한다.

**JWT는 발급 뒤에 바뀐 권한을 어떻게 알까?**

- 모른다. 토큰에는 발급 시점의 role이 들어 있고, 만료 전까지 그대로다. 관리자가 권한을 바꾸거나 사용자가 탈퇴해도 토큰은 여전히 유효하다.
- 그래서 Gateway가 요청마다 user-service 내부 API로 저장된 role과 탈퇴 여부를 다시 확인한다. 매번 부르면 user-service에 부하가 몰리니 결과를 60초 동안 캐시한다(Caffeine AsyncCache). 같은 사용자의 동시 요청은 조회 한 번으로 합쳐지고, 조회 실패는 캐시에 남기지 않는다.
- 대신 권한 변경은 최대 60초 늦게 반영된다. 이건 팀에서 정한 트레이드오프다.
- 정말 그렇게 동작하는지 실제 컨테이너에서 확인했다.
    - 0초 : USER로 로그인 후 호출 → 200 (캐시 저장)
    - 0초 : DB에서 role을 MASTER로 변경한 직후 → 200 (캐시된 USER 사용)
    - 30초 : 캐시 유지 중 → 200
    - 63초 : 캐시 만료 → user-service 재조회 → 토큰은 USER, 저장된 값은 MASTER → 401 TOKEN_ROLE_MISMATCH
    - 다시 로그인한 MASTER 토큰 → MASTER 전용 API 200
- 테스트에서는 60초를 기다리지 않고 Caffeine의 `Ticker`로 시간을 직접 흘렸다. 59초에는 캐시를 쓰고, 61초에는 다시 조회하는 것까지 확인했다.

**Spring Security는 Gateway에 두나, user-service에 두나?**

- 기준은 "누가 토큰을 검증하는가"다. 우리 SA는 Gateway가 인증을 맡는 구조라 Spring Security도 Gateway에 둔다.
- user-service는 토큰을 발급만 한다. 필요한 건 비밀번호 해시(BCrypt)뿐이라 `spring-security-crypto`만 넣었다. `spring-boot-starter-security`를 넣으면 기본 설정이 모든 API를 막아서 오히려 풀어 주는 설정만 늘어난다.
- 서비스마다 Spring Security를 넣고 각자 토큰을 검증하는 방식도 있다. 내부망도 믿지 않는 구조라 더 안전하지만, 서비스 다섯 개 모두에 설정과 키 배포가 필요하다.
- 사실 처음에는 반나절 안에 끝내려고 Gateway 인증을 Spring Security 없이 WebFilter로 직접 짰다. 그런데 SA를 다시 보니 Gateway에 Spring Security가 명시돼 있었다. 그래서 Spring Security WebFlux로 옮겼다.

**직접 짠 필터를 Spring Security로 옮길 때 주의할 점은?**

- 화이트리스트를 `permitAll()`로 열면 안 된다. permitAll이어도 Authorization 헤더가 붙어 있으면 Bearer 인증 필터가 먼저 토큰을 검증한다. 만료된 토큰이 남아 있는 상태로 로그인하면 401이 된다. 그래서 화이트리스트는 `securityMatcher`에서 아예 Security 적용 대상에서 뺐고, 만료 토큰을 붙인 로그인 요청이 통과하는지 테스트로 확인했다.
- 권한 재확인 실패를 `AuthenticationServiceException`으로 던지면 진입점(AuthenticationEntryPoint)을 거치지 않고 다시 던져져 500이 된다. 응답 코드를 담은 일반 `AuthenticationException` 하위 클래스를 따로 만들어서 401, 503을 나눴다.
- 재확인을 끼워 넣을 위치는 JWT를 Authentication으로 바꾸는 변환기(`jwtAuthenticationConverter`)였다. 서명과 만료 검증이 끝난 뒤에 호출되기 때문이다.
- 발급은 user-service에서 JJWT로, 검증은 Gateway에서 Nimbus로 한다. 라이브러리가 달라도 JWT가 표준이라 그대로 호환된다.

**Config Server에서 받은 값이 환경 변수를 이긴다?**

- Config Server가 내려준 값은 기본적으로 클라이언트의 환경 변수보다 우선한다(`override-system-properties` 기본값 true).
- 그러니 config-repo에 `localhost` 같은 고정값을 적어 두면, compose에서 `SPRING_DATASOURCE_URL`로 컨테이너용 주소를 넘겨도 무시된다.
- 그래서 환경마다 달라지는 값은 config-repo에 고정값으로 두지 않고 `${DB_HOST:localhost}` 같은 자리표시자로 둔다. 자리표시자는 클라이언트 쪽 환경 변수로 풀린다. compose는 이제 `DB_HOST`, `EUREKA_URL` 같은 짧은 값만 넘긴다.

**빈 서비스 하나가 정말 400MB나 쓸까?**

- `docker stats`로 재 보니 그랬다. 비즈니스 로직이 없는 서비스도 405~450MB, eureka는 495MB, 전체 컨테이너는 약 3.1GB였다.
- Spring 컨텍스트, Hibernate, Eureka 클라이언트, 내장 Tomcat이 기본으로 올라오기 때문이다.
- 코드와 빌드는 가볍고, 무거운 건 실행이다. 작업 중인 서비스와 의존하는 것만 띄우는 습관이 필요하다.
- MSA의 단점을 물으면 "서비스마다 런타임 비용이 든다"를 숫자로 말할 수 있게 됐다.
