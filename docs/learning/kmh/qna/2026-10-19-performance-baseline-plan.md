# 캐시 도입 전 성능 기준선 측정 계획

## 질문
성능 개선의 객관적 근거가 필요하다. Redis 캐시 후보 4개(`2026-10-19-redis-cache-candidates.md`)를 구간별로 먼저 측정하고, 하나씩 적용하며 비교하려 한다. 개발 전 성능 테스트를 어떻게 진행하면 좋은가.

## 짧은 답
순서는 다섯 단계다.
1. 항목마다 가설과 지표를 정한다.
2. 측정 환경을 고정한다.
3. 시나리오 두 개로 기준선을 잰다.
4. 같은 조건에서 3회 반복해 결과를 기록한다.
5. 캐시를 하나 넣을 때마다 같은 절차를 다시 돌린다.

핵심은 "바꾼 것 하나 말고는 아무것도 바뀌지 않았다"를 보장하는 것이다. 그래야 차이가 캐시 덕분이라고 말할 수 있다.

구간별 수치는 부하 도구가 아니라 서비스 메트릭에서 얻는다. k6는 사용자 입장의 전체 응답 시간을 준다. 서비스 간 호출 하나하나의 횟수와 지연은 Prometheus의 `feign.client.requests`와 `http.server.requests` 히스토그램에서 나눠 본다. 이 프로젝트에는 이미 둘 다 켜져 있다.

## 자세히

### 1. 항목별 가설과 지표
캐시마다 기대 효과가 다르다. 그래서 같은 지표로만 보면 안 된다.

| 항목 | 가설 | 주 지표 | 보조 지표 |
|---|---|---|---|
| A. Gateway I-01 | Redis로 바꾸면 권한 변경이 즉시 반영되고, 인스턴스가 늘어도 I-01 호출이 늘지 않는다 | 권한 변경 후 반영 시간, I-01 호출 수 | Gateway p95 (Caffeine보다 느려질 수 있다) |
| B. 허브·경로 | 캐시하면 I-03 호출과 지연이 사라진다 | 주문 생성 p95, I-03 호출 수 | hub-service DB 쿼리 수 |
| C. 업체·상품 | 주문 생성에서 company 호출 3회가 줄어 처리량이 오른다 | 주문 생성 p95, 최대 처리량 | company 호출 수, company CPU |
| D. 배송담당자 목록 | I-14 호출이 줄어든다 | I-14 호출 수와 지연 | 주문 생성 p95 |

A는 이미 Caffeine 60초 캐시가 있다. 따라서 기준선이 두 개다.
- 캐시 없음(TTL 0): 캐시 자체의 효과
- 현재(Caffeine 60초): Redis로 바꿨을 때의 차이

Redis가 Caffeine보다 응답 시간이 느리게 나올 가능성이 높다. 네트워크 왕복이 추가되기 때문이다. 이것도 객관적인 결과다. A의 근거는 응답 시간이 아니라 정합성(즉시 반영)과 확장성(인스턴스 수)에서 나온다. 가설을 미리 적어 두면 결과를 유리하게 해석하는 일을 막을 수 있다.

### 2. 측정 환경 고정
| 항목 | 고정 방법 | 이유 |
|---|---|---|
| 실행 환경 | 개발용(`script/run.sh`)과 분리된 전용 Compose 프로젝트. `script/ui-test.sh`처럼 별도 프로젝트 이름, 포트, `.env` 사용 | 개발 데이터와 섞이지 않고, 매번 같은 상태에서 시작한다 |
| 자원 | 컨테이너별 CPU·메모리 제한(`cpus`, `mem_limit`)을 정하고 바꾸지 않는다. 테스트 중 다른 프로그램을 끈다 | 노트북 환경은 다른 프로그램 때문에 결과가 흔들린다 |
| 추적 | `TRACING_SAMPLING_PROBABILITY`를 고정한다. 기본값 1.0은 모든 요청을 Zipkin에 보낸다. 측정 때는 0 또는 0.1로 두고, 원인 분석 때만 1.0으로 짧게 돌린다 | 추적 비용이 측정값에 섞인다 |
| 외부 연동 | Slack Webhook, DM 끄기 | 외부 API 지연이 섞이고, 실제 메시지가 나간다 |
| 로그 | 로그 레벨 고정. DEBUG 금지 | 로그 출력도 비용이다 |
| 데이터 | 매 측정 전 DB 초기화 후 같은 시드 | 주문 데이터가 쌓이면 조회가 점점 느려진다 |
| 워밍업 | 본 측정 전 1~2분 저부하 | JIT 컴파일, 커넥션 풀, Eureka 목록이 준비되기 전의 값을 빼야 한다 |
| 부하 도구 위치 | k6를 같은 Docker 네트워크의 컨테이너로 실행(`grafana/k6` 이미지)하거나 호스트에서 실행. 한 번 정하면 바꾸지 않는다 | 부하 도구도 같은 CPU를 쓴다. 위치가 바뀌면 비교할 수 없다 |

Windows 노트북의 Docker Desktop은 절대 수치를 믿기 어렵다. 같은 환경에서 상대 비교(전후 차이)에만 쓴다. 결과에도 "로컬 Docker 기준"이라고 적는다.

### 3. 시드 데이터
- 사용자: 수백~천 명 규모로 만들고 각각 토큰을 미리 발급한다. 몇 명으로만 요청하면 캐시 적중률이 100%에 가까워져 결과가 과장된다.
- 허브·경로: Flyway 시드를 그대로 쓴다.
- 업체·상품: 허브마다 업체와 상품 여러 개.
- 배송담당자: 허브마다 1명 이상. 없으면 배송 생성이 404로 실패한다.
- 방법: `script/ui-test-seed.py`처럼 공개 API로 만드는 스크립트를 쓰거나, k6의 `setup()` 단계에서 만든다. 대량 사용자는 회원가입 API를 반복 호출한다.

### 4. 시나리오
**S1. 인증 요청 (A 측정용)**
- `GET /api/v1/users/me`를 사용자 토큰을 돌려 가며 호출한다.
- 변형: Gateway 캐시 TTL 0초와 60초(`auth.user-cache-ttl`을 측정 환경의 설정에서만 바꾼다).
- 정합성 측정: 부하 중에 MASTER가 한 사용자의 role을 바꾸고, 그 사용자의 요청이 `TOKEN_ROLE_MISMATCH`로 바뀌기까지 걸린 시간을 잰다. 현재 구조에서는 최대 60초가 나와야 한다.
- 확장성 측정(선택): Gateway를 2대로 늘려 I-01 호출 수가 거의 두 배가 되는지 본다.

**S2. 주문 생성 (B, C, D 측정용)**
- `POST /api/v1/orders`를 요청마다 새 `Idempotency-Key`로 보낸다. 업체와 상품은 시드에서 무작위로 고른다.
- 한 요청 안에서 company(I-xx 3회), hub I-03, user I-14, user I-01이 모두 일어난다. 그래서 시나리오 하나로 B, C, D의 기준선을 함께 얻는다.
- 구간별 수치는 Prometheus에서 대상(`clientName`, `uri`)별로 나눠 본다.
- 주문 생성은 데이터를 만든다. 매 회차 DB를 초기화한다.

**S3. 읽기 (선택)**
- 허브 목록과 경로 조회(`GET /api/v1/hubs`, `/api/v1/hub-routes`). 프런트가 자주 부르는 읽기 경로라면 B의 보조 근거가 된다.

### 5. 부하 모델
- 고정 도착률(k6 `constant-arrival-rate`)을 쓴다. 가상 사용자 수 고정 방식은 서버가 느려지면 요청도 덜 보낸다. 그러면 느린 쪽이 오히려 부하를 덜 받게 되어 비교가 왜곡된다.
- 단계
  1. 스모크: 1 RPS로 1분. 시나리오가 오류 없이 도는지 확인한다.
  2. 부하: 목표 RPS 고정으로 5분. 전후 비교의 주 데이터다.
  3. 한계: RPS를 계단식으로 올리며 p95가 기준(예: 1초)을 넘거나 오류율이 1%를 넘는 지점을 찾는다. 이 지점이 "최대 처리량"이다.
- 목표 RPS는 스모크와 한계 테스트 결과를 보고 정한다. 한계의 50~70% 정도가 적당하다.
- Prometheus 수집 주기가 15초라 1분짜리 측정은 점이 4개뿐이다. 본 측정은 5분 이상 돌린다.

### 6. 수집할 지표
| 출처 | 지표 | 쓰는 곳 |
|---|---|---|
| k6 요약 | `http_req_duration` p50, p95, p99, 처리량, 실패율 | 사용자 체감 |
| Prometheus `http_server_requests_seconds` | 서비스·uri별 횟수와 p95 | 각 서비스가 받은 요청 |
| Prometheus `feign_client_requests_seconds` | 호출 대상별 횟수와 p95 | 구간별 기준선(B, C, D) |
| Prometheus `hikaricp_connections_active`, `_pending` | DB 커넥션 사용 | 병목이 DB인지 판단 |
| Prometheus `process_cpu_usage`, `jvm_gc_pause` | CPU, GC | 병목이 CPU인지 판단 |
| `docker stats` | 컨테이너 CPU, 메모리 | 자원 제한에 걸렸는지 판단 |
| Zipkin (추적 1.0으로 짧게) | 한 요청의 구간별 시간 | 원인 분석. 수치 비교에는 쓰지 않는다 |

p95 같은 분위수는 히스토그램에서 계산한다. 예를 들어 company 호출의 p95는 이렇게 구한다.
```
histogram_quantile(0.95, sum by (le, clientName) (rate(feign_client_requests_seconds_bucket{application="order-service"}[1m])))
```

### 7. 반복과 기록
- 같은 조건으로 3회 돌리고 중앙값을 쓴다. 회차 사이 편차도 함께 적는다. 개선 폭이 편차보다 작으면 "차이 없음"으로 판단한다.
- 기록할 것: 날짜, 커밋 해시, 환경(자원 제한, 추적 비율, 시드 규모), k6 스크립트 버전, 결과 표, Grafana 화면 캡처, k6 요약 JSON(`--summary-export`).
- 결과 표 예

| 회차 | 조건 | RPS | p50 | p95 | p99 | 오류율 | company 호출/주문 | I-03 p95 |
|---|---|---|---|---|---|---|---|---|
| 기준선-1 | 캐시 없음 | | | | | | 3.0 | |

### 8. 캐시 도입 후 비교 절차
1. 캐시 하나만 넣는다. 예: C(업체·상품). 커밋을 나눈다.
2. 같은 환경, 같은 시드, 같은 k6 스크립트, 같은 RPS로 다시 3회 돌린다.
3. 기준선 표 옆에 결과를 붙인다. 주 지표와 보조 지표를 모두 적고, 나빠진 값도 숨기지 않는다(예: Redis 왕복으로 늘어난 지연).
4. 적중률과 정합성 시나리오(상품 삭제 직후 주문 등)도 확인한다.
5. 다음 항목으로 넘어간다. 앞의 캐시는 켠 채로 둔다. 각 비교는 직전 단계를 기준으로 한다.

### 진행 전 준비물
- k6 설치: `winget install k6` 또는 Docker `grafana/k6` 이미지. 이 PC에는 아직 설치되어 있지 않았다(2026-10-19 확인).
- 측정 전용 Compose 설정, 시드 스크립트, k6 스크립트 2개(S1, S2).
- 스크립트와 결과를 둘 위치를 팀과 정한다. 측정 방식(도구, 환경, 판단 기준)은 다른 팀원도 같은 방식으로 재현해야 하므로 결정 기록으로 남기는 것이 좋다.

### 9. 범위 확정과 조건표 (2026-10-19 갱신)
팀 회의에서 D(배송담당자 목록 캐시)는 기각됐다. A, B, C만 측정한다.

| 조건 | 시나리오 | 바꾸는 것 | 비교 대상 |
|---|---|---|---|
| A0 | S1 | Gateway TTL 0s(캐시 없음) | 캐시 자체의 효과 |
| A1 | S1 | Gateway TTL 60s(현재 Caffeine) | 현재 기준선 |
| A2 | S1 | Redis 권한 캐시 + 변경 시 삭제 | A1 |
| BC0 | S2, S3 | 캐시 없음(TTL 60s 고정) | 공통 기준선 |
| B1-local | S2, S3 | 허브·경로 로컬 캐시(Caffeine) | BC0 |
| B1-redis | S2, S3 | 허브·경로 Redis 캐시 | BC0, B1-local |
| C1 | S2 | company-service 내부 조회 API Redis 캐시 | 채택한 B1 |

- B는 로컬 캐시와 Redis를 모두 측정해 비교한다(2026-10-19 kmh 결정).
- C의 캐시 위치는 코드 수정 범위가 가장 작은 company-service 내부 조회 API로 정했다(2026-10-19 kmh 결정). 조회 캐시와 수정·삭제 시 키 삭제를 한 서비스 안에서 끝낼 수 있다. order 쪽에 두면 company의 수정·삭제를 order 캐시에 알릴 방법이 따로 필요하다. 대신 이 위치는 order → company HTTP 호출 수를 줄이지 않는다. 그래서 C의 주 지표는 company 내부 API 지연과 company 자원이다.
- 결과는 `.local/perf/results/`와 함께 `docs/reviews/performance/`에도 남긴다(2026-10-19 kmh 결정). 절차는 `docs/guides/performance-test.md`에 있다.

- S2는 Gateway도 거치므로 B, C를 재는 동안 Gateway TTL은 60s로 고정한다.
- B와 C는 같은 S2에 영향을 준다. 하나를 넣을 때마다 직전 단계를 새 기준선으로 삼는다.
- 회차 이름은 `조건-시나리오-회차`(예: `A0-s1-r1`)로 맞춘다.

## 면접 포인트
- "성능 개선을 어떻게 증명했나": 기준선을 먼저 고정 환경에서 측정했다. 한 번에 하나만 바꾸고 같은 조건으로 3회 반복해 중앙값과 편차로 비교했다. 사용자 체감(p95, 처리량)과 구간별 호출 수, 지연을 함께 봤다.
- "평균이 아니라 p95, p99를 보는 이유": 평균은 소수의 느린 요청을 가린다. 사용자 불만은 꼬리 지연에서 나온다.
- "고정 도착률로 부하를 준 이유": 사용자 수 고정 방식은 서버가 느려지면 요청도 줄어 부하가 자동으로 낮아진다. 그래서 느린 시스템이 좋아 보이는 왜곡(coordinated omission)이 생긴다.
- 꼬리 질문: 캐시를 넣었더니 오히려 느려졌다면. 원격 캐시의 왕복 비용이 원래 호출보다 큰 경우다. 그 구간은 로컬 캐시가 맞거나 캐시가 필요 없다는 근거가 된다.
