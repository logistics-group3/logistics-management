# Mock이란 무엇이고 테스트에서 어떻게 쓰나

## 질문
mock이 무엇인지 알려 달라.

## 짧은 답
mock은 테스트할 때 진짜 의존 객체 대신 넣는 가짜 객체다. 가짜이므로 무엇을 반환할지 테스트가 정할 수 있다. 어떤 메서드가 어떤 인자로 몇 번 불렸는지도 기록한다.

예를 들어 `UserRoleService`는 hub-service를 호출하는 `HubReader`에 의존한다. 진짜 객체를 쓰면 테스트할 때마다 hub-service가 떠 있어야 하고, 네트워크 상태에 따라 결과가 달라진다. mock `HubReader`를 넣으면 "이 허브를 조회하면 이 값을 돌려준다"고 정해 두고 `UserRoleService`의 로직만 검증할 수 있다.

Java에서는 Mockito 라이브러리를 주로 쓴다. Spring Boot 테스트 스타터에 기본으로 들어 있다.

## 자세히

### 왜 필요한가
테스트하려는 대상(SUT, System Under Test)은 보통 다른 객체에 의존한다. 진짜 의존 객체를 쓰면 다음 문제가 생긴다.
- 느리다. DB, 네트워크, 다른 서비스를 실제로 부른다.
- 결과가 흔들린다. 외부 상태(데이터, 장애)에 따라 같은 테스트가 통과하기도 하고 실패하기도 한다.
- 만들기 어려운 상황이 있다. "hub-service가 503을 준다", "타임아웃이 난다" 같은 경우를 진짜로 재현하기 힘들다.
- 실패 원인이 흐려진다. 테스트가 깨졌을 때 내 코드 문제인지 의존 객체 문제인지 구분하기 어렵다.

mock으로 의존 객체를 바꾸면 내 코드의 분기만 빠르고 결정적으로 검증할 수 있다.

### 테스트 대역(Test Double)의 종류
mock은 테스트 대역의 한 종류다. 실무에서는 다 "mock"이라고 부르기도 하지만 구분해 두면 면접에서 쓸모가 있다(Gerard Meszaros, Martin Fowler 분류).

| 종류 | 하는 일 | 예 |
|---|---|---|
| Dummy | 자리만 채운다. 실제로 쓰이지 않는다 | 생성자에 넘기는 null 대신의 객체 |
| Stub | 정해 둔 값을 돌려준다 | `given(hubReader.getHub(id)).willReturn(hub)` |
| Spy | 진짜 객체를 감싸 호출을 기록한다 | `Mockito.spy(realObject)` |
| Mock | 호출을 기록하고, 기대한 대로 불렸는지 검증한다 | `verify(userService).applyRoleChange(...)` |
| Fake | 단순하지만 실제로 동작하는 구현 | 메모리 Map으로 만든 Repository |

Mockito의 `@Mock`으로 만든 객체는 stub(반환값 지정)과 mock(호출 검증) 역할을 모두 한다.

### Mockito 기본 사용법
```java
@ExtendWith(MockitoExtension.class)        // JUnit 5에서 Mockito 어노테이션을 처리한다
class UserRoleServiceTest {

    @Mock HubReader hubReader;              // 가짜 객체 생성
    @Mock UserService userService;
    @InjectMocks UserRoleService userRoleService;   // 위 mock들을 생성자로 주입한 진짜 객체

    @Test
    void looksUpHubBeforeChange() {
        // given: mock이 돌려줄 값을 정한다(stubbing)
        given(hubReader.getHub(hubId)).willReturn(hub);

        // when: 테스트 대상을 실행한다
        userRoleService.changeRole(master, target, command);

        // then: mock이 기대한 인자로 불렸는지 확인한다(verification)
        verify(userService).applyRoleChange(target, command, hub);
    }
}
```
- mock은 따로 정하지 않은 메서드를 부르면 기본값(null, 0, false, 빈 컬렉션)을 돌려준다.
- `given(...).willReturn(...)`은 BDD 스타일이다. 같은 의미로 `when(...).thenReturn(...)`도 쓴다. 이 프로젝트는 `given`을 쓴다.
- 예외 상황은 `willThrow(new BusinessException(...))`로 만든다.
- 인자 매처: `any()`, `eq(x)`, `argThat(c -> ...)`. 한 호출 안에서 매처와 실제 값을 섞으면 안 된다. 섞어야 하면 실제 값을 `eq()`로 감싼다.
- 호출 검증: `verify(mock).method(...)`(한 번 불림), `verify(mock, times(2))`, `never()`, `verifyNoInteractions(mock)`(아예 안 불림).

### 이 프로젝트에서는
**1) 서비스 단위 테스트: `@Mock` + `@InjectMocks`**
`UserRoleServiceTest`는 Spring 없이 순수 JUnit과 Mockito로 돈다. 그래서 빠르다.
- "hubId가 없으면 hub-service를 부르지 않는다": `verifyNoInteractions(hubReader)`
- "MASTER가 자기 권한을 바꾸려 하면 허브 조회와 DB 변경 전에 막는다": 예외를 확인하고 `verifyNoInteractions(hubReader, userService)`

반환값만이 아니라 "무엇을 부르지 않았나"까지 검증할 수 있다는 점이 mock의 강점이다.

**2) 웹 슬라이스 테스트: `@MockitoBean`**
`UserControllerWebMvcTest`는 `@WebMvcTest`로 컨트롤러, 필터, 인터셉터, 예외 처리기만 띄운다. 서비스 계층은 띄우지 않는다. 컨트롤러가 의존하는 서비스는 `@MockitoBean`으로 가짜 빈을 넣는다.
```java
@MockitoBean UserQueryService userQueryService;

@Test
void searchRequiresMaster() throws Exception {
    as(Role.USER, get("/api/v1/users"))
            .andExpect(status().isForbidden());
    verifyNoInteractions(userQueryService);   // @RequireRole이 컨트롤러 전에 막았다
}
```
- `@Mock`은 Spring과 무관한 객체다. `@MockitoBean`은 Spring 컨텍스트의 빈을 mock으로 바꾼다.
- `@MockitoBean`은 Spring Framework 6.2에서 들어왔다. 이전의 `@MockBean`(Spring Boot)은 Boot 3.4부터 deprecated다.
- `MockMvc`도 이름에 Mock이 붙는다. 실제 서버를 띄우지 않고 가짜 HTTP 요청을 DispatcherServlet에 넣는 도구다.

**3) 설계가 mock을 쉽게 만든다**
`UserRoleService`는 Feign `HubClient`가 아니라 `HubReader` 인터페이스에 의존한다. 그래서 테스트에서 `HubReader`만 mock으로 바꾸면 된다. 의존성을 생성자로 받고(DI) 인터페이스로 추상화해 두면 테스트하기 쉬워진다. 반대로 `new HubClient()`를 메서드 안에서 직접 만들면 바꿔 끼울 방법이 없다.

**4) mock을 쓰지 않는 테스트도 있다**
`UserAuthIntegrationTest` 같은 통합 테스트는 Testcontainers로 진짜 PostgreSQL을 띄운다. UNIQUE 제약, CHECK 제약, `@SQLRestriction`, Flyway 마이그레이션은 mock으로 검증할 수 없기 때문이다.

### mock의 한계와 주의점
- mock이 진짜와 다르게 동작해도 테스트는 통과한다. 예를 들어 Repository를 mock으로 바꾸면 "중복 username이면 DB가 예외를 던진다"는 사실은 검증되지 않는다. DB가 관여하는 규칙은 통합 테스트로 확인한다.
- 구현 세부를 과하게 검증하면 테스트가 깨지기 쉽다. 내부 호출 순서를 하나하나 `verify`하면, 동작은 같은데 리팩터링만 해도 테스트가 실패한다. 결과(반환값, 상태)를 먼저 검증하고, 호출 검증은 "부르면 안 되는 것"이나 "외부로 나가는 명령"처럼 의미 있는 곳에만 쓴다.
- 내가 소유하지 않은 타입(외부 라이브러리 클래스)을 직접 mock하지 말라는 원칙이 있다. 이 프로젝트처럼 `HubReader` 같은 내 인터페이스로 감싸고 그것을 mock한다.
- 테스트에 mock이 너무 많이 필요하면 대상 클래스가 너무 많은 일을 하고 있다는 신호일 수 있다.

### 직접 해보기
1. `user-service/src/test/java/com/sparta/logistics/user/application/UserRoleServiceTest.java`를 연다.
2. IntelliJ에서 클래스 이름 옆 실행 버튼을 누르거나, CLI에서 `./gradlew :user-service:test --tests "*UserRoleServiceTest"`를 실행한다. 확인: 모든 테스트가 통과하고, Docker나 다른 서비스 없이 몇 초 안에 끝난다.
3. `looksUpHubBeforeChange`의 `given(...)` 줄을 주석 처리하고 다시 실행한다. 확인: `hubReader.getHub`가 null을 돌려줘서 `verify`가 기대한 인자(`hub`)와 실제 인자(`null`)가 다르다는 메시지로 실패한다.
4. 주석을 되돌린다.

### 더 깊이
- 고전파(Classicist)와 런던파(Mockist): 고전파는 진짜 객체를 최대한 쓰고 외부 경계(DB, 네트워크)만 대역으로 바꾼다. 런던파는 대상 클래스의 모든 협력 객체를 mock으로 바꾼다. 이 프로젝트의 서비스 단위 테스트는 협력 객체를 mock하고, DB 규칙은 통합 테스트로 확인하는 혼합형이다.
- final 클래스와 static 메서드: Mockito 5부터 기본 mock 생성기(inline)가 final 클래스도 mock할 수 있다. static은 `mockStatic`으로 가능하지만, 필요해지면 설계를 먼저 의심한다.

## 면접 포인트
- "mock과 stub의 차이": stub은 정해 둔 값을 돌려주는 것(상태 검증용)이고, mock은 호출이 기대대로 일어났는지 검증하는 것(행위 검증용)이다. Mockito 객체는 둘 다 할 수 있다.
- "mock을 쓰면 무엇을 놓치나": mock은 진짜 의존 객체의 동작을 보장하지 않는다. DB 제약이나 직렬화처럼 경계에서 생기는 문제는 통합 테스트로 보완한다.
- "`@Mock`과 `@MockitoBean` 차이": `@Mock`은 Spring 없이 쓰는 순수 Mockito 객체다. `@MockitoBean`은 Spring 테스트 컨텍스트의 빈을 mock으로 교체한다. 슬라이스 테스트에서 띄우지 않는 계층을 대신한다.
- 꼬리 질문: 테스트하기 쉬운 코드란. 의존성을 생성자로 주입받고 인터페이스로 추상화해, 테스트에서 대역으로 바꿔 끼울 수 있는 코드다.
