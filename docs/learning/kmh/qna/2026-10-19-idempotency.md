# 멱등성이란 무엇이고 이 프로젝트는 어떻게 보장하나

## 질문
멱등성(idempotency)이 무엇인지 설명해 달라.

## 짧은 답
같은 요청을 한 번 보내든 여러 번 보내든 서버의 최종 상태가 같으면 그 연산은 멱등하다. "배송을 CANCELED로 만든다"는 몇 번 실행해도 결과가 같으므로 멱등하다. "재고를 1 줄인다"는 실행할 때마다 결과가 달라지므로 멱등하지 않다.

멱등성이 중요한 이유는 분산 환경에서 타임아웃이 나면 상대가 요청을 처리했는지 알 수 없기 때문이다. 멱등한 API는 다시 보내도 안전하고, 멱등하지 않은 API는 다시 보내면 주문이 두 번 생기거나 재고가 두 번 차감될 수 있다.

## 자세히

### 정의에서 자주 헷갈리는 점
- 기준은 서버 상태이고 응답이 아니다. `DELETE /orders/1`을 두 번 보내면 첫 번째는 204, 두 번째는 404일 수 있다. 그래도 "주문 1이 없다"는 최종 상태가 같으므로 멱등하다.
- 안전(safe)과 다르다. 안전한 메서드는 상태를 아예 바꾸지 않는다(GET). 멱등은 바꿔도 되지만 여러 번 해도 결과가 같아야 한다(PUT, DELETE).
- 수학의 f(f(x)) = f(x)와 같은 개념이다. 절댓값을 두 번 취해도 결과가 같다.

### HTTP 메서드별 성질 (RFC 9110)
| 메서드 | 안전 | 멱등 | 이유 |
|---|---|---|---|
| GET, HEAD | O | O | 조회만 한다 |
| PUT | X | O | "이 값으로 덮어써라". 여러 번 덮어도 같다 |
| DELETE | X | O | "없애라". 이미 없으면 그대로 없다 |
| POST | X | X | "새로 만들어라". 보낼 때마다 새 자원이 생길 수 있다 |
| PATCH | X | X(보장 안 함) | `{"stock": 10}`이면 멱등이지만 `{"stock": "-1"}` 같은 증감이면 아니다 |

메서드의 성질은 약속일 뿐이다. 구현이 지키지 않으면 PUT도 멱등하지 않다. 반대로 POST라도 설계로 멱등하게 만들 수 있다.

### 왜 MSA에서 특히 중요한가
order-service가 delivery-service에 배송 생성을 요청했는데 20초 동안 응답이 없다고 하자. 가능한 경우는 세 가지다.
1. 요청이 도착하지 않았다.
2. 처리 중에 실패했다.
3. 처리는 끝났고 응답만 사라졌다.

호출한 쪽은 셋을 구분할 수 없다. 다시 보내면 3번일 때 배송이 두 개 생기고, 다시 보내지 않으면 1번일 때 배송이 없다. API를 멱등하게 만들면 이 문제가 사라진다. 그냥 다시 보내면 되고, 이미 처리됐으면 서버가 기존 결과를 돌려준다.

### 멱등하게 만드는 방법
| 방법 | 설명 | 이 프로젝트의 예 |
|---|---|---|
| 자연키 + UNIQUE | 업무상 한 번만 있어야 하는 값에 유니크 제약을 걸고, 있으면 기존 것을 돌려준다 | 배송의 `order_id UNIQUE`. 주문 1건에 배송 1건 |
| 상태 확인 후 no-op | 목표 상태에 이미 있으면 아무것도 하지 않는다 | `Delivery.cancel()`은 이미 `CANCELED`면 바로 반환한다 |
| 멱등키(Idempotency-Key) | 클라이언트가 요청마다 고유 키를 만들어 보내고, 서버는 키별 처리 결과를 저장한다 | 주문 생성 O-01의 `Idempotency-Key` 헤더 |
| 증감 대신 절댓값 | "1 빼라" 대신 "10으로 해라" | (일반 기법) |
| 이력 테이블 UNIQUE | 같은 작업 이력을 두 번 쓰지 못하게 막는다 | 재고 변경 이력 `UNIQUE (hub_stock_id, order_id, change_type)` |

### 이 프로젝트에서는
**1) 배송 생성 (I-09): orderId로 멱등**
```java
// DeliveryCreationService.create
Optional<Delivery> existing = deliveryRepository.findByOrderId(command.orderId());
if (existing.isPresent()) {
    return CreateDeliveryResult.existing(existing.get());   // 이미 있으면 새로 만들지 않는다
}
```
order-service는 주문을 저장하기 전에 orderId를 먼저 발급한다(SA 핵심 설계 6). 그래서 재시도해도 같은 orderId가 가고, delivery-service는 같은 배송을 돌려준다. 조회와 저장 사이에 동시 요청이 끼어드는 경우는 `order_id` UNIQUE 제약이 막는다. 애플리케이션 코드의 확인만으로는 동시성을 막을 수 없어서 DB 제약이 최종 방어선이다.

**2) 취소·원복·삭제: 상태 확인 후 no-op**
- `Delivery.cancel()`: 이미 `CANCELED`면 그대로 둔다.
- `Delivery.revertCancel()`: 취소 상태가 아니면 아무것도 하지 않는다.
- 배송 삭제(I-13): 대상이 없거나 이미 삭제됐어도 204로 성공한다.

**3) 재시도는 멱등한 API에만**
`IdempotentRetryConfig`(Feign `Retryer`, 최대 3회)는 필요한 FeignClient에만 붙인다. 일부러 `@Configuration`을 붙이지 않았다. 빈으로 등록되면 모든 FeignClient에 적용되어 멱등하지 않은 POST까지 다시 보내기 때문이다. 재시도 대상은 GET과 orderId 기반 배송 API(생성, 취소 원복, 삭제)다(SA 3.5, `docs/agents/rules/feign.md`).

**4) 보상도 멱등에 기댄다**
배송 생성 호출이 타임아웃이면 생성됐는지 모르므로 I-13 배송 삭제를 보낸다. 생성되지 않았어도 삭제가 성공으로 끝나기 때문에, 결과를 몰라도 안전하게 보상할 수 있다.

**5) 사용자 요청: Idempotency-Key**
클라이언트가 주문 생성 버튼을 두 번 누르거나 응답을 못 받고 다시 보내는 경우다. 서버 간 호출과 달리 외부 POST는 요청마다 새 orderId가 생기므로, 클라이언트가 같은 시도임을 알려 줘야 한다(order ADR 0008).
- 클라이언트는 새 주문마다 UUID 키를 만들고, 재시도에는 같은 키와 같은 본문을 보낸다.
- 서버는 `(orderer_id, idempotency_key)`를 UNIQUE로 저장하고, 요청 본문의 SHA-256 지문과 최초 응답을 함께 둔다.
- 같은 키와 같은 본문으로 완료된 요청이 다시 오면 최초 응답을 그대로 201로 돌려준다. 같은 키에 다른 본문이 오면 409 `ORDER_IDEMPOTENCY_KEY_CONFLICT`, 처리 중이면 409 `ORDER_CREATION_IN_PROGRESS`다.
- 지문을 두는 이유: 키만 보면 실수로 같은 키를 다른 주문에 썼을 때 엉뚱한 응답을 돌려주게 된다.

### 직접 해보기
1. 전체를 띄운다: `script/run.sh`
2. Swagger UI(`http://localhost:8080/swagger-ui.html`)에서 로그인 후 `order-service`의 주문 생성을 연다.
3. `Idempotency-Key`에 임의의 UUID를 넣고 실행한다. 확인: 201과 orderId가 나온다.
4. 같은 키, 같은 본문으로 다시 실행한다. 확인: 같은 orderId로 201이 나오고 주문 목록에 주문이 하나만 있다.
5. 같은 키로 수량만 바꿔 실행한다. 확인: 409 `ORDER_IDEMPOTENCY_KEY_CONFLICT`가 나온다.

### 더 깊이
- 멱등성은 "정확히 한 번 실행(exactly-once)"을 직접 보장하지 않는다. 네트워크는 "최소 한 번 전달(at-least-once)"까지만 보장할 수 있고, 여기에 멱등한 수신 처리를 더해야 결과적으로 한 번 처리한 것과 같아진다. Kafka 컨슈머를 붙일 때도 같은 원리다.
- 멱등키 저장 기간(TTL)은 트레이드오프다. 짧으면 오래된 재시도가 새 요청으로 처리되고, 길면 저장 공간이 는다. 이 프로젝트는 자동 만료하지 않는다.
- Stripe 같은 결제 API가 `Idempotency-Key` 헤더 방식의 대표 예다.

## 면접 포인트
- "멱등성이란": 같은 요청을 여러 번 보내도 서버 상태가 한 번 보낸 것과 같은 성질. 기준은 응답이 아니라 상태다. DELETE가 두 번째에 404를 줘도 멱등하다.
- "타임아웃이 났는데 실제로는 처리됐다면": 그래서 멱등하게 설계한다. orderId를 먼저 발급하고 배송 API를 orderId 기준으로 멱등하게 만들어, 재시도와 보상을 결과를 몰라도 안전하게 할 수 있게 했다.
- "중복 결제·중복 주문을 어떻게 막나": 클라이언트 멱등키 + DB UNIQUE 제약 + 요청 지문 + 최초 응답 저장. 애플리케이션의 조회 후 저장만으로는 동시 요청을 막지 못한다.
- 꼬리 질문: 모든 API에 재시도를 걸면 안 되는 이유. 멱등하지 않은 POST를 다시 보내면 중복 처리가 생긴다.
