# 이 프로젝트에서 Redis 캐시를 적용할 만한 구간

## 질문
Redis 캐시를 적용해 볼 만한 구간이 있는가. 추후 성능 테스트를 할 예정이다.

## 짧은 답
후보는 네 곳이다. 효과와 위험을 기준으로 순서를 매겼다.

| 순위 | 구간 | 데이터 변경 빈도 | 추천 방식 |
|---|---|---|---|
| 1 | Gateway 권한 재확인(I-01) | 가끔(role 변경, 탈퇴) | Redis + 변경 시 즉시 삭제. Redis를 쓸 이유가 가장 분명하다 |
| 2 | 허브·허브 경로 조회(I-02, I-03, H-01~04) | 사실상 없음(시드 데이터, 쓰기 API 없음) | 효과는 크지만 Redis보다 로컬 캐시(Caffeine)가 맞다 |
| 3 | 주문 생성 시 업체·상품 조회(company I-xx) | 가끔(PATCH, DELETE) | Redis + 수정·삭제 시 삭제 + 짧은 TTL |
| 4 | 허브별 배송담당자 목록(I-14) | 가끔(U-07) | Redis + U-07 시 삭제. 효과는 작다 |

캐시하면 안 되는 곳도 있다. 주문·배송 상태, 담당자 배정 건수, 멱등키 처리 상태는 항상 최신 값이 필요하다. 이 값들은 정합성이 성능보다 중요하다.

"Redis냐 로컬 캐시냐"의 기준은 무효화다. 데이터가 바뀔 때 여러 인스턴스의 캐시를 한 번에 지워야 하면 Redis가 맞다. 바뀌지 않는 데이터라면 네트워크를 한 번 더 타지 않는 로컬 캐시가 더 빠르다.

## 자세히

### 요청 하나에 원격 호출이 몇 번 일어나나
주문 생성(O-01) 한 건의 원격 호출을 세면 다음과 같다.
```
Gateway ── I-01 권한 재확인 (현재 Caffeine 60초 캐시)
  └ order ── company: 공급업체, 수령업체, 상품 조회 (3회)
       └ delivery 생성 ── hub I-03 경로 조회 (1회)
                       ── user I-14 허브별 배송담당자 (허브 수만큼)
                       ── user I-01 수령 담당자 Slack ID (1회)
```
캐시 없이 주문 한 건에 동기 HTTP 호출이 7회 안팎 일어난다. 이 중 업체, 상품, 경로, 담당자 목록은 주문마다 거의 같은 값이다. 캐시 후보는 이런 "자주 읽고 드물게 바뀌는" 값이다.

### 1순위: Gateway 권한 재확인 (I-01)
**현재:** `CachedUserLookup`이 Caffeine(로컬 메모리)으로 60초 캐시한다.

**한계 두 가지**
- 권한 변경이 최대 60초 늦게 반영된다. MASTER를 USER로 강등해도 60초 동안은 MASTER로 통과한다.
- Gateway 인스턴스를 늘리면 인스턴스마다 캐시가 따로 있다. 같은 사용자도 인스턴스 수만큼 I-01을 부른다.

**Redis로 바꾸면**
- user-service가 U-07(권한 변경)과 U-08(삭제)을 처리할 때 Redis의 `user:{userId}` 키를 지운다. 그러면 다음 요청부터 바로 반영된다. TTL은 안전망으로 남긴다.
- 모든 Gateway 인스턴스가 같은 캐시를 본다.

**주의점**
- 모든 요청이 Redis를 한 번 거친다. 로컬 캐시보다 느리다(같은 네트워크면 보통 1ms 미만이지만 측정해야 안다).
- Redis가 죽었을 때 정책이 필요하다. I-01을 직접 부르는 방향으로 넘어가게(fallback) 해야 Redis 장애가 전체 장애가 되지 않는다.
- 두 단계 캐시(로컬 수 초 + Redis)로 나누는 방법도 있다. 다만 로컬 단계를 두면 즉시 반영이 다시 몇 초 늦어진다.
- Gateway는 WebFlux라 리액티브 Redis 클라이언트(`ReactiveRedisTemplate`, Lettuce)를 써야 한다. 블로킹 클라이언트를 쓰면 이벤트 루프가 멈춘다.
- SA의 "60초 캐시"는 팀 결정이다(SA 8.2). 바꾸려면 팀 합의와 ADR이 필요하다.

### 2순위: 허브·허브 경로 (hub-service)
- 허브와 경로는 Flyway 시드 데이터(`V2__seed_hubs.sql`, `V3__seed_hub_routes.sql`)다. hub-service에는 조회 API만 있고 쓰기 API가 없다.
- 호출하는 곳: user(U-07 허브 확인), company(업체 등록), delivery(배송 생성 시 I-03 경로), 프런트(허브 목록).
- 바뀌지 않는 데이터라 무효화가 필요 없다. 그래서 Redis의 장점(공유 무효화)을 쓸 일이 없다. 호출하는 쪽에 Caffeine을 두거나 hub-service에 `@Cacheable`을 두는 편이 단순하고 빠르다.
- 나중에 허브 수정 API가 생기면 그때 Redis와 삭제 로직을 검토한다.

### 3순위: 업체·상품 조회 (주문 생성)
- 주문 생성 한 건마다 company-service를 3번 부른다. 성능 테스트에서 주문 생성 처리량을 올리려면 가장 효과가 큰 구간이다.
- 업체와 상품은 PATCH와 DELETE로 바뀐다. company-service의 수정·삭제 로직에서 Redis 키를 지워야 한다.
- 캐시를 어디에 둘지 정해야 한다.
  - company-service 안(`@Cacheable`): DB 조회만 줄고 HTTP 호출은 그대로다. 무효화가 같은 서비스 안이라 단순하다.
  - order-service 쪽: HTTP 호출까지 줄지만, 무효화하려면 company가 order 쪽 캐시를 알아야 한다. 같은 Redis 키 규칙을 공유하는 계약이 생긴다.
- 위험: 삭제된 상품이나 바뀐 가격으로 주문이 만들어질 수 있다. 삭제 즉시 무효화와 짧은 TTL(예: 30~60초)로 위험 구간을 줄이고, 그 위험을 받아들일지 팀이 정한다.

### 4순위: 허브별 배송담당자 목록 (I-14)
- 배송 생성 때 허브마다 부른다. 목록은 U-07(배송담당자 지정·해제) 때만 바뀐다.
- 목록만 캐시하고, 배정에 쓰는 담당자별 건수(`counts`)는 캐시하지 않는다. 건수가 오래된 값이면 배정이 한 사람에게 몰린다.
- 호출량이 크지 않아 효과는 작다. 1~3순위를 측정한 뒤 판단한다.

### 캐시하면 안 되는 것
| 데이터 | 이유 |
|---|---|
| 주문·배송 상태 | 취소 가능 여부 판단에 쓴다. 오래된 값이면 잘못된 상태 전이가 일어난다 |
| 배송담당자 배정 건수 | 공정 배정의 근거다 |
| 주문 생성 멱등키 상태 | DB UNIQUE 제약과 트랜잭션이 정합성을 보장한다. 캐시로 옮기면 동시성 보장이 깨진다 |

### 캐시 말고 Redis를 쓸 만한 곳 (참고)
- Gateway 요청 수 제한: Spring Cloud Gateway의 `RequestRateLimiter` 필터가 Redis를 저장소로 쓴다. 성능 테스트 중 과부하 보호와 함께 검증할 수 있다.
- 분산 락: 여러 인스턴스가 같은 자원을 동시에 바꾸는 경우. 지금은 DB 제약으로 충분해서 필요하지 않다.

### 성능 테스트와 묶어서 진행하는 방법
1. 기준선을 먼저 잰다. 캐시를 넣기 전 같은 시나리오로 p50, p95, p99 응답 시간과 처리량(RPS), 오류율을 기록한다. 비교 대상이 없으면 개선을 증명할 수 없다.
2. 시나리오는 읽기 위주(`GET /users/me`, 허브 목록, 주문 조회)와 쓰기(주문 생성)로 나눈다. 도구는 k6, nGrinder, JMeter 중 하나를 고른다.
3. 원격 호출 수를 함께 본다. Prometheus와 Grafana가 이미 붙어 있다. Feign 메트릭(`FeignMeterFilter`)과 Gateway 메트릭으로 캐시 전후의 하위 서비스 호출 수를 비교한다. 캐시 적중률도 지표로 노출한다.
4. 테스트 사용자 수를 현실적으로 잡는다. 가상 사용자 10명이 같은 토큰으로 계속 요청하면 적중률이 거의 100%라서 결과가 과장된다. 사용자와 상품 ID를 넉넉히 분산한다.
5. 하나씩 바꾼다. 1순위만 적용하고 측정, 그다음 3순위를 적용하고 측정한다. 여러 개를 한 번에 바꾸면 어느 변경이 효과를 냈는지 알 수 없다.
6. 정합성 시나리오도 넣는다. 권한 변경 직후의 요청, 상품 삭제 직후의 주문처럼 캐시가 틀린 값을 줄 수 있는 경우가 의도대로 동작하는지 확인한다.

### 진행 전에 할 일
- SA는 Redis를 고도화 단계의 선택 항목으로 둔다(SA 1장, 기술 스택 표). 도입은 되돌리기 어려운 인프라 결정이라 `docs/decisions/`에 ADR로 남기고 팀 리뷰를 받는다.
- `docker-compose.yml`에 Redis 컨테이너를 추가하는 것은 모든 서비스에 영향이 가는 변경이라 팀 전체 리뷰 대상이다.

## 면접 포인트
- "무엇을 캐시하나": 자주 읽고 드물게 바뀌며, 잠시 오래된 값이어도 괜찮은 데이터. 반대로 상태 전이나 정합성의 근거가 되는 값은 캐시하지 않는다.
- "로컬 캐시와 Redis 중 무엇을 고르나": 무효화를 여러 인스턴스에 전파해야 하면 Redis, 바뀌지 않거나 조금 늦어도 되면 로컬 캐시. Redis는 네트워크 왕복과 장애 지점이 하나 늘어난다.
- "캐시 무효화는 어떻게 했나": 변경 시 키 삭제(cache-aside + evict)를 하고, TTL은 삭제가 실패했을 때의 안전망으로 둔다.
- "캐시 효과를 어떻게 증명했나": 같은 시나리오로 기준선과 비교했다. 응답 시간 분위수, 처리량, 하위 서비스 호출 수, 적중률을 함께 봤다.
- 꼬리 질문: Redis가 죽으면. 원본 조회로 넘어가게 해서 Redis를 성능 최적화 계층으로만 둔다. 반대로 원본까지 몰리는 부하(캐시 스탬피드)는 동시 요청 합치기와 TTL 분산으로 막는다.
