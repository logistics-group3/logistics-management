# 물류 MSA 프로젝트에서 배운 것과 생활의 변화

- 작성일: 2026-10-20
- 작성자: Junhyun An
- 상태: 실제 구현 범위와 실측 수치를 반영한 자기소개서형 회고 초안

## 자기소개서형 회고

MSA 기반 물류 관리 프로젝트에서 주문 서비스 백엔드와 React·TypeScript·Vite 기반 운영 콘솔 제작을 담당했습니다. AI를 활용해 구현과 검증을 진행하며, 주문 처리 기능부터 실제 API를 사용하는 화면, 모니터링과 장애 복구까지 연결했습니다.

주문 백엔드에서는 생성·검색·상세 조회·요청사항 수정·취소·삭제, 비동기 생성 진행 조회, 운영자 복구와 이력 조회를 포함한 외부 API 10종을 구현했습니다. 업체·상품·사용자 권한을 검증하고 배송 서비스와 연동했으며, 멱등키로 동일 요청을 식별하고 원격 호출과 DB 저장의 트랜잭션 경계를 분리했습니다. 실패한 작업의 보상과 복구를 다루면서 서비스 간 통신과 데이터 정합성의 의미를 구체적으로 이해했습니다.

프런트엔드는 대시보드·주문·배송·업체·상품·허브·사용자 관리의 7개 업무 영역으로 구성했습니다. 팀의 서비스 API를 연결해 회원가입과 로그인, 업체·상품 등록, 주문 생성, 배송 구간의 출발·도착 처리를 화면에서 수행하도록 만들었습니다. 대시보드에는 배송 상태 8종의 실제 건수를 표시하고, 상태를 선택하면 해당 조건으로 배송 목록을 조회하도록 연결했습니다.

화면에서도 서버의 처리 상태와 권한을 반영했습니다. 비동기 주문의 진행 조회, 응답 유실·새로고침 후 같은 요청을 확인하는 흐름, 사용자와 배송담당자별 조작 범위, 큰 원화 금액의 정밀도를 다뤘습니다. 모바일 화면과 멘토용 테스트 가이드도 제공해 다른 사람이 업무 흐름을 직접 확인할 수 있도록 했습니다.

주문 커밋 후 배송담당자에게 Slack DM을 비동기로 보내는 기능도 연동했습니다. 이메일로 수신자를 찾고, 알림 전송 실패가 주문 결과에 영향을 주지 않도록 분리했습니다.

서버 상태를 확인하기 위해 Prometheus와 Grafana를 연동했습니다. Gateway를 포함한 6개 서비스의 지표를 15초마다 수집하고, 요청 수·오류율·응답 시간과 JVM·DB 커넥션 상태를 함께 살펴볼 수 있도록 구성했습니다. 이를 통해 성능 문제를 관찰하고 원인 가설을 세우는 방법을 익혔습니다.

k6로 주문 생성 API에 부하를 가한 결과, 실행기가 포화돼 거절될 요청도 업체·상품 조회 3회와 DB 기록을 먼저 수행하는 낭비를 발견했습니다. 실행기 여유를 접수 초기에 확인해 불필요한 작업 전에 거절하도록 개선했습니다.

로컬 환경에서 같은 이미지로 초당 640건을 45초간 요청하는 조건을 두 차례 A/B 비교한 결과, 평균 접수 처리량은 213.5 TPS에서 265.5 TPS로 24.4% 증가했습니다. 접수 API 응답 시간의 p95는 각각 82.4ms에서 17.9ms, 229.5ms에서 19.2ms로 줄었습니다. 이 지표는 거절 응답도 포함하므로 접수 처리량과 함께 확인했고, 두 비교에서 접수된 주문은 모두 최종 완료됐음을 검증했습니다.

측정 과정에서는 데이터 누적과 DB 통계 상태가 결과를 크게 바꿀 수 있다는 점도 배웠습니다. 조건을 바꾼 뒤 더 높은 처리량이 나와도 같은 조건의 코드 개선 효과로 해석할 수 없었습니다. 반복 측정과 원본 기록을 통해 결과를 설명하는 습관을 익혔습니다.

보상 트랜잭션과 Saga 패턴은 실제 장애 복구 과정에서 이해를 넓혔습니다. 주문 처리 전과 배송 생성 후 주문 저장 전이라는 2개 지점에서 서버를 강제 종료해 남는 상태를 확인하고, 운영자가 안전하게 정리할 수 있는 복구 기능을 구현·검증했습니다. 배송 생성 후 중단된 사례에서는 주문 없이 남은 배송 1건과 배송 구간 2건을 복구 후 활성 상태 0건으로 정리했고, 같은 요청을 반복하거나 늦게 배송을 생성해도 데이터가 다시 생기지 않는지 확인했습니다.

AI를 사용하는 환경에서 협업하는 방법도 배웠습니다. 각자의 결과를 팀이 함께 이해하고 검토할 수 있도록 작업 맥락과 기준을 공유하고, 구현·검토·통합에 필요한 시간을 함께 고려했습니다. 이전과 다른 속도로 진행되는 프로젝트에서 일정을 조율하는 경험이었습니다.

개인적으로는 하루 12시간씩 한 가지에 집중하는 생활에 조금 익숙해졌습니다. 단조로운 일상을 반복하고 다른 것들을 덜어내면서, 하나의 문제를 계속 붙잡고 생각하는 시간이 쌓였습니다. 아직 완전히 자리 잡은 습관이라고 단정할 수는 없지만, 집중하는 생활에 적응해가는 경험이었습니다.

### 프런트 검증을 설명할 때

- 2026-10-15 최초 운영 UI 검증은 실제 Gateway·서비스·DB와 브라우저로 회원가입 → 업체·상품 등록 → 주문 → 배송 구간 처리를 확인했다. 이때의 단위 테스트 40개·E2E 14개는 당시 결과다.
- 2026-10-16 허브 간 주문 연동 뒤에는 생성 → 3구간 → 담당자별 처리 → 완료·삭제를 포함한 E2E 18개가 통과했다.
- 2026-10-20 UI 개편 기록은 프런트 단위 테스트 56개와 최종 주요 E2E 17개 통과다. 전체 20개 중 담당자가 고정됐다고 가정한 3개는 데이터 전제 불일치로 미통과이며, 전체 성공으로 쓰지 않는다.
- 문구 수정은 관련 E2E 10개를 확인한 별도 실행이다. 기존 17개와 합쳐 27개의 독립 테스트가 통과했다고 세지 않는다.
- 이번 회고 보강은 코드·기존 실행 기록을 대조한 문서 작업이다. 프런트 코드 변경·새 브라우저 검증은 하지 않았다.

## 수치와 근거

### 주문 성능 개선

2026-10-19의 k6 원본 JSON 4개를 2026-10-20에 대조하고 다시 계산했다. 같은 이미지에서 조기 거절을 끄고 켜며, 각 실행에 초당 640건을 45초 동안 요청한 두 쌍이다.

| 비교 | 적용 전 접수·완료 건수 | 적용 후 접수·완료 건수 | 접수 TPS 전후 | 증가율 | 접수 API p95 전후 |
|---|---:|---:|---|---:|---|
| 1차 | 9,893 | 12,292 | 219.8 → 273.2 | 24.2% | 82.4 → 17.9ms |
| 2차 | 9,319 | 11,600 | 207.1 → 257.8 | 24.5% | 229.5 → 19.2ms |
| 두 실행 평균 | 9,606 | 11,946 | 213.5 → 265.5 | 24.4% | 백분위수는 평균으로 합치지 않는다 |

- 계산: 접수 TPS는 각 실행의 접수 건수 ÷ 45초다. 평균 증가율은 `(23,892 ÷ 19,212 − 1) × 100 = 24.36%`다. 각 실행의 `orders_accepted`와 `orders_completed`가 일치한다.
- p95는 `http_req_duration{name:O-01 접수}`다. 성공·거절 응답을 모두 포함하며, 주문 완료 시간의 p95가 아니다. 개선 후에도 용량을 넘는 요청은 거절했다.
- 환경은 개인 macOS PC 12코어·Docker VM 메모리 7.6GiB·서비스별 인스턴스 1개이며, k6도 같은 PC에서 실행했다. 원본 보고서는 반복 변동을 약 ±15%로 기록한다.
- 이 A/B는 활성 배송 구간이 쌓이고 DB 통계 갱신이 지연되는 조건에서 측정했다. 후속 현실적 데이터 조건에서 조기 거절의 효과를 다시 측정한 결과는 없다. 운영 환경의 용량이나 보편적인 개선율로 일반화하지 않는다.
- 근거: [수치 추출·계산 기록](assets/2026-10-20-order-performance-metrics.json), 별도 로컬 성능 브랜치의 `docs/reviews/2026-10-19-order-load-test.md`. 보고서 확인 버전은 `perf/portfolio-load-test@ea11dd37cd7033d80f52b214dd9fd7263f902b37`다. 원본 보고서·k6 파일은 GitHub에 게시되지 않았다. 이 문서에는 인증 정보를 제외한 수치 요약을 포함하며 원본 파일명·브랜치·SHA-256은 수치 기록에 보존했다.

### 추가로 활용할 문제 해결 사례

통합 테스트의 DB 연결 고갈을 설명하는 자소서에는 다음 문장을 활용할 수 있다.

> 주문 서비스 테스트 463개 중 18개가 실패하는 문제를 조사해, 공유 PostgreSQL에 Spring 테스트 컨텍스트의 커넥션 풀이 누적되는 원인을 찾았습니다. 임시로 풀 크기를 제한해 실패를 0건으로 줄인 뒤, 테스트 컨텍스트 캐시 상한을 8개로 제한하는 공통 대책을 적용했습니다. 후속 세 차례 측정에서 최대 idle 연결 수는 적용 전 91·96·91개에서 적용 후 72·80·80개로 줄었고, 주문 테스트 463개가 통과했습니다.

근거: [초기 실패와 임시 해결](../../../reviews/2026-10-19-test-connection-exhaustion.md), [공통 대책의 3회 측정](../../../reviews/2026-10-19-test-connection-exhaustion-plan.md). 서비스 운영 중 API 성능과 별개의 테스트 환경 개선 사례다.

### 개인 성과 수치에 포함하지 않은 내용

- 배송 조회 p95 `4,307 → 15ms`는 배송 담당자의 장애 격리 기록이다. 본인의 구체적인 기여가 확인되지 않아 개인 성과 문장에 넣지 않았다.
- 접수 약 `350 → 690 TPS`는 실행기·데이터·DB 통계 조건이 달라진 실험이며, 800건/s 구간에는 접수 후 실패 8,164건이 있었다. 안정적인 완료 처리량을 두 배 개선했다고 쓰지 않는다.
- 전체 JUnit XML 857개에는 팀의 기존 테스트와 재사용된 결과가 포함된다. 개인이 새로 작성하거나 이번에 모두 재실행한 수로 쓰지 않는다.
- AI 활용으로 단축한 일정·투입 인원·개발 시간은 비교 기록이 없어 수치화하지 않았다.

## 매체별 활용

링크드인에서는 자기소개서형 회고에서 기술·협업·생활의 변화를 함께 전한다. 하루 12시간이라는 시간과 그 생활에 조금씩 익숙해졌다는 감각을 함께 쓰면 개인적인 경험이 드러난다.

기술블로그에서는 아래 주제별로 실제 문제와 확인 과정을 풀어 쓴다. 회고 본문은 프로젝트 전체를 돌아보는 도입이나 마지막 글로 활용한다.

| 글감 | 중심 질문 | 넣을 내용 |
|---|---|---|
| 백엔드 API를 물류 운영 콘솔로 연결한 과정 | 사용자가 가입부터 주문·배송 처리까지 이어가려면 무엇이 필요했나 | 7개 업무 영역, 실제 API 연동, 권한별 조작, 비동기 진행·미확정 요청, 금액 정밀도 |
| 물류 MSA에서 서비스의 경계를 이해한 과정 | 주문 하나가 여러 서비스를 거칠 때 무엇을 함께 고려해야 했나 | 서비스별 책임, 요청 흐름, 로컬 트랜잭션의 경계 |
| 서버 성능을 측정하고 개선하며 배운 것 | 무엇을 측정했고 어떤 변화로 개선을 판단했나 | 측정 환경·데이터·부하 조건, 관찰한 지표, 변경 내용, 전후 결과 |
| Prometheus와 Grafana로 서버 상태를 살펴본 경험 | 지표를 보고 어떤 질문에 답할 수 있었나 | 요청 수·응답 시간·오류율, 서비스별 관찰, 지표를 해석한 사례 |
| 주문 처리 중 서버가 종료됐을 때의 보상과 복구 | 배송은 만들어졌는데 주문이 없다면 어떻게 처리할까 | Saga와 보상, 장애 지점 재현, 남은 데이터, 운영자 복구와 재요청 검증 |
| AI를 활용하는 팀에서 협업과 일정을 맞춘 경험 | 각자의 작업을 어떻게 함께 이해하고 통합했나 | 맥락과 기준 공유, 결과 검토, 구현·검토·통합 일정에 대한 경험 |

## 작성 근거

- 기술 학습, 서버 성능 측정·개선 경험, AI 환경의 협업·일정 변화, 하루 12시간의 몰입과 생활 변화는 2026-10-20 사용자가 직접 설명한 내용을 바탕으로 정리했다.
- 프런트 제작·주문 API의 구현 범위는 2026-10-20 현재 Controller·앱 메뉴·화면 코드와 Git 이력, 해당 작업의 구현·검증 문서를 대조했다. 다른 작업의 미커밋 프런트 수정과 기존 PR 발행 기록은 보존했다.
- [메트릭 수집 결정 기록](../../../decisions/0018-metrics-prometheus-grafana.md): 수집·표시하는 지표와 도구의 역할을 확인했다.
- [주문 생성 복구 결과](../../../reviews/order-creation-recovery/2026-10-20-implementation-results.md): 배송 생성 뒤 주문 저장 전 서버 종료, 남은 데이터와 운영자 복구 결과를 확인했다. 이 실험은 정합성·복구 검증이며 성능 비교 자료로 사용하지 않는다.
- [프로젝트 공통 지침](../../../../AGENTS.md)과 [서비스 협업 창구](../../../services/README.md): 팀의 공유 기준과 작업 기록 방식을 확인했다.
- 성능 수치는 별도 worktree의 보고서와 k6 원본을 대조해 추가했다. 현재 주문 서비스의 담당자 기록과 성능 ADR 0012의 결정자가 Junhyun An인지 확인했다. 다른 담당자의 성능 개선 기록은 개인 성과에 포함하지 않았다.
- 기술·실험 관련 내용은 기존 기록을 확인한 것이며 이번 글쓰기 작업에서 실험을 재실행한 결과가 아니다.
