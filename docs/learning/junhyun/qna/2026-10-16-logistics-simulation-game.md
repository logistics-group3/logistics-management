# 가속 시간과 AI 돌발 사건을 넣어 물류 시스템을 시뮬레이션 게임으로 만들면 어떤가

## 질문

> 음 그러면 실제 현실처럼 배송상황을 트래킹 하는것도 만들면좋겠는데, 이제 가상의 주문과 배송이 실제로 일어나는거지! 랜덤 딜레이 또는 거리에 비례한 딜레이. 대신 현실시간이 하루 걸린다면 이 서비스에서는 3분 걸리도록? 그리고 ai로 랜덤 사건을 일으키는 거야!! 막 막 물품 유실되고 막 좀비나오고 ! 이런것들이 다 로그로 남아서 시뮬레이션 게임과 물류 관리시스템이 공존하는 그런거는 어떤가?

## 짧은 답

추천하는 방향이다. 가상 주문과 배송이 기존 API를 통해 실제 상태 전이를 만들고, 운영자의 대응에 따라 납기·비용·복구 결과가 달라지게 구성한다.
가상 하루를 현실 3분에 진행하려면 480배속이며, 물류 시간과 서버의 실제 시간을 구분한다.
AI는 허용된 사건을 제안하고 상황을 설명하며, 규칙 엔진과 도메인 서비스가 적용 여부와 결과를 결정한다.
사건·선택·결과를 저장해 재생하고 비교할 수 있으면 게임의 재미와 백엔드 검증이 연결된다.
이번 문서는 설계 제안이다. 서비스 도입·새 상태·API 계약 변경을 확정하거나 구현한 기록이 아니다.

## 자세히

### 1. 사용자가 하는 일

가상의 고객들이 주문하면 배송이 집하 → 허브 이동 → 업체 배송 순서로 진행된다. 지도나 노선 화면에서 현재 구간·예상 도착 시각·지연 이유를 확인한다.
운영자는 문제가 생긴 배송을 찾아 대기·담당자 재배정·우회·재출고 같은 허용된 조치를 선택한다.
게임 결과는 납기 준수율·미완료 건수·운송 비용·복구 시간으로 설명할 수 있다. 계산식과 비용 전제는 구현 전에 정한다.

예를 들어 중앙 허브가 폐쇄되면 기다리는 선택과 우회하는 선택이 생긴다. 우회는 추가 비용을 쓰지만 납기 실패를 줄일 수 있다.
물품 유실 후에는 기존 배송의 유실 기록을 보존하고, 재출고 배송을 원래 주문과 연결한다. 기존 배송을 정상으로 덮어써 이력을 없애지 않는다.
사건이 무작위로 나오는 것에 더해, 사용자의 선택이 결과에 영향을 줘야 운영 게임이 된다.

### 2. 현실 모드와 카오스 모드

| 모드 | 사건의 이야기 | 시스템에 적용할 효과 후보 | 운영 선택 후보 |
|---|---|---|---|
| 현실 | 폭우·교통 정체 | 구간 소요시간 증가 | 대기, 우회, 예상 도착 안내 |
| 현실 | 물품 유실 | 배송 사고 기록·완료 차단 | 조사, 재출고 |
| 현실 | 차량 고장 | 구간 진행 일시 중단 | 담당자·운송 수단 재배정 |
| 카오스 | 좀비 출현 | 특정 허브 또는 노선 일시 폐쇄 | 우회, 출발 보류 |

두 모드는 같은 물류 효과를 재사용할 수 있다. 취업 시연에서는 현실 모드로 정합성·복구를 설명하고 카오스 모드로 확장성을 보여 준다.
현재 API가 우회·유실·재출고까지 지원한다는 뜻은 아니다. 사건 종류별로 필요한 상태·계약을 추가 설계해야 한다.

### 3. 하루를 3분으로 압축하는 방법

`24 × 60 × 60 ÷ (3 × 60) = 480`이므로 현실 1초에 가상 8분이 흐른다. 가상 1시간은 현실 7.5초다.
구간 이동시간은 `거리 ÷ 평균속도 + 상하차·대기시간 + 사건으로 인한 추가시간` 같은 모델로 계산한 뒤 가상 시계에 예약한다.
초기에는 기존 허브 경로의 예상 소요시간을 쓰고, 범위가 정해진 무작위 지연을 더하는 방식으로 시작할 수 있다.

- 가상 시계: 출발·도착 예약, 교통 지연, 납기와 영업 시간 계산에 사용한다.
- 실제 시계: JWT 만료, HTTP 타임아웃, DB 감사 시각, 서버 지연 측정에 사용한다.
- 속도 변경·일시정지: 그 시점의 가상 시각을 기준으로 이후 흐름에 적용한다. 전체 경과시간에 새 배율을 곱해 과거를 바꾸지 않는다.
- 재기동: 마지막 가상 시각·실행 상태·미처리 사건을 저장한다. 초기 데모는 서버 중단 시간 동안 세계도 정지하는 정책을 제안한다.
- 진행 중인 HTTP 요청: 세계를 일시정지해도 이미 전송된 작업은 완료될 수 있으므로 결과를 계속 기록한다.

Java 17의 `Clock`은 시간 의존성을 주입할 수 있는 추상화다. 480배속·정지·복구 정책은 별도로 구현해야 하며, `Clock.offset`만으로 가속 시계가 되지는 않는다([공식 문서](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/Clock.html)).

배송마다 스레드를 만들고 오래 sleep하는 방식보다 다음 사건의 실행 시각을 관리하는 방식을 추천한다.
같은 가상 시각의 사건에도 순서를 정하고, 아직 생성되지 않은 배송의 도착을 먼저 적용하지 않도록 한다. SimPy도 시각과 증가하는 사건 ID로 순서를 관리한다([공식 문서](https://simpy.readthedocs.io/en/latest/topical_guides/time_and_scheduling.html)).
480배속과 480배의 HTTP 트래픽은 다르다. API 처리량을 넘으면 대기열을 관측하고 발행량을 제한해야 하며, 부하 시험은 별도 목표와 환경으로 수행한다.

### 4. 시뮬레이션 실행기와 물류 서비스의 책임

시뮬레이션 실행기는 가상 고객·배송 기사·외부 상황을 맡고 기존 서비스 API에 명령을 보낸다.
주문·배송 서비스는 권한, 상태 전이, 중복 처리와 정합성을 기존 도메인 규칙에 따라 검증한다. 실행기가 서비스 DB를 직접 바꿔 성공처럼 꾸미지 않는다.
사건 효과에 새 API가 필요하면 제공 서비스와 계약을 먼저 정한다. 별도 서비스나 모듈로 분리하는 방식은 구현 범위에 따라 선택할 후보로 둔다.

첫 단계는 전용 테스트 스택과 가상 계정을 사용해 시뮬레이션 데이터를 격리하는 방식을 추천한다.
실행별 runId와 요청별 멱등키를 두고, 재실행 시 이전 주문·배송과 섞이지 않도록 한다. 외부 Slack 발송은 이 환경에서 끈다.
화면의 이동 좌표는 가상 위치임을 표시한다. 지도 애니메이션은 서버의 구간·가상 시간으로 보간할 수 있지만 실제 배송 상태의 권위는 서버에 둔다.

### 5. AI는 사건을 제안하고 규칙이 결과를 결정한다

AI가 제안할 수 있는 사건 종류, 대상, 강도, 지속 시간과 빈도에 범위를 둔다.
예를 들어 “중앙 허브 주변 좀비 출현”이라는 설명과 `HUB_CLOSED` 효과를 제안하면, 규칙 엔진이 존재하는 허브인지·현재 적용 가능한지·종료 시각이 유효한지 확인한다.
허용된 명령으로만 적용하고, 실패하거나 거절된 제안도 원인과 함께 저장한다.

매 tick마다 모델을 호출하지 않는다. 실행 시작 전에 사건 후보를 묶어서 준비하거나 다음 사건이 필요할 때 비동기로 준비한다.
AI 응답이 늦거나 형식이 틀리면 정해 둔 사건 목록으로 진행할 수 있게 한다. 물류 세계의 시간이 모델 응답에 묶이지 않도록 한다.
일반 교통 지연의 수치와 확률은 난수 생성기로 충분하다. AI는 상황에 맞는 사건 조합·설명·운영 리포트에 쓰는 것이 유용하다.

### 6. 모든 사건을 기록하고 재생한다

사건 기록에는 runId, eventId, 대상 주문·배송, 가상 발생 시각, 실제 기록 시각, 사건 종류·효과, 생성 주체, 원인 사건 ID를 둔다.
운영자의 선택과 API 명령·응답, 관련 traceId, 실제 적용 결과도 연결한다. 사람이 읽는 사건 일지와 디버깅용 기술 로그는 같은 식별자로 찾을 수 있게 한다.
배송 지연·물품 유실 같은 업무 사건과 HTTP 타임아웃·프로세스 종료 같은 기술 장애는 별도 유형으로 기록한다. 두 사건은 함께 발생시켜 볼 수 있다.

난수 seed뿐 아니라 확정된 AI 사건, 초기 데이터, 시나리오·엔진 버전, 운영자 선택을 저장해야 한다.
Java `Random`은 같은 seed와 같은 호출 순서에서 같은 난수열을 만들지만, LLM 응답이나 분산 서비스의 처리 순서까지 같게 만들지는 않는다([공식 문서](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/Random.html)).

- 기록 재생: 저장된 사건과 결과를 시간순으로 보여 준다. 재생 버튼이 실제 API를 다시 호출하지 않는다.
- 전략 비교: 같은 초기 상태와 사건 목록으로 새 실행을 만들고 다른 대응을 선택한다. 결과가 달라진 이유를 비교한다.
- 회귀 검증: 결정적인 엔진 테스트와 실제 서비스 통합 실험을 구분한다. 서비스 실험은 처리 순서가 달라도 지켜야 하는 불변식으로 검증한다.

사건 일지를 보관하려고 전체 서비스를 Event Sourcing으로 전환할 필요는 없다. 첫 단계는 실행·예정 사건·적용 결과를 기록하는 것으로 범위를 제한한다.

### 7. 작은 첫 버전과 이후 순서

첫 버전은 허브 3개, 소수의 가상 주문, 480배속, 노선별 진행 표시, 지연 사건 1종, 사건 일지로 시작하는 것을 추천한다. 수치는 초기 범위 제안이다.
기존 집하·허브 이동·업체 배송 API를 실제로 호출하고, 새로고침·일시정지·재기동 이후의 일관성을 확인한다.

1. 허브 간 경로 API·데이터와 정상 주문 흐름을 완성한다.
2. 가상 시간·주문 생성·배송 구간 진행·기록을 연결한다.
3. 현실 사건 1종과 운영자 대응 1종을 끝까지 연결한다.
4. 사건 재생과 같은 시나리오의 대응 전략 비교를 추가한다.
5. AI 사건 제안과 좀비 테마를 얹는다.
6. 기존 [장애 복구 고도화](2026-10-16-backend-portfolio-hardening.md)와 연결해 지연 응답·재기동·중복 요청도 실험한다.

첫 버전에서 3D 전투·경제 시스템·전국 도로 라우팅까지 함께 구현하면 물류 정합성·재현성 검증에 쓸 시간이 줄어든다.
시뮬레이션에서 가정한 비용·속도와 실측 API 성능을 구분하고, 실제 물류 기업의 운영 데이터를 재현했다고 주장하지 않는다.

## 이 프로젝트에서는

- 현재 `Delivery`는 집하·허브 이동·업체 배송 구간을 만들고 구간 상태를 통해 전체 배송 상태를 바꾼다. 가상 기사가 기존 D-05 상태 변경 API를 호출하는 출발점이 있다.
- 현재 `RouteStatus`는 WAITING·MOVING·ARRIVED·CANCELED다. 유실·보류·우회 상태나 사고 모델은 아직 이 enum에 없다. 명칭을 임의로 확정하지 않는다.
- `Hub`에는 위도·경도가, `HubRoute`와 `RouteInfo`에는 거리·예상 소요시간이 있다. 실제 GPS가 아니라 가상 이동 위치를 계산할 기초 데이터다.
- 현재 SA는 재고를 무한으로 가정하고 배차 경로 최적화·AI 연동을 기본 범위에서 제외한다. 새 기능을 채택할 때 설계·계약을 합의하고 ADR을 남긴다.
- 코드 확인 기준은 2026-10-16 HEAD `9f64e3c`다. 별도 모니터링 작업의 미커밋 변경은 이 상담에서 수정하지 않았다.

## 면접 포인트

- 가상 시간과 실제 시간을 왜 분리했는가? 물류 진행을 빠르게 해도 인증 만료·통신 타임아웃·실제 성능 측정의 의미는 유지해야 한다.
- 랜덤 사건인데 어떻게 재현하는가? seed·호출 순서와 확정 사건·입력·엔진 버전을 기록하고, 재생과 재실행을 구분한다.
- AI가 잘못된 사건을 만들면 어떻게 하는가? 구조·대상·강도·현재 상태를 검증하고 거절하며 기본 사건으로 대체한다.
- 시뮬레이터가 직접 DB를 바꾸면 무엇이 빠지는가? 실제 API의 인증·권한·트랜잭션·멱등성 검증을 우회하게 된다.
- 유실 후 재출고는 중복 배송과 어떻게 다른가? 새 배송의 업무상 근거와 원래 주문·사고·이전 배송 관계를 기록해야 한다.
