# 이 프로젝트는 DDoS에 대비돼 있나, 그리고 k6로 DDoS 테스트를 할 수 있나

## 질문

DDoS 공격에 대한 대비가 돼 있는지 알려 달라. DDoS 테스트도 k6로 하는 건가?

## 짧은 답

애플리케이션 계층(L7)의 방어는 거의 없다. Gateway에 요청 제한이 없고 로그인 시도 제한도 없다. 서비스 하나가 느려지는 것을 막는 장치(주문 실행기 상한, delivery의 서킷 브레이커)는 일부 있지만, 과도한 요청 자체를 막는 장치는 아니다.
k6로는 "한 대의 PC에서 HTTP 요청을 쏟아붓는" L7 부하(HTTP flood, 로그인 무차별 대입 모의)를 재현할 수 있다. 분산 출처, 네트워크 계층 대량 트래픽, 연결을 오래 붙잡는 공격은 k6로 흉내 낼 수 없고, 실제 방어는 CDN·WAF·클라우드 계층이 맡는다.
테스트는 **내 PC의 전용 로컬 스택에만** 한다. 남의 서버나 팀 공용 환경에 쏘지 않는다.

## 자세히

### 1. 현재 상태(2026-10-19 확인)

| 항목 | 상태 | 근거 |
|---|---|---|
| Gateway 요청 제한(rate limit) | 없음 | `gateway-service`와 `config-repo`에 요청 제한 설정이 없다. [보안 노트](2026-10-16-security-hardening-priorities.md)도 같은 결론 |
| 로그인 시도 제한·계정 잠금 | 없음 | 오답 로그인 300건을 동시 20으로 보내 2.9초(약 100건/초)에 모두 401, 429 없음(로컬 전용 스택) |
| 로그인 비용 | BCrypt 포함 건당 약 58ms | 정상 로그인 3회 측정. 로그인은 인증 없이 통과하는 경로이고 CPU를 쓰므로 한 계정·한 IP가 user-service CPU를 쓸 수 있다. 다른 요청에 미치는 영향은 **측정하지 않았다** |
| 토큰 없는 요청 | 싸게 거절 | 400건을 동시 40으로 보내 모두 401. Gateway가 처리하고 하위 서비스에는 닿지 않는다(하위 서비스 호출 여부는 별도로 확인하지 않았다) |
| 클라이언트 IP 신뢰 | 해당 없음 | `X-Forwarded-For`를 위조해도 응답이 달라지지 않는다. IP 기준 제한 자체가 없다 |
| 큰 본문 | 400으로 거절 | 5MB 본문 로그인 요청이 51ms에 400. 본문 크기 상한 설정이 있는지, 응답이 검증 때문인지 상한 때문인지는 **미확인** |
| 목록 API의 페이지 크기 상한 | 미확인 | 큰 `size`로 비싼 조회를 만들 수 있는지 확인하지 않았다 |
| 느린 연결·연결 고갈(slowloris) | 미확인 | k6로는 확인하기 어렵다 |
| 관리 포트 | 비공개 | 호스트에는 Gateway 8080만 공개한다(ADR 0018) |

### 2. 과부하에서 이미 가진 방어(요청 제한은 아님)

- 주문 생성은 처리 실행기가 유한(스레드 4·대기열 50)하고, 가득 차면 업체 조회·기록 전에 바로 503이다([ADR 0012](../../../services/order/decisions/0012-order-shed-load-before-accept.md)). 측정으로 한계(접수 약 320~350 TPS)를 확인했다([부하 측정 보고서](../../../reviews/2026-10-19-order-load-test.md)).
- delivery의 user 호출에는 타임아웃·벌크헤드·서킷 브레이커가 있다(T06). 다른 서비스 호출에는 없다.
- 내부 Feign 호출에는 타임아웃이 있다.
- 단점: 막는 곳이 서비스 안이라, 공격 트래픽이 이미 Gateway와 서비스 스레드를 쓴 뒤다. 정상 사용자도 같은 503을 받는다.

### 3. k6로 할 수 있는 것과 없는 것

| 공격 유형 | k6로 재현 | 비고 |
|---|---|---|
| L7 HTTP flood(한 엔드포인트에 다량 요청) | 가능 | 한 PC의 처리 한계까지. 우리가 한 부하 측정이 이 형태다 |
| 로그인 무차별 대입·계정 대입 | 가능 | 429가 나오는지, 로그인 폭주 중 정상 요청이 얼마나 느려지는지 측정 |
| 비싼 엔드포인트 겨냥(큰 조회) | 가능 | 먼저 비싼 경로를 찾아야 한다 |
| 분산 출처(여러 IP) | 불가 | 한 PC의 한 IP. IP별 제한 검증이 어렵다. 헤더 위조는 신뢰 경계를 시험하는 것이지 분산이 아니다 |
| L3/L4 대량 트래픽(SYN flood, UDP) | 불가 | k6는 HTTP 도구. 이 계층은 로컬에서 재현하지 않고 CDN·클라우드 보호에 맡긴다 |
| slowloris(연결을 오래 붙잡기) | 사실상 불가 | 전용 도구(slowhttptest 등)가 맞다 |

현업에서 "DDoS 대비"는 대부분 **앞단(CDN, WAF, 로드밸런서의 보호)** 에서 대량 트래픽을 걸러 내고, 서비스는 **요청 제한·타임아웃·격리·자동 확장** 으로 버티게 한다. 로컬 부하 테스트는 "서비스 안쪽이 어디서 무너지는가"를 보는 용도다.

### 4. 고도화 순서 제안

1. **먼저 측정**: 로그인 폭주(예: 초당 200건)를 걸고 동시에 정상 주문(초당 20건)의 p95·실패율을 잰다. 정상 요청이 영향을 받는지 숫자로 확인한다.
2. **Gateway 요청 제한**: Spring Cloud Gateway의 `RequestRateLimiter`로 IP별·사용자별 제한. 인스턴스 간 공유가 필요하면 Redis가 필요하다(신규 인프라라 결정 기록 필요). 초과 시 429와 `Retry-After`.
3. **로그인 보호**: 계정별 짧은 재시도 제한. 계정을 오래 잠그면 타인이 일부러 잠글 수 있어 짧은 지연 방식을 쓴다.
4. **신뢰 경계**: 프록시가 붙으면 `X-Forwarded-For`를 신뢰할 프록시에서만 받는다.
5. **입력 상한**: 본문 크기, 목록 `size` 상한.
6. **다시 측정**: 같은 시나리오로 전후를 비교한다. 정상 요청의 p95가 얼마나 보호되는지가 핵심 지표다.

주의: 제한은 정상 사용자도 막을 수 있다. 임계값은 실제 정상 트래픽(이 프로젝트의 한계는 접수 약 320~350 TPS)보다 충분히 높게 시작하고 관측하면서 조정한다.

## 이 프로젝트에서는

- 요청 제한을 넣을 위치는 `gateway-service`다. 설정은 `config-repo/gateway-service.yml`이고 보안 필터는 `gateway/security/`에 있다.
- 로그인은 `user-service`의 `AuthService`이며 `dummyPasswordHash`로 존재하지 않는 사용자와 소요 시간을 비슷하게 맞춰 두었다(계정 존재 여부 추측 방지). 이 설계 덕에 오답 로그인도 BCrypt 비용을 낸다.

## 면접 포인트

- "DDoS를 어떻게 막았나요?"에는 "앞단 보호(CDN·WAF)와 서비스 안쪽 방어(요청 제한·격리·타임아웃)를 나누어 설명하고, 서비스 안쪽은 측정으로 한계를 확인했다"고 답한다. 한 PC의 k6로 DDoS 전체를 재현했다고 말하지 않는다.
- 요청 제한 알고리즘(토큰 버킷, 고정·슬라이딩 윈도우), 분산 환경에서 카운터 공유(Redis), 정상 사용자 오차단과 임계값 조정, 로그인 계정 잠금의 악용 가능성.
