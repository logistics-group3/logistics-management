# 주문 도메인은 어떤 기능부터 구현하는 것이 좋은가

## 질문
> 자! dev로 부터 나의 작업 브랜치를 파볼까!! 어떤 기능부터 만드는게 좋을까.... 나의 담당은 주문 도메인이야.

## 짧은 답
첫 기능으로 주문 생성(O-01)을 추천한다. 첫 구현 단위는 주문 모델·테이블·저장 테스트로 작게 잡는다.
이후 업체·상품 검증, 배송 생성, 실패 보상을 붙이고 마지막에 커밋 후 알림까지 완성한다.
다른 서비스가 준비되기 전에는 테스트 대역으로 흐름을 검증하고 실제 연동은 별도로 확인한다.

## 자세히
주문 생성은 주문에 무엇을 저장할지, 누가 주문할 수 있는지, 배송과 어떻게 연결할지를 함께 드러낸다. 이 기준을 먼저 구현하면 조회·수정·취소가 같은 모델 위에서 이어진다.
한 번에 전체 흐름을 구현하면 DB 문제와 원격 API 문제를 구분하기 어려우므로 다음 순서를 제안한다.

| 순서 | 구현 범위 | 확인할 동작 |
|---|---|---|
| 1 | `Order`, `OrderStatus`, Flyway, Repository | 수량·금액 규칙, 상품명·단가 스냅샷, 저장·조회, 논리 삭제 |
| 2 | 주문 생성 application 흐름과 외부 호출 테스트 대역 | 업체·상품 소속과 주문 권한 검증, 배송 생성, 주문 저장 |
| 3 | 실패 보상과 O-01 HTTP API | 배송 타임아웃·주문 저장 실패 시 배송 삭제, 입력 검증과 응답 계약 |
| 4 | Slack 알림과 실제 서비스 연동 | 커밋한 주문만 알림, 알림 실패 시 주문 유지, 실제 API 계약 일치 |

테스트 대역은 실제 company·delivery 서버 대신 약속된 성공·실패 응답을 돌려주는 객체다. 이를 이용해 상대 서비스 구현을 기다리지 않고 주문 로직을 검증할 수 있지만, 실제 HTTP 통신이나 전체 서비스 연동까지 검증한 것은 아니다.

주문 생성 이후에는 단건 조회(O-03) → 검색(O-02) → 요청사항 수정(O-04) → 취소(O-05) → 삭제(O-06)를 추천한다. 단건 조회부터 구현하는 선택도 가능하지만, 생성 과정의 권한·스냅샷·배송 연결이 주문 도메인의 핵심이므로 먼저 기반을 잡는 편이 낫다.

## 이 프로젝트에서는
- 브랜치는 `origin/dev`의 `f700c0c`에서 만든 `feat/order-create`다. 브랜치 생성 뒤 진행한 기반 구현은 [스텝 35](../steps/step-35-order-foundation.md)에 기록했다.
- 주문 1건은 한 품목이다. 첫 구현에 `OrderItem`이나 장바구니 모델을 추가할 근거는 없다.
- 상품명과 단가는 주문 시점 값을 보관하고 `totalPrice = unitPrice × quantity`를 계산해 저장한다. 요청에서 임의의 가격을 받지 않는다.
- `orderId`는 배송 호출 전에 선발급한다. 배송 생성 후 주문 저장이 실패하면 같은 ID로 배송 삭제(I-13)를 요청한다.
- 주문 상태는 `ORDERED`, `CANCELED`다. 배송 진행 상태는 delivery-service가 관리한다.
- SA v2.0은 재고 확인·차감을 기본 범위에서 제외한다. 주문 ADR 0001·0002의 재고 처리와 `HUB_WAITING` 취소 조건은 제안 상태의 구안이므로 구현 기준으로 쓰지 않는다.
- company I-07·I-08, delivery I-09·I-13은 확인한 `dev`에서 아직 구현되지 않았다. 구현 전에 해당 서비스 협업 창구에서 계약을 맞추고, 실제 통합 검증은 상대 API가 준비된 뒤 수행한다.

## 면접 포인트
- 상품 가격을 매번 조회하지 않고 주문에 저장하는 이유는 무엇인가? 상품 정보가 바뀌어도 주문 당시 금액과 상품명을 보존하기 위해서다.
- 배송 생성은 성공했지만 주문 저장이 실패하면 어떻게 하는가? 주문의 로컬 트랜잭션을 롤백하고, 선발급한 orderId로 배송 삭제 보상을 호출한다. 상대 서비스 DB까지 로컬 트랜잭션으로 되돌릴 수는 없다.

## 주문 기반 다음에 할 일 (2026-10-15 후속 질문)

> 좋아 이 다음엔 뭐해야하지!

주문 기반과 정수 원화 금액 복원이 끝났으므로 다음 추천 범위는 O-01의 application 흐름과 테스트 대역을 이용한 단위 테스트다. 이번 후속 질문에서는 다음 범위만 정리했으며 기능 코드는 추가하지 않았다.
현재 기반은 미커밋 상태다. 먼저 `feat(order): 주문 엔티티와 저장소 기반 구현`처럼 검증한 기반을 한 커밋으로 남긴 뒤 다음 구현을 진행하면 변경을 구분하기 쉽다. 커밋은 사용자 요청 시 수행한다.

| 만들 것 | 역할 |
|---|---|
| `CreateOrderCommand`, `OrderResult` | application의 입력과 결과. 금액은 정수 원 단위 long이다 |
| 업체·상품 조회 및 배송 생성·삭제 인터페이스 | company I-07·I-08, delivery I-09·I-13을 호출하는 경계. 테스트에서는 Mock으로 대체한다 |
| `OrderService`와 단위 테스트 | ID 선발급 → 업체·상품·권한 검증 → 배송 생성 → 주문 저장을 조율하고 실패를 보상한다 |

먼저 확인할 시나리오는 다음과 같다.

1. 정상 요청은 같은 orderId로 배송을 생성하고 반환된 deliveryId를 주문에 저장한다.
2. 상품이 공급업체 소속이 아니거나 요청자가 수령업체 관리자가 아니면 배송 생성·주문 저장을 하지 않는다. MASTER의 관리자 확인 예외도 검증한다.
3. 배송담당자 없음처럼 저장 전에 거절된 실패는 그대로 반환한다.
4. 배송 타임아웃·5xx는 생성 여부를 모르므로 선발급 orderId로 배송 삭제 보상을 호출한다.
5. 배송 성공 후 주문 DB 저장·커밋이 실패하면 배송을 삭제한다. 보상 자체가 실패하면 SA의 재시도·로그 규칙을 적용한다.

원격 호출은 DB 트랜잭션 밖에 두고 주문 저장만 로컬 트랜잭션으로 묶는다. 저장 메서드의 flush 성공과 최종 커밋 성공을 구분해야 한다.
이 단계가 통과하면 실제 Feign 구현과 Controller를 연결하고 Gateway를 통한 API 검증, 커밋 후 Slack 알림으로 이어간다. Mock 테스트 통과는 실제 서비스 연동 완료를 의미하지 않는다.
