# 성능 병목은 어떤 과정으로 찾나

## 질문

원래 병목을 찾으려면 어떤 과정을 거쳐야 하나?

## 짧은 답

병목은 느린 곳이 아니라 부하를 올릴 때 가장 먼저 포화되는 자원이다. 환경을 안정시키고, 증상을 숫자로 정의하고, 모든 자원의 사용률·대기·오류를 같은 시각에 보면서 부하를 단계적으로 올려 포화가 처음 나타나는 곳을 찾는다. 그다음 가설 하나에 변경 하나만 주고 같은 방법으로 다시 잰다. 하나를 고치면 병목이 옮겨 가므로 한계가 얼마나 올랐는지 확인한다.

## 자세히

1. **측정 환경을 안정시킨다.** 같은 데이터 상태, 예열, 호스트의 다른 부하 제거. 반복 측정으로 변동폭을 먼저 안다. 변동폭보다 작은 차이는 개선으로 말하지 않는다.
2. **증상을 숫자로 정의한다.** 예: 접수가 약 320~350/s에서 늘지 않고 p95가 튄다.
3. **자원 관점(USE)과 요청 관점(RED)으로 본다.** 자원마다 Utilization·Saturation·Errors를, 서비스마다 Rate·Errors·Duration을 본다. 사용률보다 포화(큐 길이, 대기 시간)가 병목의 신호다.
4. **포화가 처음 나타나는 곳을 찾는다.** 단계 부하에서 처리량이 꺾이는 순간 가장 먼저 변하는 지표가 후보다.
5. **구간별로 시간을 쪼갠다.** 분산 추적으로 한 요청의 시간이 어느 호출에 쓰이는지 본다.
6. **가설 하나, 변경 하나.** 여러 개를 한꺼번에 바꾸면 효과의 원인을 알 수 없다. 켬·끔을 번갈아 짝으로 비교한다.
7. **병목은 옮겨 간다.** 고친 뒤 같은 방법으로 다시 재서 새 한계와 다음 병목을 확인한다.
8. **고치지 않는 병목도 기록한다.** 이유와 함께 남긴다.

## 이 프로젝트에서는

- 주문 생성의 한계는 접수 약 320~350 TPS이고 원인은 아직 특정하지 못했다. 후보는 호스트 CPU 경쟁(k6와 서비스가 한 PC), 요청당 업체·상품 조회 3건, delivery의 활성 구간 집계, order 실행기·DB 풀이다. 근거: [주문 부하 측정 보고서](../../../reviews/2026-10-19-order-load-test.md).
- 도구: k6, Prometheus·Grafana(HikariCP·Feign 패널), Zipkin, `docker stats`, `pg_stat_activity`.

## 면접 포인트

- "병목을 어떻게 찾았나요?"에는 "추측하지 않고 포화가 먼저 오는 자원을 단계 부하와 지표로 찾았고, 가설 하나씩 켬·끔 비교로 검증했다"고 답한다.
- USE와 RED의 차이, 사용률과 포화의 차이, 병목이 옮겨 가는 현상, 측정 환경이 결과를 바꾸는 사례(이 프로젝트의 데이터 누적·호스트 경쟁).
