# 물류 서비스를 취업 포트폴리오로 고도화할 때 무엇부터 해야 하나

## 질문

> 지금 이 서비스 고도화해서 취업에 쓰고싶은데 뭘 고도화하면좋을까? 진짜 막 와 진짜 얘는 진짜다 싶을만한걸로

## 짧은 답

백엔드 취업 기준으로는 장애가 발생한 주문의 결과를 확인하고 안전하게 복구하는 기능을 대표 사례로 추천한다.
현재 구현된 멱등키·진행 기록·커밋 재확인을 바탕으로, 늦게 도착한 배송 생성과 삭제의 순서 역전까지 해결하는 방향이다.
장애 주입, 복구 관제 화면, 변경 전후 측정을 함께 제공하면 설계 이유와 검증 근거를 보여 줄 수 있다.
기본 허브 간 주문 흐름을 먼저 완성하고, 복구 사례를 완성한 뒤 알림 Outbox와 재고 동시성으로 확장한다.
이 문서는 우선순위 제안이다. 설계 변경의 채택이나 고도화 구현을 확정한 기록이 아니다.

## 자세히

### 1. 현재 구현에서 출발한다

검토 기준은 2026-10-16 로컬 브랜치 `feat/infra-monitoring-mentor-guide`, HEAD `9f64e3c`다.
코드·테스트 소스·설계 문서를 정적으로 읽었으며, 이번 상담에서 서비스를 실행하거나 장애·성능 실험을 하지는 않았다.

| 확인한 내용 | 근거 | 고도화와의 연결 |
|---|---|---|
| 사용자별 주문 멱등키, 진행 기록, 커밋 재확인 구현이 있다 | `OrderService`, `OrderWriter`, `OrderCreation`, 주문 ADR 0007·0008 | 같은 기능을 새 과제로 잡기보다 복구까지 이어 간다 |
| 불확실한 배송 결과는 `RECOVERY_REQUIRED`로 남는다 | `OrderService.handleUnknownDelivery`, 주문 실패 처리 문서 | 결과 조회·복구 유스케이스가 후속 과제다 |
| 삭제할 배송이 없으면 I-13은 종료하고, I-09는 이후 저장될 수 있다 | `DeliveryService.deleteByOrderId`, `DeliveryCreationService.create`, DELIVERY-002 OPEN | 늦은 생성과 종료 요청의 순서 역전을 재현할 수 있다 |
| 주문 알림은 커밋 후 메모리 비동기 작업으로 전달한다 | `OrderCreatedEventListener`, `SlackOrderNotificationSender` | 커밋 이후 프로세스 종료 시 전달할 작업을 잃을 수 있다 |
| Zipkin 계측 설정은 있다. Prometheus·Grafana는 별도 작업이 진행 중이다 | 루트 `build.gradle`, `config-repo/application.yml`, `docker-compose.yml`, 현재 progress | 이 상담에서 모니터링 구축 완료를 검증한 것은 아니다 |
| 허브 내부 Controller는 I-02만 제공하며 경로 I-03 Controller가 없다 | `InternalHubController`, hub 소스 목록, delivery 협업 문서 | 허브 간 정상 주문의 실제 연동을 먼저 완성한다 |
| 주문은 재고를 차감하지 않는다 | `OrderService.create`, SA 1장·2장 | 무한 재고가 현재 합의다. 유한 재고는 별도 고도화 설계다 |

테스트 파일의 존재는 현재 실행 성공의 증거가 아니다. 기존 문서의 과거 검증 결과와 이번 상담의 검증 범위를 구분한다.

### 2. 최우선: 주문 장애 복구와 운영 관제

대표 질문은 “요청은 타임아웃인데, 상대 서비스가 이미 처리했다면 어떻게 하는가?”다.
현재 코드는 결과를 모른다는 사실을 기록한다. 다음 단계는 그 기록을 실제 확인·복구 절차로 연결하는 것이다.

대표 실험은 다음 순서를 강제로 만든다.

1. 주문이 배송 생성 I-09를 호출한다. 배송 저장 직전 처리를 지연시킨다.
2. 주문 쪽 타임아웃이 발생하고 배송 삭제 I-13이 먼저 실행된다.
3. 아직 배송이 없으므로 삭제는 204를 반환한다.
4. 멈췄던 I-09를 진행시키면 주문 없는 배송이 뒤늦게 생길 수 있다.
5. 개선 후 같은 실험에서 종료된 주문의 배송이 새로 살아나지 않는지 검증한다.

복구 설계 후보는 다음과 같다. 제공 서비스와 계약을 정한 뒤 하나씩 구현한다.

- 주문 시도 상태 조회와 운영자 복구 목록: 원인·경과 시간·orderId·attemptId·관련 trace를 보여 준다.
- 결과 대조: 각 서비스의 조회 계약을 통해 실제 결과를 확인한다. 정상 서비스 코드가 다른 서비스 DB를 직접 읽는 방식은 피한다.
- 종료 표시 보존: 배송이 아직 없더라도 해당 orderId의 생성 종료를 기록하고, 생성과 종료가 같은 작업 기록을 기준으로 원자적으로 경합하도록 한다. 종료 표시를 읽고 별도로 INSERT하는 것만으로는 경쟁 조건을 없애지 못한다.
- 오래된 실행 차단: 시도 토큰이나 버전을 쓰는 경우 실제 저장 시점에 검증한다. 토큰을 요청에 붙이는 것만으로는 충분하지 않다.
- 복구 실행권: 복구 작업자 두 개가 동시에 실행돼도 같은 보상을 중복 적용하지 않도록 한다. 실행권 만료 후 과거 작업자가 늦게 돌아오는 경우도 검증한다.
- 복구 이력: 누가 어떤 근거로 재확인·보상·종료했는지 남긴다. 버튼으로 상태 값만 바꾸는 구현은 피한다.
- 안전한 중단: 증거가 부족하면 수동 확인 대상으로 남긴다. 경과 시간만으로 실패나 미처리를 단정하지 않는다.

현재 생성 기록은 원본 요청 전체를 재실행용으로 저장하지 않는다. 자동으로 원래 주문을 다시 만드는 기능과, 이미 발생한 작업의 결과를 대조·정리하는 기능은 구분해야 한다.
먼저 결과 확인과 정리 범위를 완성하면 변경 범위를 줄일 수 있다.
AWS도 멱등 요청의 늦은 도착과 리소스 삭제 이후의 동작을 별도 설계 문제로 설명한다([공식 문서](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)).

### 3. 복구 기능과 함께 만드는 증명 수단

전용 테스트 환경에서만 동작하는 장애 시나리오 실행 도구와 관제 화면을 만든다. 기존 운영 콘솔을 확장하면 된다.
시나리오 실행은 실제 외부 Slack 전송을 끈 환경에서 수행한다. 사용자 운영 환경의 프로세스를 임의로 중단하지 않는다.

| 실험 | 확인할 불변식·결과 |
|---|---|
| 동일 사용자·키·본문 동시 재전송 | 논리 주문과 배송이 중복 생성되지 않는다. 처리 중 응답과 완료 재조회도 확인한다 |
| 배송 커밋 후 HTTP 응답 유실 | 타임아웃을 미처리로 오판하지 않고 실제 결과로 수렴한다 |
| 삭제 요청 이후 늦은 생성 | 종료된 시도가 새 배송을 만들지 않는다 |
| 진행 기록 저장 후 주문 프로세스 종료·재기동 | 멈춘 시도가 탐지되고 근거에 따라 복구되거나 수동 확인 대상으로 남는다 |
| 복구 작업자 두 개의 동시 실행 | 중복 부작용이 없고 오래된 작업자의 후속 저장을 막는다 |
| 하위 서비스 지연 중 정상 요청 유입 | 요청 시간 예산과 재시도 횟수가 제한되고, 다른 기능의 지연·오류 영향을 측정할 수 있다 |

HTTP 200 비율만으로 성공을 판정하지 않는다. 중복 주문 수, 고아 배송 수, 미복구 건수, 가장 오래된 복구 대기 시간, 복구 시간 분포를 함께 확인한다.
관제 화면에는 주문 상태 전이와 복구 이력을 두고, 상세 요청 원인은 기존 Zipkin trace로 연결한다. orderId·traceId를 메트릭 label로 계속 추가하는 방식은 피한다.
장애 중 재시도가 요청을 더 늘릴 수 있으므로 호출 전체의 시간 예산과 재시도 주체를 정한다([AWS 공식 문서](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)).

### 4. 다음 확장: 알림 Outbox

Outbox는 주문과 “보낼 이벤트”를 같은 DB 트랜잭션에 저장한 뒤 별도 작업자가 전달하는 방식이다.
주문 커밋과 비동기 작업 제출 사이에 프로세스가 종료돼도 보낼 작업을 다시 찾을 수 있다.
다만 전달은 중복될 수 있으므로 수신 측의 멱등 처리도 필요하다([AWS 공식 문서](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)).

먼저 DB Outbox와 제한된 재시도·실패 이력·수동 재처리를 구현하는 후보를 검토한다. Kafka는 소비자 분리·재생·처리량 등 필요성을 확인한 뒤 비교한다.
내부 소비자는 처리 기록과 실제 변경을 같은 트랜잭션으로 묶어 중복 부작용을 막는 방향을 검토할 수 있다.
외부 Slack의 성공 응답이 유실된 경우는 별도 문제다. 상대 API의 보장을 확인하지 않고 “알림 정확히 한 번”이라고 주장하지 않는다.

### 5. 이후 선택: 유한 재고와 동시성

시간이 더 확보되면 재고 예약 → 주문 확정 → 예약 해제 흐름을 추천한다. 수량 차감뿐 아니라 취소·재시도·중단을 포함한다.
예를 들어 재고 100개에 1개씩 주문 1,000건을 집중시킨 뒤 초과 판매·중복 차감·예약 누수를 검증한다. 이 수치는 실험 설계 예시이며 현재 성과가 아니다.
정상 조건에서는 확정 주문 수와 실제 차감 수가 일치해야 하고, 장애 조건에서는 미확정 예약까지 포함한 재고 보존 관계를 정의해야 한다.

한 상품 집중 부하와 여러 상품에 분산된 부하를 구분한다. 조건부 UPDATE·비관적 락·낙관적 락은 동일한 업무 불변식과 자원 조건에서 비교한다.
현재 SA의 다중 허브 재고 취합과 허브 ADR의 단일 공급 허브 제안은 전제가 다르다. 먼저 팀과 범위를 정하고, 하나의 방식이 이미 채택됐다고 간주하지 않는다.
이 범위는 상품·허브·주문·배송에 걸쳐 커질 수 있으므로 첫 복구 사례와 동시에 시작하지 않는 것을 추천한다.

### 6. 성능은 실제 병목 하나를 증명한다

데이터 크기·인덱스·검색 조건·하드웨어·컨테이너 제한·샘플링률을 고정하고 기준선을 측정한다.
현재 호출 흐름에서는 느린 하위 서비스와 재시도에 따른 자원 점유, 데이터가 커진 주문 검색 등을 후보로 삼되 병목은 측정 후 정한다.
개선 전후에는 성공 처리량, p95·p99, 오류율, DB 연결 대기나 락 대기 등 원인 지표를 함께 남긴다.

“동시 사용자 1,000명”은 “초당 1,000건”과 다르다. 요청 도착률을 유지하려면 부하 모델을 명시하고, 생성하지 못한 요청도 보고한다.
k6는 이전 반복 종료를 기다리는 closed 모델과 종료 여부에 독립적으로 시작하는 open 모델을 구분한다([공식 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)).
합성 데이터 실험은 실험 환경의 결과로 표시한다. 실제 고객 트래픽을 운영한 실적으로 표현하지 않는다.

### 7. 실행 순서와 산출물

| 순서 | 할 일 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 0 | 허브 간 경로 API·데이터와 전체 주문 흐름 완성 | 다른 허브 주문 생성·배송 상태 변경·취소의 실제 연동 증거 |
| 1 | 지연 생성·삭제 역전 실험 하나를 재현 | 현재 동작, 기대 불변식, 재현 스크립트와 데이터 확보 |
| 2 | 제공 서비스 계약과 결과 확인·복구 구현 | 같은 실험에서 안전한 종료를 확인하고 정상 주문 회귀도 통과 |
| 3 | 장애 관제·복구 지표·짧은 시연 | 다른 사람이 동일 환경에서 실패와 복구를 재현 가능 |
| 4 | 알림 Outbox 또는 실제 병목 하나 개선 | 선택 이유, 전후 비교, 보장 범위와 남은 한계 |
| 5 | 유한 재고 등 다음 도메인 확장 | 팀 설계 합의와 기존 복구·검증 기반 재사용 |

가장 작은 대표 사례는 순서 1~3이다. 전체 기능의 수보다 한 사례의 재현성·원인 설명·대안 비교·복구 근거를 먼저 완성한다.
첫 작업은 배송 생성이 늦게 끝나도록 제어하고 삭제를 먼저 실행하는 회귀 시나리오의 설계다.

포트폴리오에는 3분 안팎 시연, 재현 명령·시드, 핵심 코드 링크, 원인과 대안, 측정 결과를 묶는다.
팀 전체 결과와 본인의 설계·구현·검증 범위를 나눠 적고, 면접에서 격리 수준·트랜잭션 경계·실패 시점을 직접 설명할 수 있어야 한다.
시연 순서는 정상 주문 → 장애 주입 → 미확정 상태와 trace 확인 → 복구 → 최종 데이터 검증이다.

## 면접 포인트

- 타임아웃과 업무 실패는 어떻게 다른가? 원격 커밋 후 응답만 유실될 수 있어 실제 결과를 확인해야 한다.
- 삭제 API가 멱등한데 왜 늦은 생성 문제가 생기는가? 각각의 중복 처리 보장만으로 서로 다른 명령의 순서를 제어하지 못한다.
- 자동 복구를 언제 멈추는가? 원격 결과를 확인할 수 없거나 재실행 안전성을 증명하지 못하면 수동 확인 대상으로 남긴다.
- Outbox만 있으면 정확히 한 번 처리되는가? 전달 중복과 외부 시스템의 부작용까지 별도로 설계해야 한다.
- Kafka 없이 시작한 이유는 무엇인가? 현재 필요한 보장, 구현·운영 비용, 추후 필요한 소비·재생 요구를 비교해 설명한다.
- 성능 개선 수치를 어떻게 검증했는가? 동일한 자원·데이터·부하 모델에서 성공 처리량과 지연·오류·원인 지표를 비교한다.
