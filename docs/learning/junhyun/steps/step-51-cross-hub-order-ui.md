# 51. dev의 허브 경로 API 병합과 다른 허브 간 주문 화면 연동

- 날짜: 2026-10-16
- 브랜치: `feat/infra-monitoring-mentor-guide`
- 이전 작업 커밋: `36c6219 Merge remote-tracking branch 'origin/dev' into feat/infra-monitoring-mentor-guide`
- 이번 커밋 제목: `feat(ui): 다른 허브 간 주문 제한 해제와 멘토 가이드 갱신`
- 범위: 사용자 요청 "dev에 반영된 hub 관련 기능까지 현재 브랜치로 가져와줘", 이어서 가이드·화면 갱신 동의. hub PR #9(경로 272건 V3, H-03·H-04, I-03)를 병합한 뒤 화면과 멘토 가이드를 실제 동작에 맞췄다. hub 코드는 고치지 않았다.

## 바뀐 동작

- 새 주문 화면에서 서로 다른 허브의 업체를 고르면 주문을 막지 않는다.
  - 대신 "다른 허브 간 주문입니다. 배송은 공급업체 집하 → 허브 간 이동(출발 허브 → 도착 허브) → 수령업체 배송 3구간" 안내가 나온다.
- 멘토 가이드 변경:
  - "허브 간 이동정보" 시나리오: 경로 272개 조회, 출발·도착 허브 검색, 정렬
  - "발제 예시: 경기 → 부산" 시나리오: uimaster 주문 → uidrvgg 집하·허브 간 이동 → uidrvbs 업체 배송 → 배송 완료
  - "구현 대기" 카드 없음
  - "현재 범위"의 경로 미구현 항목을 "P2P 1구간, 중계 경로 없음"으로 바꿨다

## 확인한 실제 동작

| 확인 | 결과 |
|---|---|
| `GET /api/v1/hub-routes` | 200, 272건. 경기 북부 → 부산 443.02km·380분 |
| 개발 스택 HUB_A → HUB_B 주문 | 201, 3구간 생성 |
| 같은 주문의 허브 간 이동 구간 | 예상 52.13km·45분 |
| 구간 담당자 배정 | 집하·허브 간 이동은 출발 허브 담당자, 업체 배송은 도착 허브 담당자 |
| 허브 간 이동 도착 처리 | 실제 거리·소요시간 입력이 필수다(화면 필드가 required) |
| 다른 허브 담당자 | 자기 구간이 아니면 처리 버튼이 없다. 앞 구간이 도착해야 다음 구간이 출발한다 |

## 왜 이렇게 만들었는가

- **merge를 쓴 이유**: 이 브랜치는 푸시 전이지만, 커밋 이력을 다시 쓰지 않는 쪽이 안전하다. hub 파일과 겹치는 변경이 없어 충돌이 없었다.
- **서버 기능이 들어온 뒤에야 제한을 푼 이유**: ADR 0015 결정 6("미구현 I-03을 성공한 것으로 꾸미지 않는다")을 따랐다. 실제 주문·구간 처리를 확인하고 나서 바꿨다.
- **E2E 계정 전환을 주소 재방문으로 바꾼 이유**: 배송 상세는 다이얼로그다. 열려 있으면 배경이 접근성 트리에서 숨겨져 로그아웃 버튼을 찾지 못한다. 토큰이 메모리에만 있으므로 주소를 다시 열면 로그인 화면이 된다.
- **실제 거리·시간을 입력하게 한 이유**: 발제의 배송 경로 기록에 "예상/실제 거리 및 소요시간"이 있다. 허브 간 이동 도착 때 실제값을 받는 것이 서버·화면 계약이다. E2E와 가이드 절차에 이 단계를 넣었다.

## 검증 결과

- `./gradlew build`(병합 후): 테스트 766개 통과(hub 62개 포함), 실패 0. `script/docs-check.sh origin/dev` OK
- 프런트: build·lint·format 통과, 단위 테스트 46개 통과
- E2E(UI 테스트 스택, DM 꺼짐): 18개 모두 통과. 새 테스트 "발제 예시: 경기 → 부산 허브 간 주문…"이 생성·3구간·담당자별 처리·완료·삭제까지 확인한다
- 처음 두 번은 E2E가 실패했다(로그아웃 버튼 숨김, 실제 거리 필수 입력). 그때 남은 테스트 주문 3건은 관리자 API로 완료·취소 후 삭제했다
- 검증 뒤 `.env.ui-test`의 DM을 원래 값(true)으로 되돌렸다(백업과 동일 확인). UI 테스트 스택은 내렸고, 개발 스택은 원래 테스트 모드로 다시 올렸다

## 직접 해보기

1. `script/ui-test.sh up`과 `seed` 후 `frontend`를 실행한다. DM이 켜져 있으면 seed가 거부하므로 `.env.ui-test`의 `SLACK_DM_ENABLED=false`를 먼저 확인한다.
2. http://127.0.0.1:5174/guide 의 "발제 예시: 경기 업체 상품을 부산 업체로 배송한다" 카드에서 "uimaster로 시작"을 누른다.
3. 경기 건조식품 가공 → 부산 수산 도매, 마른오징어 가공품 50개로 주문한다. 배송 상세에 3구간과 "예상 443.02km · 380분"이 보이면 성공이다.
4. 가이드의 계정 표에서 uidrvgg로 시작해 같은 배송 주소를 열고, 집하·허브 간 이동을 처리한다. 허브 간 이동 도착 때 실제 거리·시간을 넣는다.
5. uidrvbs로 바꿔 업체 배송을 처리하고 "배송 완료"를 확인한다. uimaster로 주문을 삭제한다.

## 확인 질문

- 허브 간 이동 구간의 담당자는 왜 도착 허브가 아니라 출발 허브 소속인가(발제 "소속 허브는 출발지 기준")
- 화면 제한을 서버 기능보다 먼저 풀면 어떤 문제가 생기나
- feature 브랜치에 dev를 merge할 때와 rebase할 때의 차이는 무엇인가
