# 성능·안정성 실험 지도

이 문서는 성능·안정성 실험 후보 7개를 한곳에 모은 목록이다. 이력서·포트폴리오에 정량 결과로 쓰는 것이 목적이다. 시나리오마다 보여줄 역량, 코드 근거, 가설, 측정 지표, 이력서 문장 틀을 적었다. 실험 절차가 길어지는 시나리오는 상세 문서를 따로 두고 여기서 링크한다.

> 작성: 2026-10-16 (jihaneol). 코드 근거는 `feat/delivery-T06` 브랜치(모니터링 PR #10 반영 후) 기준이다. 아래 예상 수치는 코드와 설정으로 계산한 값이고, 실측은 각 시나리오의 결과 칸에 채운다.

## 원칙

1. **측정 → 하나만 바꾸기 → 같은 조건으로 다시 측정.** 둘을 같이 바꾸면 어느 쪽 효과인지 모른다.
2. **증거를 남긴다.** k6 결과 JSON, Grafana 캡처, `EXPLAIN` 출력, PR 링크. 숫자만 있고 증거가 없으면 면접에서 오히려 약점이 된다.
3. **절대 수치보다 전후 비율.** 맥 한 대에서 k6와 모든 서비스가 같이 돈다. 측정 환경(맥 모델, 메모리, Docker 할당)을 함께 적는다.
4. **내 기여를 정확히 쓴다.** Prometheus·Grafana는 팀원이 붙였다(ADR 0018). 나는 그것을 **써서** 문제를 찾고 고쳤다고 쓴다. 다른 서비스 코드를 바꾼 경우에는 협의 사실을 적는다.
5. **이력서에 올리는 코드는 직접 읽고 직접 짠다.** "왜 그 값인가"에 답하려면 코드를 알아야 한다. AI에게는 스크립트와 설정 같은 주변 작업을 맡긴다.

## 1. 장애 격리
- **문제(코드 근거):** user 호출 하나가 read 20초 × 재시도 3번으로 최악 약 60초 묶인다. 초당 20건이면 약 10초 만에 Tomcat 스레드 200개가 다 차서, user를 부르지 않는 D-01 조회까지 멈춘다.
- **실험:** 생성과 조회를 동시에 보내는 중에 `docker compose pause user-service`를 30초 건다. 그다음 타임아웃 → 재시도 정책 → 벌크헤드 → 서킷 브레이커 → 부분 저하 순서로 하나씩 넣는다.
- **지표:** k6 구간별(before/fault/recovery) p95·실패율, `tomcat_threads_busy_threads`, `hikaricp_connections_pending`, 서킷 상태, 복구 시간
- **상세:** [fault-isolation.md](../../../delivery-service/docs/fault-isolation.md). 절차, 통제(Gateway 캐시, Eureka 만료), 결과표, 이력서 문장 틀, 면접 질문이 모두 있다.

## 2. 재시도 증폭
- **문제:** order → delivery I-09 대기(20초)가 delivery → user 대기(최대 60초)보다 짧다. order가 포기하고 다시 보낸 요청이 delivery에서 겹쳐 돈다. 멱등이라 데이터는 안전하지만 일이 최대 3배가 된다.
- **지표:** delivery가 받은 I-09 수 ÷ order가 받은 O-01 수 (PromQL은 상세 문서 3절 5번)
- **이력서 틀:** 호출 사슬의 타임아웃 예산 불일치로 생긴 재시도 증폭(주문 1건당 하위 호출 __배)을 측정하고 1.0배로 줄임
- **상세:** fault-isolation.md S2, 7-F. order 설정 변경은 order 담당과 협의한다.

## 3. 원격 조회 캐시
- **문제(코드 근거):** `DeliveryCreationService.create`는 배송 1건마다 I-14 배송담당자(허브마다 1번), I-01 수령인, I-03 허브 경로(허브가 다를 때)를 차례로 부른다. I-03은 허브 17개 사이 경로(시드 272건)라 거의 바뀌지 않는다. I-14는 담당자 지정·해제 때만 바뀐다.
- **가설:** I-03을 긴 TTL로, I-14를 30~60초 TTL로 캐시하면 배송 1건당 원격 호출이 2~3번에서 거의 0번이 된다. 같은 p95 기준에서 받을 수 있는 최대 RPS가 오른다.
- **실험:**
  - 측정 대상: `load-test/k6/delivery-create.js`(`TARGET=delivery`)
  - 최대 처리량 정의: **p95 < 1초, 실패율 < 1%, `dropped_iterations` = 0을 지키는 가장 높은 `PEAK_RATE`**. 20 → 40 → 80 → 160으로 올려 가며 찾는다.
  - 주의: 지금 스크립트는 출발·도착이 같은 서울 허브라 I-03을 부르지 않는다. I-03 효과를 보려면 도착 허브를 경기 북부로 바꾼 변형이 필요하다(시드에 경기 북부 배송담당자 `dmgr3`이 있다). 두 허브 사이 경로가 시드에 있는지 먼저 확인한다.
- **지표:** I-09 p95, 최대 RPS, I-09 1건당 Feign 호출 수(`feign_client_requests_seconds_count` rate ÷ I-09 rate), 캐시 적중률(Caffeine `recordStats()`를 켜면 `cache_gets_total{result="hit"}`)
- **결정할 것(ADR감):**
  - 담당자를 해제해도 최대 TTL 동안은 배정될 수 있다. 이 지연을 받아들일지
  - 캐시를 어디에 둘지. Adapter 안에 직접 둘지(Gateway `CachedUserLookup` 방식), `@Cacheable`을 쓸지
  - 인스턴스를 늘리면 캐시가 인스턴스마다 따로 생기는데 괜찮은지(Redis와 비교)
- **이력서 틀:** 거의 바뀌지 않는 원격 조회를 로컬 캐시로 바꿔 배송 생성 1건당 내부 호출 __회 → __회, 최대 처리량 __ → __ RPS(p95 1초 이하 유지 기준)
- **면접 질문:** 캐시 데이터가 바뀌면? TTL은 어떻게 정했나? 같은 키를 동시에 조회하면(캐시 스탬피드)? 로컬 캐시와 Redis 중 왜 이것인가?

## 4. DB 인덱스
- **문제(코드 근거):** `V1__create_delivery_tables.sql`의 인덱스는 모두 단일 컬럼이다.
  - 담당 건수 쿼리(`countActiveRoutes`, I-09마다 실행): `manager_id IN (...) AND status IN ('WAITING','MOVING')`인데 `manager_id` 단일 인덱스라 이미 도착한 과거 구간까지 훑는다. 데이터가 쌓일수록 느려진다.
  - D-01 허브별 최신순: `departure_hub_id`로 거른 뒤 `created_at` 정렬을 따로 한다.
- **가설과 개선:**
  - 진행 중 구간만 담는 부분 인덱스 `ON p_delivery_routes (manager_id) WHERE status IN ('WAITING','MOVING') AND deleted_at IS NULL`
  - 복합 부분 인덱스 `ON p_deliveries (departure_hub_id, created_at DESC) WHERE deleted_at IS NULL`
  - Flyway V2 마이그레이션으로 넣는다.
- **실험:** `infra/postgres/seed/delivery-load.sql`로 30만 건과 100만 건을 넣는다. `EXPLAIN (ANALYZE, BUFFERS)` 쿼리는 load-test.md 5절에 있다. 같은 쿼리를 3번 돌려 중앙값을 쓴다(첫 실행은 디스크에서 읽어 느리다). API 수준은 `delivery-read.js`로 잰다.
- **지표:** Execution Time, `Buffers: shared hit/read`, `Rows Removed by Filter`, `Sort` 노드가 있는지, `Seq Scan`인지 `Index Scan`인지, D-01 p95, I-09 p95
- **선택:** 깊은 페이지 OFFSET과 커서(키셋) 페이지네이션 비교. 다만 응답 계약이 바뀌므로 SA 확인이 필요하다.
- **이력서 틀:** 30만(100만) 건 데이터에서 실행계획으로 병목 쿼리를 찾아 부분 인덱스를 설계, 실행 시간 __ms → __ms, 읽은 블록 __ → __, 목록 API p95 __ms → __ms
- **면접 질문:** 부분 인덱스는 언제 쓰나? 복합 인덱스의 컬럼 순서는 왜 그런가? 인덱스를 늘리면 쓰기는 얼마나 느려지나(INSERT p95도 같이 잰다)?

## 5. 동시 배정 쏠림
- **문제(코드 근거):** `ManagerAssigner`는 후보들의 담당 건수를 읽고 가장 적은 사람을 고른다. 잠금이 없다(결정 로그 16, 편차 "1~2건"으로 가정). 같은 허브에 동시에 N건이 들어오면 모두 같은 건수를 읽고 같은 사람을 고른다.
- **실험:** 같은 허브(서울, 담당자 2명)에 I-09를 50건 동시에 보낸다(k6 짧은 몰아치기 또는 `CountDownLatch` 통합 테스트). 끝나고 SQL로 담당자별 배정 수를 센다.
  - 담당자가 2명이면 편차가 잘 안 보일 수 있다. 시드에 서울 담당자를 5~10명 더 넣은 변형으로 잰다.
- **개선 후보(ADR감):**
  - 허브 단위 `pg_advisory_xact_lock`: 단순하다. 하지만 같은 허브 생성이 한 줄로 서서 처리량에 상한이 생긴다.
  - 담당자별 건수 테이블 + `SELECT ... ORDER BY count, user_id LIMIT 1 FOR UPDATE SKIP LOCKED`: 병렬로 서로 다른 사람에게 배정한다. 구간이 도착·취소될 때 건수를 줄이는 일이 함께 필요하다.
- **지표:** 담당자별 배정 수의 최대-최소 차이, 표준편차, 동시 생성 p95와 처리량(공정성과 처리량을 맞바꾼 정도)
- **이력서 틀:** 동시 요청 50건에서 작업 배정이 한 명에게 쏠리는 문제(편차 __건)를 재현하고 `SKIP LOCKED`로 편차 __건, 처리량 손실 __% 이내로 개선
- **참고:** 재고 차감 락 전략 비교(조건부 UPDATE, 비관적 락, 낙관적 락)도 좋은 주제다. 다만 2026-10-16 기준 저장소에 재고 차감 코드가 없다(hub ADR 0002 "제안" 상태). 개인 확장으로 따로 구현할 때만 후보로 둔다.

## 6. CI/CD 성능 게이트
- **현재:** 저장소에 Jenkinsfile이 없다. GitHub Actions는 `docs-guard.yml`(문서 검사)뿐이다. 인프라 설계(`docs/design/05-infra.md`)는 GitHub Actions를 계획하고 있다. Jenkins를 쓸지 팀과 먼저 맞춘다.
- **후보:**
  1. 바뀐 모듈만 빌드 + Gradle 빌드 캐시 + 병렬 실행: 전체 빌드·테스트 시간 전후
  2. Docker BuildKit 캐시로 멀티 모듈 이미지 빌드 시간 줄이기(junhyun 학습 노트 `docker-multistage-buildkit-cache` 참고)
  3. k6 스모크 테스트를 파이프라인 품질 기준(게이트)으로: `thresholds`를 넘으면 k6 종료 코드가 0이 아니어서 파이프라인이 실패한다. 4번 인덱스를 일부러 빼서 게이트가 회귀를 잡는지 시연한다.
- **지표:** 빌드 시간(같은 커밋으로 캐시 없음/있음 각 3번), 게이트가 잡은 회귀 사례
- **이력서 틀:** 변경 모듈 선택 빌드와 캐시로 CI 시간 __분 → __분, k6 성능 게이트로 p95 회귀를 배포 전에 차단
- **범위:** 공통 영역이라 팀 리뷰 대상이다. 2일 안에는 3번(게이트)만 해도 충분하다.

## 7. 장애 탐지 알림
- **현재:** `infra/grafana/provisioning/alerting`이 비어 있다. 대시보드는 있지만 알림이 없다. 인프라 설계에는 "Prometheus + Grafana + Slack 알림"이 계획(📝)으로 있다.
- **실험:**
  - Grafana 알림 규칙을 파일로 만든다(프로비저닝). 예: 서비스 5xx 비율 > 1%가 1분 지속, 외부 요청 p95 > 1초가 1분 지속.
  - 받는 곳은 Slack webhook(팀이 이미 쓴다)이나 로컬 테스트용 webhook으로 둔다.
  - 1번의 장애 주입을 그대로 다시 쓴다.
- **지표:** 장애 주입 시각부터 알림 도착까지 걸린 시간(MTTD). 수집 주기 + 평가 주기 + 지속 조건(for)으로 이론값을 먼저 계산하고 실측과 비교한다. 알림에서 Grafana 그래프의 예시(exemplar) traceId를 눌러 Zipkin으로 가서 원인 구간을 찾기까지의 흐름도 캡처한다.
- **이력서 틀:** 오류율·지연 알림을 코드로 관리(프로비저닝)하고, 장애 주입 실험에서 탐지 __초, 지표 → trace로 원인 구간 확인까지 __분
- **면접 질문:** 알림이 너무 자주 오면(알림 피로)? `for` 조건은 왜 1분인가? 평균이 아니라 p95·오류율로 알리는 이유는?

## 공통 측정 규칙
- 매 측정은 `script/run.sh --reset` 후 같은 데이터 상태에서 시작한다. 1번은 시드만, 3·4번은 대량 데이터까지 넣는다.
- 부하 테스트 중에는 추적 비율을 낮춘다(`.env` `TRACING_SAMPLING_PROBABILITY=0.1`).
- JVM 예열을 위해 처음 30~60초는 비교에서 뺀다. 평균은 쓰지 말고 p95/p99를 쓴다.
- 같은 조건으로 3번 재고 중앙값을 쓴다. `checks`가 100%가 아니거나 `dropped_iterations`가 0이 아닌 결과는 쓰지 않는다(1번 장애 구간은 예외).

### 1번 세부: 결정 사항
| 항목 | 값 | 이유 |
|---|---|---|
| 타임아웃(user·hub·company) | connect 1초, read 2초 | 평소 내부 조회는 수십 ms |
| 재시도 | 연결 실패만 1번 | 읽기 타임아웃 재시도는 스레드만 더 묶는다 |
| 벌크헤드(user) | 동시 10, 대기 0 | 평소 동시 호출 < 1(리틀의 법칙) |
| 서킷 브레이커(user) | 최근 10초, 최소 20건, 실패 50% 또는 1.5초 넘는 호출 80% | 처음 "최근 20건"은 초당 80요청에서 0.25초 분량이라 정상인데도 열리는 오탐(생성 19% 503). 바꾼 뒤 같은 부하에서 0.4%, 서킷 열림 없음 |
| 실패 처리 | 담당자 후보·재배정 확인은 503, 수령인 Slack ID는 없이 생성 | 대신할 값이 있는 것만 부분 저하 |

### 메시지 큐(Kafka)·Redis 판단
- 지금 측정한 문제는 동기 방식 안에서 풀린다. SA도 Kafka를 고도화로 미뤘다(ADR 0013 동기 Feign).
- 넣을 이유가 생기는 곳: 보상 실패 처리(지금은 3번 실패하면 로그만 남고 수동 처리) → DB 아웃박스 → Kafka 순서.
- Redis: 인스턴스가 하나라 로컬 캐시(Caffeine)로 충분하고 분산 락도 DB 잠금으로 해결된다. 인스턴스를 늘려 캐시를 공유해야 할 때 검토한다.
