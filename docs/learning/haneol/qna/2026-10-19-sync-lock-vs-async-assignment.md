# 배정에 잠금을 걸었더니 서비스가 멈췄다. 비동기로 바꾸면 같은 잠금인데 왜 괜찮나

## 질문
허브 단위 잠금으로 배정 편차는 없앴는데, 초당 40건이면 조회까지 실패했다. 배정을 주문 완료 뒤로 떼어 비동기로 하면 요청이 몰릴 때 문제가 없나? 5초 주기 작업도 대용량이면 병목이 되지 않나? 초당 40건은 대용량인가? 비동기도 try-lock을 쓰는데 왜 성능이 올라가나? 나중에 메시지 큐로 바꿀 수 있나?

## 짧은 답
- 동기 잠금의 문제는 잠금 자체보다 **요청이 잠금을 기다리며 DB 커넥션을 쥐는 것**이다. 기다리는 요청이 풀을 다 차지하면 잠금과 상관없는 조회까지 멈춘다.
- 비동기로 떼면 줄이 요청 처리 경로(스레드·커넥션) 밖, DB의 "배정 대기" 행에 생긴다. 몰려도 주문·조회는 정상이고 **배정만 늦어진다**(부하 평탄화).
- 같은 잠금이라도 잡는 주체가 주문 요청에서 허브별 배정 작업 하나로 바뀌고, 횟수는 주문마다에서 배치마다로 줄고, try-lock이라 기다리지 않는다. 잠금·쿼리·커밋 비용을 배치 안의 여러 건이 나눠 낸다.
- 주기 작업은 5초에 1건이 아니라 5초 동안 쌓인 것을 한 번에 처리한다. 약점은 처리량보다 지연이다.
- 허브 하나에 초당 40건은 하루 약 345만 건으로, 이 서비스(B2B 허브 물류)에는 비현실적으로 크다. 이번 측정은 요구 처리량이 아니라 스트레스 테스트였고, 보여 줄 것은 "한계를 넘을 때 어떻게 무너지나"다.
- 깨우는 쪽(트리거)과 배정하는 쪽(`assignPending`)을 나누면 깨우는 쪽만 메시지 큐로 바꿀 수 있다. Kafka에서 키를 허브로 두면 같은 허브는 소비자 하나가 순서대로 처리해 잠금이 필요 없어진다.

## 자세히

### 1. 측정으로 본 흐름
| 단계 | 결과 |
|---|---|
| 잠금 없음, 동시 50건 | 담당 건수 `[0, 50, 0, 50, 0]` (모두 같은 건수를 읽고 같은 사람을 고름) |
| 허브 advisory lock, 동시 50건 | `[20, 20, 20, 20, 20]`, 처리 1,270ms → 3,091ms (잠금 구간 건당 약 36ms) |
| 허브 lock, k6 같은 허브 생성 40/s + 조회 40/s | 30초 안에 생성·조회 0%, 커넥션 10/10·대기 187, postgres CPU 41% |
| 잠금 전 같은 부하 | 생성 p95 140ms, 실패 0.4% |

잠금 구간이 36ms면 허브 하나는 초당 약 28건까지만 처리한다. 들어오는 양이 이보다 많으면 줄이 계속 길어지고, 줄 선 요청이 커넥션을 쥐고 있어 다른 API까지 멈춘다.

> 정정(2026-10-20, 결정 로그 28): 위 표의 k6 결과와 28건 상한은 같은 절차 재측정에서 재현되지 않았다. 36ms는 통합 테스트 처리 시간에서 거꾸로 계산한 추정이었다. 다시 잰 단계는 (1) 생성+조회 160+160에서 D-01 조회 병목(건당 33ms) → 복합 인덱스, (2) 조회를 고정하고 생성만 올리자 동기 잠금이 240/초에서 무너짐(커넥션 10개 중 8~9개가 advisory lock 대기) → 배정 분리 뒤 640/초 통과다. "줄 선 요청이 커넥션을 쥐어 다른 API까지 멈춘다"는 구조는 맞았고 숫자가 틀렸다. 숫자는 추정이 아니라 같은 조건 2회 측정으로 정해야 한다.

### 2. 무엇이 쌓이나
| | 동기 배정 | 비동기 배치 배정 |
|---|---|---|
| 몰릴 때 쌓이는 곳 | Tomcat 스레드와 DB 커넥션 | DB의 배정 대기 행 |
| 결과 | 생성·조회 타임아웃 | 배정 지연만 늘어남 |
| 쓰는 자원 | 요청 수만큼 | 허브당 작업 하나의 고정량 |

### 3. 배치가 빠른 이유
```
동기: (잠금 + 건수 쿼리 + 저장 + 커밋) × 500건
배치:  잠금 1번 + 건수 쿼리 1번 + 500건 갱신 + 커밋 1번
```
고르는 계산은 메모리에서 하므로 거의 비용이 없다. 실제 이득은 측정으로 확인한다.

### 4. try-lock의 함정: 빠지는 건
작업 A가 대기 건을 읽은 뒤 들어온 주문은 깨우기 요청이 try-lock에 실패해 그냥 끝날 수 있다. A는 그 주문을 모른 채 커밋한다. 막는 방법은 두 가지다. 작업이 커밋 뒤 대기 건을 다시 확인하고, 주기 작업이 남은 대기를 줍는다. 이 순서를 일부러 만드는 테스트를 둔다.

### 5. 메시지 큐로 가는 길
- 1단계는 DB를 대기열로 쓴다. 배송 저장과 대기 표시가 한 트랜잭션이라 메시지 유실이 없다.
- 3단계에서 Kafka로 바꿀 때는 "배송 저장"과 "메시지 발행"을 함께 성공시키려고 아웃박스 테이블을 쓴다.
- 파티션 키를 허브로 두면 허브별 순서 처리가 구조로 보장되고, 인스턴스를 늘리면 파티션을 나눠 맡는다.

## 확인 질문
- 동기 잠금에서 "잠금을 기다리는 요청"이 왜 잠금과 상관없는 조회를 멈추게 하나?
- try-lock을 실패한 깨우기 요청이 그냥 끝나도 되는 조건은 무엇이고, 그 조건이 깨지는 순서는?
- 배치 크기를 키우면 무엇이 좋아지고 무엇이 나빠지나(트랜잭션 길이, 지연)?
- Kafka 파티션 키를 허브로 두면 왜 허브 잠금이 필요 없어지나? 허브 하나에 몰리면 무슨 일이 생기나?
