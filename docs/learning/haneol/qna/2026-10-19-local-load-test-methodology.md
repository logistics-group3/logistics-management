# 맥 한 대에서 부하 테스트를 할 때 무엇을 통제하고, 성능 개선을 어떤 숫자로 말해야 하나

## 질문
맥 자원이 부족해서 터지면 서버를 늘려도 이 맥에서는 터지지 않나? 맥 자원을 넘지 않게 측정해서 안전하게 성능을 높이려면 어떻게 하나? 왜 RPS라고 하고 TPS는 안 보나? 관련 없는 서비스를 끄면 되나?

## 짧은 답
- 같은 맥 안에서 인스턴스를 늘리면 CPU를 나눠 쓸 뿐이고 JVM이 늘어나 더 빨리 터질 수 있다. 수평 확장은 늘어난 인스턴스가 자기 몫의 자원을 받을 때만 효과가 있다.
- 로컬에서는 "더 많이 받기"가 아니라 "같은 자원으로 더 많이 받기"(효율)를 보여 준다. 한계점을 먼저 찾고, 실험은 그 아래에서, 결과는 비율·자원 대비·요청당 비용으로 말한다.
- RPS는 초당 HTTP 요청, TPS는 초당 처리 단위다. 요청 1개가 업무 1건이면 같고, 주문처럼 내부 요청이 여러 개면 다르다. 이력서에는 "배송 생성 TPS"처럼 단위를 붙인다.
- 놀고 있는 서비스는 CPU를 거의 쓰지 않아 꺼도 효과가 작았다. 진짜 문제는 예열되지 않은 JVM이었다.

## 자세히

### 1. 측정 대상이 먼저 한계에 닿게 한다
맥 전체가 먼저 바닥나면 어디가 병목인지 모른다. 측정 대상(delivery)에 CPU·메모리 상한을 걸면 조건이 반복 가능해지고 "CPU 1코어에서 최대 __ TPS"처럼 자원 대비로 말할 수 있다.

### 2. 한계점(knee)을 먼저 찾는다
속도를 단계적으로 올려 p95가 꺾이고 커넥션 대기가 생기는 지점을 찾는다. 장애 격리처럼 "장애 때문에 무너지는 것"을 보려면 평소에는 여유가 있어야 하므로 한계의 절반 정도로 잰다. 처리량 개선은 한계점 자체가 측정값이다. 인덱스는 부하 없이 `EXPLAIN (ANALYZE, BUFFERS)`로 본다.

### 3. JVM 예열을 통제한다
JIT 컴파일러는 자주 실행되는 코드를 실행 중에 기계어로 바꾼다. 기동 직후 몇 분은 이 컴파일에 CPU를 쓰고 같은 요청도 느리다. `docker compose up`으로 컨테이너를 다시 만들면 예열이 사라진다.

### 4. 숫자를 환경에 덜 의존하게 말한다
- 비율: 장애 중 조회 실패율 90% → 0%
- 자원 대비: 같은 CPU 1코어 제한에서 최대 처리량 2배
- 요청당 비용: 요청당 원격 호출 4회 → 1회, 요청당 DB 커넥션 획득 2회 → 1회

### 5. RPS와 TPS
| 용어 | 세는 것 | 주로 쓰는 곳 |
|---|---|---|
| RPS | 초당 HTTP 요청 | k6, Gatling (`http_reqs` rate) |
| TPS | 초당 처리 단위(정의하기 나름) | nGrinder, JMeter, 국내 성능 테스트 보고서 |
| DB TPS | 초당 DB 트랜잭션 커밋 | PostgreSQL `pg_stat_database.xact_commit` |
TPS는 성공한 요청만 센다. 실패까지 센 `http_reqs` rate와 다르다.

## 이 프로젝트에서는
2026-10-19 측정(맥북 에어, Docker CPU 8·메모리 7.8GiB, JVM `-Xmx384m`, 장애 없음, 각 1분):

| 실행 | 속도 | 생성 p95 | delivery CPU |
|---|---|---|---|
| 재기동 후 첫 실행 | 10+10 | 2,151ms | 227% |
| 바로 다음 실행 | 10+10 | 1,433ms | 20% |
| 그다음 | 20+20 | 539ms | 123% |

- 같은 속도에서 CPU가 10배 차이 났다. GC는 누적 0.6초, 힙 사용 30% 이하라 원인이 아니었다(힙 부족 가설 기각).
- 예열 없이 초당 20+20을 넣은 실행은 커넥션 풀(10개)이 바닥나 대기 157건, 모든 요청이 10초 타임아웃이었다(TS-028).
- 그래서 측정 방식을 바꿨다: 같은 속도로 2번 이상 예열, 측정 사이에는 `load-test/reset-delivery-data.sh`로 배송 테이블만 비움, 본 측정은 초당 10+10.
- 놀고 있는 grafana·order·company·hub는 측정 중 CPU 0~2%였다. zipkin은 끄면 서비스가 구간 전송 실패 경고를 남기므로 끄려면 추적 비율도 0으로 낮춘다.

## 면접 포인트
- "로컬에서 잰 숫자를 믿을 수 있나?" → 절대값이 아니라 같은 조건의 전후 비율과 자원 대비 지표로 말한다. 예열, 데이터 상태, 속도, 자원 상한을 통제했고 서버 지표(CPU, 커넥션 풀, GC)를 함께 남겼다.
- "응답이 느릴 때 서버를 늘리면 되나?" → 자원이 늘어나는 확장인지 먼저 본다. 같은 호스트에서 인스턴스만 늘리면 자원을 나눠 쓴다. 요청당 비용을 줄이는 개선(캐시, 인덱스, 풀 크기)은 어디서든 효과가 있다.
- "부하 테스트 첫 결과가 나쁠 때 무엇부터 보나?" → 예열 상태, 실패 응답의 종류, 서버 자원(CPU·커넥션 풀·스레드·GC). 클라이언트 타임아웃만으로는 원인을 알 수 없다.
