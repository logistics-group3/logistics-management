# 0001. 입고 진입점: company-service가 받아 hub에 반영

- 상태: 제안
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-07, 원문 상태 "확정". 본문은 원문 문장을 그대로 옮겼다
- SA v2.0과의 차이: 원문은 입고를 company의 새 API(P-06)로 받아 hub 내부 API로 반영한다. SA v2.0은 입고를 hub의 H-06(고도화)로 둔다.

## 맥락
- 입고 권한을 확인하려면 "이 사용자가 이 상품 업체의 관리자인가"와 "업체의 소속 허브"를 알아야 합니다. 둘 다 company의 데이터입니다.
- 한편 company는 이미 업체 생성 때 허브 존재를 확인하려고 hub를 부릅니다(company → hub).
- SA와 다른 부분은 서비스 담당자가 채택 여부를 결정한다.

## 결정
입고는 공급업체 관리자 본인과 MASTER만 할 수 있습니다. 요청은 상품의 하위 리소스인 `POST /api/v1/companies/{companyId}/products/{productId}/stocks/inbound`(P-06)로 company-service가 받고, 권한을 확인한 뒤 hub 내부 API(I-04)로 재고를 올립니다.

## 검토한 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| hub가 받고 company에 권한 물어보기 (원본 H-06) | 재고 API가 hub에 모임 | hub → company 호출이 생겨 company ↔ hub 순환 의존 |
| hub가 받고 MASTER만 허용 | 호출 없이 단순 | 업체가 자기 상품을 입고할 수 없어 도메인과 어긋남 |
| **company가 받고 hub에 반영 (채택)** | 권한 데이터가 있는 곳에서 확인, 호출 방향 유지 | 재고 쓰기 API가 company와 hub 두 곳에 나뉠 |

## 결과
### 이유
- 권한 판단에 필요한 데이터(업체 관리자, 상품 소속, 업체 허브)가 모두 company에 있습니다. 데이터가 있는 곳에서 판단하면 추가 호출이 없습니다.
- hub를 "다른 서비스를 부르지 않는 최하위"로 유지합니다. 순환 의존이 생기면 한쪽 장애가 다른 쪽을 다시 끌어내리고, 배포 순서도 꼬입니다.
- URL이 "이 업체의 이 상품을 입고한다"라는 업무 언어와 같아, 권한 규칙도 경로만 보고 알 수 있습니다.
- 삭제된 상품은 company에서 먼저 404로 막히므로 hub는 상품 상태를 몰라도 됩니다.

### 트레이드오프
- 재고 읽기(H-05)는 hub, 쓰기 중 입고(P-06)는 company에 있어 API 위치가 나뉩니다. 문서에 이유를 남겨 혼동을 줄입니다.
- hub의 I-04는 권한을 다시 확인하지 않고 company를 믿습니다. 내부 API는 Gateway 라우팅이 없어 외부에서 부를 수 없다는 전제입니다.

## 면접 답변
> "입고 권한을 판단할 데이터가 company에 있어서 company가 요청을 받고 hub에 반영합니다. hub가 받으면 hub → company 호출이 생겨 순환 의존이 되기 때문에, 호출 방향을 한쪽으로 지키는 쪽을 골랐습니다."
- **Q. 순환 의존이 왜 문제인가요?** A가 B를 부르고 B가 A를 부르면, 한 요청이 두 서비스 스레드를 서로 기다리게 만들 수 있고 한쪽 장애가 양쪽으로 퍼집니다. 또 두 서비스를 따로 배포·테스트하기 어렵습니다.
