# 주문 연동 담당자를 위한 실패 계약과 확인 항목

- 기준일: 2026-10-15
- 대상: company·delivery 구현자, 공통 예외 처리·Gateway 유지보수 담당자
- 정본: [SA](../../SA/sparta-logistics-sa.md) 6.3·7장. 이 문서는 현재 주문 코드의 기대 동작과 미확정 사항을 연결한다.
- 검증 범위: 주문의 실제 HTTP·Feign·PostgreSQL 테스트. 팀 company·delivery의 실제 업무 구현과의 연동은 아직 미확인이다.

## PR 준비 시 최신 dev와 대조한 결과

2026-10-15의 dev `df419a4`에는 user·company·delivery와 허브 조회·I-02 구현이 반영됐다. I-07·I-08 응답 필드와 정수 원화 가격, I-09 요청 필드, I-09~I-12 결과의 deliveryId·orderId·status, I-13의 204는 주문 어댑터와 정적으로 대조했다.
user I-14와 hub I-02는 dev에 있다. hub I-03 Controller는 해당 dev에 아직 없다. 같은 허브 주문은 I-03을 생략하므로 먼저 연동할 수 있고, 서로 다른 허브의 주문에는 I-03 구현·경로 데이터가 필요하다. 배송담당자·업체·상품 데이터도 함께 준비한다. 전체 모듈 테스트와 서비스 간 실제 호출 검증은 구분한다.

배송의 I-11·D-05는 로컬 트랜잭션에서 동일 Entity 상태를 읽고 바꾼다. 현재 DeliveryRepository·DeliveryJpaRepository와 Delivery에서 행 잠금·버전 필드는 확인되지 않아, 집하 시작과 취소의 동시 요청에서 제공자의 상태 전이 보호를 검증해야 한다.
이 항목은 DELIVERY-001에 추가 확인으로 남겼다. 주문의 잠금만으로 배송 서비스 내부 경쟁까지 보호한다고 가정하지 않는다. 지연 I-09와 I-13의 순서 역전은 계속 DELIVERY-002의 미확정 계약이다.

## 먼저 알아야 할 원칙

**4xx 거절, 5xx, 타임아웃은 같은 의미가 아니다.** 주문은 제공 서비스의 명확한 4xx를 변경 전 거절로 취급한다.
제공 서비스가 상태를 바꾼 뒤 4xx를 반환하면 보상이 생략될 수 있으므로, 실패 시 로컬 트랜잭션을 롤백한 뒤 공통 오류 응답을 반환해야 한다.
5xx·응답 없음·잘못된 성공 본문은 변경 여부를 모르는 결과로 취급한다.

- 내부 성공 응답은 ApiResponse로 감싸지 않은 DTO다([ADR 0010](../../decisions/0010-internal-api-unwrapped-response.md)).
- 오류 응답은 공통 ErrorResponse 형식이며 code·message가 필요하다. 하위 4xx 코드는 주문 응답까지 유지된다.
- X-User-*는 공통 FeignHeaderInterceptor가 전달한다. 제공 서비스는 공통 Audit를 사용해 원래 호출 사용자를 기록한다.
- 원격 호출 자체를 로컬 DB 롤백으로 되돌릴 수 없다. 주문은 성공한 앞 단계를 별도 보상 API로 되돌린다.
- 주문에서 500·503을 반환했더라도 원격 변경이 없었다고 단정하지 않는다. 재호출 전에 진행 기록과 실제 상태를 확인한다.

## company 담당자

| API | 주문이 사용하는 계약 | 실패 시 주문 처리 |
|---|---|---|
| I-07 GET /internal/companies/{companyId} | companyId·name·hubId·address·managerId | 명확한 4xx는 그대로 반환, 배송 호출 없음 |
| I-08 GET /internal/products/{productId} | productId·companyId·name·price | 명확한 4xx는 그대로 반환, 배송 호출 없음 |

가격은 0 이상인 정수 원화다. 누락과 0원을 구분하고, 소수 가격을 조용히 잘라 쓰지 않는다. 상품 ID·소속 업체·필수 텍스트도 주문 어댑터에서 확인한다.
두 GET은 응답 없는 통신 실패에 최대 3회 호출할 수 있다. 5xx 응답은 재시도하지 않는다.
새 키의 조회·권한 검증은 생성 진행 기록과 I-09 호출보다 앞에 있다. 거절된 조회 때문에 배송·생성 진행 기록이 만들어지지 않아야 한다. 완료된 같은 키의 재요청에는 회사 조회를 반복하지 않는다.

|---|---|---|
| I-09 POST /internal/deliveries | 같은 orderId의 생성이 중복되지 않음. 성공 응답에 deliveryId | 같은 orderId로 통신 실패 최대 3회. 성공 ID 누락·본문 오류는 미확정 처리 |

| I-12 POST /internal/deliveries/{deliveryId}/cancel-revert | 취소 전 상태로 원복. 이미 원복된 같은 요청은 no-op | 통신 실패 최대 3회, 5xx는 1회. 현재 주문은 성공 응답 본문을 사용하지 않음 |

| I-10 GET /internal/deliveries/{deliveryId} | deliveryId·orderId·status | 새 ORDERED 주문 삭제에서 ID 일치·DELIVERED 확인. 통신 실패 최대 3회, 5xx는 1회 |

I-11이 이미 CANCELED일 때 200을 반환하는 서버 멱등성과, 주문이 자동 재시도하지 않는 정책은 별개다. 현재 호출 정책은 SA 3.5를 따른다.
I-09·I-13은 orderId 기준, I-11·I-12는 deliveryId 기준이다. 재시도마다 다른 ID를 발급하지 않는다.

### 생성에서 주의할 순서 역전

`I-09 처리 중 → 주문에서 타임아웃 → I-13이 없음으로 204 → 지연된 I-09 생성 완료` 순서가 가능하다.
따라서 주문은 SA 7.1의 I-13 보상을 시도하되, I-09 결과가 불확실하면 삭제 성공 후에도 RECOVERY_REQUIRED를 유지한다.
I-13의 204만으로 지연 I-09가 끝났다고 판단하지 않는다.

같은 orderId의 늦은 생성·재시도를 종료 표시로 차단할지, 시도 토큰으로 처리할지는 **미확정**이다. 기존 API가 이 보장까지 제공한다고 가정하지 않는다.
삭제 이력을 포함한 멱등키 수명과 요청 순서 역전 정책은 [DELIVERY-002](../delivery/README.md#delivery-002-지연-생성과-삭제의-순서-역전-방지-계약-검토)에 질문으로 남겼다.

## 주문이 보관하는 진행 기록

| 기록 | 언제 생기는가 | 완료 기준 |
|---|---|---|
| p_order_creations | 업체·상품·권한 검증 후, I-09 호출 전 | 주문 행과 COMPLETED를 같은 커밋으로 확정 |
| p_order_cancellations | 주문·권한·상태 검증 후, I-11 호출 전 | 주문 CANCELED와 COMPLETED를 같은 커밋으로 확정 |
| p_order_deletions | MASTER 권한·취소/배송 완료·미해결 취소 없음 확인 후, I-13 호출 전 | 주문 논리 삭제와 COMPLETED를 같은 커밋으로 확정 |

PROCESSING은 아직 최종 결과를 기록하지 못한 상태다. RECOVERY_REQUIRED는 배송 결과·커밋 결과·보상 결과의 추가 확인이 필요하다는 뜻이다.
두 상태를 시간만으로 만료시키거나 다른 서비스가 주문 DB를 직접 갱신하지 않는다. 생성·취소의 미확정 기록 종료에는 실제 상태에 대한 주문 담당자의 확인과 별도 복구 유스케이스가 필요하다.
생성·취소의 운영 복구 API는 없으며 확인 쿼리·판단 순서는 [실패 처리 설계](failure-handling.md)에 있다. 삭제는 아래의 같은 DELETE 재요청으로 진행할 수 있다.

생성 기록은 주문 행이 없어도 존재한다. 이전 버전에서 생성한 주문에 기록이 없다고 미완료 주문으로 판단하지 않는다.
V4부터 생성 기록에 외부 키·요청 지문·최초 응답을 저장한다. 기존 키 없는 기록에는 값을 역으로 채우지 않는다.

## O-01 호출자·Gateway 담당자: 필수 멱등키

`POST /api/v1/orders`는 `Idempotency-Key` 헤더가 필수다. UUID를 권장하며 1~128자 영문·숫자·`.`·`_`·`:`·`-`를 허용한다. 누락·빈 값·형식 위반은 400 VALIDATION_ERROR다.
Gateway는 헤더를 주문 서비스까지 그대로 전달한다. 키 범위는 인증 사용자 ID이며 다른 사용자의 같은 키와 충돌하지 않는다. 내부 배송 I-09의 멱등키는 계속 orderId다.

| 재요청 조건 | 호출자 처리 |
|---|---|
| 응답 유실·통신 오류 | 같은 키·같은 본문으로 결과를 재확인. HTTP 재시도마다 키를 만들지 않음 |
| 같은 키·본문, COMPLETED | 201과 최초 생성 응답. 회사·배송 재호출 및 주문·알림 재생성 없음 |
| 같은 키, 다른 유효한 본문 | 409 ORDER_IDEMPOTENCY_KEY_CONFLICT. 이미 사용한 키를 수정 주문에 재사용하지 않음 |
| PROCESSING | 409 ORDER_CREATION_IN_PROGRESS. 간격을 두고 같은 키로 확인, 새 키로 우회하지 않음 |
| ABORTED | 409 ORDER_CREATION_ABORTED. 원인 해결 후 별도 새 주문을 시도할 때만 새 키 사용 |
| RECOVERY_REQUIRED·기록 논리 삭제 | 409 ORDER_CREATION_RECOVERY_REQUIRED. 주문 담당자가 기존 결과를 확인, 새 키로 우회하지 않음 |

헤더·본문 검증은 재요청에도 적용한다. 키가 없던 최초 요청의 업체·상품·권한 검증 실패는 키를 소비하지 않지만, 생성 기록을 커밋한 키는 실패 종료돼도 재사용하지 않는다.
키에는 자동 만료가 없다. 주문 수정·취소·논리 삭제 뒤에도 완료 응답은 원래 생성 스냅샷이다. 현재 주문은 O-03에서 조회한다. 생성 기록 조회·자동 복구 API는 후속 범위다.
판단 근거와 동시 요청 처리는 [ADR 0008](decisions/0008-order-idempotency-key.md), 실패 분류는 [예외 설계](failure-handling.md)를 따른다.

## O-06 삭제 재요청과 delivery의 보장

MASTER의 `DELETE /api/v1/orders/{orderId}`는 200·data=null이다. 새 ORDERED 주문은 I-10의 두 ID 일치와 DELIVERED가 필요하고, 주문 자체가 CANCELED이면 조회를 생략한다. I-10의 404는 최초 삭제 허가가 아니다.
I-13은 배송과 구간을 함께 논리 삭제하고, 이미 삭제·없는 orderId도 204를 반환해야 한다. 이전 I-13 성공 뒤 주문 DB가 롤백된 경우에도 같은 orderId의 I-13을 안전하게 반복할 수 있어야 한다.
주문 어댑터는 정확한 204를 완료로 확인한다. 200·202 등 다른 2xx는 미확정 결과로 처리해 503을 반환한다. 이 확인은 기존 생성 실패 보상의 I-13에도 적용되며 호출 횟수 정책은 유지한다.

주문은 I-13 전에 삭제 허가 근거를 기록한다. 실패 후 같은 DELETE는 그 기록을 사용해 이어가므로, 삭제된 배송을 I-10에서 다시 반환하도록 제공 계약을 바꾸지 않는다.
삭제는 종료 상태로 수렴하는 같은 동작을 계속하는 경우라 생성·취소의 새 시도와 다르다. 진행 기록을 시간만으로 해제하거나 새 주문을 생성하는 기능은 아니다.
SA 7.5에 따라 I-13 중 주문 잠금·로컬 트랜잭션을 유지한다. O-06은 요청당 I-13을 1회 호출해 잠금 안의 재시도를 중첩하지 않으며, 실패 시 MASTER가 같은 주문 삭제를 재요청한다.
삭제 진행 중에는 새 취소를 차단한다. 이미 로컬 삭제가 완료된 주문의 새 요청은 404이며, 같은 호출 안에서 커밋을 재확인한 경우에는 200을 유지한다.

## 팀 연동 때 함께 확인할 시나리오

| 시나리오 | 확인할 결과 |
|---|---|
| 상품·업체 없음, 배송담당자 없음 | 원래 4xx 코드 유지, 변경 데이터 없음 |
| 동일 orderId로 I-09 동시 요청·타임아웃 재시도 | 하나의 배송과 같은 deliveryId |
| 집하 시작과 I-11 동시 요청 | delivery에서 한쪽 상태 전이만 성공 |
| I-11 성공 후 주문 DB 롤백 | I-12로 배송·구간이 함께 원복 |
| I-12 응답 유실 후 같은 요청 | 중복 원복 부작용 없음 |
| I-13 반복 호출, 없는 주문 ID | 204이며 다른 배송에 영향 없음 |
| I-09 응답 지연·I-13 선행 | 지연 생성 처리 정책을 확인하고 미해결 결과를 복구 대상으로 식별 |
| 주문 커밋 완료 후 반환 경계 예외 | 주문 보존, I-13 없음, 생성 이벤트 재발행 없음 |
| O-01 같은 사용자·키·본문 동시 요청 | 하나의 주문·배송 실행. 다른 요청은 최초 201 또는 처리 중 409 |
| O-01 응답 유실 뒤 같은 키·본문 재요청 | 최초 응답 201, 회사·배송·생성 이벤트 재실행 없음 |
| O-06 I-13 성공 뒤 주문 DB 롤백 | 삭제 허가 기록 유지. 같은 DELETE는 I-10 없이 I-13을 반복하고 주문 삭제 완료 |
| O-06 실패·응답 유실 후 I-13 반복 | 이미 삭제·없음도 204, 다른 주문·배송에 영향 없음 |

주문 측 재현은 `./gradlew :order-service:test --tests '*OrderCreation*' --tests '*OrderIdempotency*' --tests '*OrderHttpIntegrationTest' --tests '*OrderCancellation*'`로 시작한다.
외부 서비스 대역 테스트의 성공을 제공 서비스 실제 구현 검증으로 표시하지 않는다. 담당자의 구현·실제 연동 결과를 협업 로그에 추가한다.

## 진행 중인 협업 기록

### 커밋 후 DM 확장 (ADR 0016, 2026-10-16)

I-15는 `{deliveryId, orderId, status, managerIds}`를, I-16은 `{userId, isDeliveryManager, slackEmail}`을 감싸지 않고 반환한다. 기존 I-10 응답과 I-01·I-14 필드 구성은 유지한다.

신규 가입 화면·U-01은 필수 slackEmail만 받도록 사용자의 후속 요청을 반영했다. 기존 I-01·I-14의 필드 구성은 유지하지만 신규 사용자의 slackId는 null이다. delivery는 수령인 ID 없음과 배정 후보 ID 조회를 구분해야 하며, DM은 I-16의 이메일을 사용한다. user V2/V3와 U-01 요청 변경을 함께 반영한다.
order는 배송·주문 연결을 검증하고 활성 구간의 담당자에게만 발송을 시도한다. 내부 API 실패·Slack 실패는 커밋 후 알림 실패로 기록하며 O-01 응답·배송 보상으로 전파하지 않는다.
실제 같은 허브 경로의 연동은 확인했다. 제공 담당자의 팀 리뷰, 다른 허브 I-03, 동시 재배정·취소와 발송의 원자성, Outbox 보장은 별도다. [설정·실패 표](../../guides/slack-dm.md), USER-002·DELIVERY-003을 함께 확인한다.

- [COMPANY-001](../company/README.md#company-001-주문-연동용-조회-응답과-오류-계약-확인): 기존 I-07·I-08 구현·연동 확인 요청.
- [DELIVERY-001](../delivery/README.md#delivery-001-주문-saga의-내부-api와-실패-계약-연동-확인): 기존 I-09·I-11·I-12·I-13 구현·연동 확인 요청.
- [DELIVERY-002](../delivery/README.md#delivery-002-지연-생성과-삭제의-순서-역전-방지-계약-검토): 추가 정책 검토, 아직 합의되지 않음.

현재 주문 보강은 기존 SA와 대역 테스트를 기준으로 진행할 수 있다. 위 요청은 실제 서비스 연동과 추가 자동 복구 보장을 확인하기 위한 것이며, 다른 서비스의 결정으로 임의 표시하지 않는다.
