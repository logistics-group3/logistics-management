## O-01 커밋 후 배송담당자 Slack DM (2026-10-16)

### 처리 과정
- OrderCreatedEvent에 deliveryId를 추가했다. 기존 커밋과 멱등성 경계는 유지하고 별도 AFTER_COMMIT 리스너가 AsyncDeliveryManagerDmSender에 맡긴다.
- DeliveryManagerDmService는 I-15 담당자 → I-16 이메일 → SlackDirectMessageGateway 순서로 처리한다. NotificationDirectoryAdapter가 Feign을 연결하고 SlackDmClient가 Slack Web API를 호출한다.
- SlackDmClient는 이메일 조회 → DM 열기 → 메시지 발송을 하고 HTTP와 JSON ok·채널·ts를 확인한다. Bot Token·워크스페이스·허용 목록은 서버 설정으로 받는다.

### 핵심
- 커밋 전에 보내면 롤백된 주문을 알릴 수 있다. 비동기로 넘기면 Slack 지연이 주문 응답·DB 트랜잭션을 붙잡지 않는다.
- 원격 호출을 application 포트 뒤에 둬 업무 규칙과 인증·HTTP 응답 형식을 분리한다.
- 같은 이벤트의 담당자·이메일은 한 번만 시도한다. HTTP 200의 ok=false도 실패이며, 응답 유실 후 재전송은 중복 메시지를 만들 수 있어 Slack POST는 자동 반복하지 않는다.
- 실패는 이미 생성된 주문과 분리한다. 큐는 메모리이므로 재시작 후 발송 보장은 없으며 Outbox는 후속 범위다.

### 확인 질문
- 주문 응답 201과 SLACK_DM_SENT는 각각 무엇을 확인한 결과인가?
- 주문 멱등키가 있어도 프로세스 재시작까지 알림을 보장하지 못하는 이유는 무엇인가?

### 메모
- 주문 451개·전체 727개 테스트, 실제 Gateway→delivery→user→Slack 접수 1건을 확인했다. 검증·팀 계약은 [실행 안내](../../guides/slack-dm.md)에 연결했다.

## O-02 주문 검색·O-03 단건 조회 (2026-10-15)

### 처리 과정

1. Slack 실제 연동 기록을 사용자 요청에 따라 `af0ba34`로 커밋했다.
2. OrderQueryService와 검색 조건·저장소 계약, QueryDSL 구현, ORDER_NOT_FOUND를 추가했다.
3. 기존 Controller·OrderResponse에 검색·단건 조회를 연결하고 권한·페이지·기간·삭제 제외를 검증했다.

### 핵심

- 검색은 인증 사용자의 ordererId를 내용·count 쿼리에 함께 넣는다. MASTER만 주문자 제한을 생략한다.
- 조회는 readOnly 트랜잭션에서 저장된 상품·가격 스냅샷을 읽으며 회사·배송·Slack을 호출하지 않는다.
- 종료일 다음 날 0시 미만으로 비교해 마지막 소수 초까지 포함한다. 정렬은 createdAt·quantity만 허용하며 ID로 동률 순서를 고정한다.
- 요청 SearchCondition과 서버가 권한·시간 경계를 정한 SearchCriteria를 나눠 domain이 application DTO에 의존하지 않게 한다.

### 검증

신규 application 10개·MVC 12개·HTTP/PostgreSQL 22개를 추가했고 전체 주문 152개가 통과했다. 전체 build 성공, XML 합계 250개이며 실패·오류·skip은 0이다.
격리 Gateway·JWT·Order·PostgreSQL에서 200·400·401·403·404, 위조 헤더 차단, 본인 범위·count를 확인했다. 임시 프로세스와 DB는 정리했다. 자세한 실행 근거는 [스텝 41](../../learning/junhyun/steps/step-41-order-query-api.md)에 있다.
Swagger size 기본값 불일치는 TS-011, 공유 테스트 DB의 fixture 간섭은 TS-011로 해결했다.

### 확인 질문

- 본인 주문 제한을 조회 후 필터링하면 페이지와 전체 건수에 어떤 문제가 생기는가?
- 종료일 23:59:59와 다음 날 00:00 미만 조건은 어떻게 다른가?

### 메모

테이블·마이그레이션·공통 모듈과 원화 long 계약은 바꾸지 않았다. 조회 코드와 기록은 후속 사용자 요청으로 `9a41925`에 커밋했다. 추가 Slack 메시지는 보내지 않았다.

## O-04 요청사항 수정 (2026-10-15)

### 처리 과정

1. 조회 구현 20개 파일을 `9a41925`에 커밋했다. 다른 작업의 Q&A 학습 노트 3개 변경은 제외했다.
2. `OrderRequestNoteTest`로 수정 규칙을 먼저 작성하고 메서드 누락으로 컴파일이 실패하는 것을 확인했다. `Order.updateRequestNote`에 취소 상태·입력 검증을 구현했다.
3. Repository에 잠금 조회와 flush 계약을 추가했다. OrderService에서 소유자 확인·변경·flush를 하나의 쓰기 트랜잭션으로 묶었다.
4. UpdateOrderRequest → UpdateOrderCommand → OrderResult → OrderResponse를 기존 Controller의 PATCH에 연결했다.
5. 단위·MVC·실제 PostgreSQL·Gateway/JWT로 권한·상태·경계값·잠금·롤백·Audit를 검증했다.

### 핵심

- 필수 요청사항은 SA 6.7·8.5에 따라 null·공백을 거부한다. 생성 때 요청사항이 선택인 것과 수정 때 필수인 것은 서로 다른 계약이다.
- 소유자 검증은 application, 취소 상태와 값의 불변식은 Entity가 맡는다. setter 없이 허용된 필드만 바꾼다.
- 비관적 쓰기 잠금은 같은 주문의 상태 확인과 변경 사이에 경쟁 요청이 끼어드는 것을 막는다. DB 트랜잭션 안에서만 사용한다.
- 관리되는 Entity의 변경 감지로 저장하며 새 save를 호출하지 않는다. 응답 직전 flush는 Audit 갱신용이며 커밋과는 다르다.
- 생성용 OrderWriter와 이벤트를 거치지 않는다. 요청사항 수정은 로컬 주문 데이터만 변경한다.

### 검증

도메인 7개·application 7개·MVC 11개·HTTP/PostgreSQL 14개, 총 39개를 추가했다. `./gradlew build --console=plain` 성공, 주문 191개·전체 XML 289개이며 실패·오류·skip은 0이다.
실제 PostgreSQL이 잠금 대기를 보고한 뒤 취소·삭제 트랜잭션을 커밋했고 대기하던 PATCH의 409·404와 기존 요청사항 유지를 확인했다.
격리 Gateway·JWT·Order·PostgreSQL에서는 200·400·401·403·404·409와 위조 헤더 차단을 확인했다. 자세한 재현 절차와 실행 근거는 [스텝 42](../../learning/junhyun/steps/step-42-order-request-note-update.md)에 있다.

### 확인 질문

- readOnly 조회 후 별도 트랜잭션에서 수정하면, 그 사이 취소된 주문을 어떻게 놓칠 수 있는가?
- save 없이 수정 값이 저장되는 이유와 flush 후에도 롤백 가능한 이유는 무엇인가?
- 응답 DTO를 flush 전에 만들면 updatedAt이 이전 값으로 남을 수 있는 이유는 무엇인가?

### 메모

O-04 변경은 후속 사용자 요청으로 `6ac9b8a`에 커밋했다. 스키마·마이그레이션 변경 없이 기존 request_note 컬럼을 사용한다. 실제 Slack 메시지는 보내지 않았다. 후속 취소·삭제의 로컬 상태 변경도 같은 잠금 계약을 따라야 한다.

## O-05 주문 취소와 실패 흐름 설계 (2026-10-15)

### 처리 과정

1. O-04 작업 22개 파일을 `6ac9b8a`로 커밋하고 취소 도메인 테스트의 미구현 실패를 확인했다.
2. 중복 취소와 보상 간 경쟁을 설명한 ADR 0006을 먼저 제안했다. 사용자가 진행 기록 추가를 승인한 뒤 V2와 OrderCancellation을 구현했다.
3. OrderCancellationWriter는 실행권·주문 완료·결과 확인·종료 기록을 짧은 독립 트랜잭션으로 처리한다. Service는 그 밖에서 I-11·I-12를 호출한다.
4. 실제 Feign을 Controller에 연결했다. I-11은 재시도하지 않고 I-12는 통신 실패에만 최대 3회 시도한다.
5. PostgreSQL 제약·지연 트리거와 HTTP 대역으로 실패를 주입했다. 사용자 추가 요청에 따라 생성·취소의 [실패 처리 설계](failure-handling.md)를 작성했다.

### 핵심

- 공개 주문 상태와 취소 진행 상태를 분리한다. PROCESSING·RECOVERY_REQUIRED가 남아 있으면 서버가 재시작돼도 새 시도를 막는다.
- 집하 시작 여부는 I-11이 최종 판단한다. 사전 GET으로 확인한 상태가 취소 시점에도 같다고 가정하지 않는다.
- 주문 CANCELED와 시도 COMPLETED를 같은 DB 트랜잭션으로 커밋한다. 예외가 나면 새 트랜잭션에서 실제 결과를 재확인한다.
- 확인된 롤백만 배송을 원복한다. 타임아웃·5xx·잘못된 성공 응답은 진행 기록을 보존하고 결과 확인을 기다린다.
- 복구·종료 기록 실패가 최초 HTTP 오류를 덮지 않게 한다. 자동 만료나 수동 확인 없는 재실행은 추가하지 않았다.

### 검증

신규 도메인 12개·application 14개·PostgreSQL 17개·HTTP/Feign 18개, 총 61개를 추가했다. 주문 252개와 전체 build가 통과했고 전체 XML은 350개, 실패·오류·skip은 0이다.
격리 Gateway·JWT·Order·PostgreSQL에서 권한·위조 헤더·실제 커밋·배송 원복·늦은 취소 결과를 확인했다. 팀 user·delivery 응답은 HTTP 대역이다.
POST 401의 테스트 드라이버 본문 누락은 TS-012에 기록했다. 상세 근거는 [스텝 43](../../learning/junhyun/steps/step-43-order-cancellation.md)에 있다.

- 커밋 예외와 실제 롤백을 구분하지 않으면 정상 취소를 어떻게 되돌릴 수 있는가?

## O-01 생성 진행 기록·커밋 재확인 (2026-10-15)

### 처리 과정

1. O-05 작업을 2e5fcc1에 커밋했다. 사용자가 첫 생성 보강 구현과 다른 서비스 담당자를 위한 인계 기록을 요청했다.

3. 기존 OrderWriter에 시작·저장·재확인·종료·복구 기록을 연결했다. OrderService는 원격 호출 밖에서 짧은 트랜잭션을 조율한다.
4. 실제 DB 커밋 뒤 transaction advice 바깥에서 예외를 주입했다. 저장된 주문 반환·삭제 생략·알림 1회를 확인했다.
5. 중앙 서비스 목록과 company·delivery README에 [연동 계약](integration-contract.md)을 연결했다. 실제 연동·미확정 정책은 받는 서비스의 OPEN 기록에 남겼다.

### 핵심

- 주문 행이 없는 실패도 추적하려면 생성 진행 기록을 먼저 커밋해야 한다. 아직 존재하지 않는 p_orders에는 FK를 걸지 않는다.
- 주문과 완료 기록은 원자적으로 저장한다. 재확인은 같은 진행 기록을 먼저 잠가 원래 저장 트랜잭션이 끝난 결과를 읽는다.
- 커밋이 확인되면 저장된 결과를 반환하고 배송 삭제·이벤트 재발행을 하지 않는다. 미저장 확인과 결과 불확실을 구분한다.
- I-09 미확정 결과는 기존 I-13 보상을 시도해도 복구 대기로 남긴다. 삭제 204를 지연 생성 종료로 해석하지 않는다.
- 이 단계에서는 생성 멱등키·원본 요청 저장·자동 재실행을 도입하지 않았다. 후속 멱등키 구현 전에는 기록만으로 외부 POST 재요청 중복을 막지 못했다.

### 검증

신규 도메인 11개·application 11개·PostgreSQL 15개·HTTP 3개, 총 40개를 추가했다. 전체 build 성공, 주문 292개·전체 XML 390개에 실패·오류·skip은 없다.
실제 DB 커밋 뒤 반환 실패와 재확인 잠금, 주문·완료 기록 동시 롤백, I-13 뒤 지연 생성에도 복구 기록 유지, 생성 이벤트 중복 방지를 확인했다. 실제 커밋 응답 패킷 유실을 주입한 시험은 아니다.
격리 Gateway·JWT·실제 Feign·PostgreSQL에서 201·400·401·500·503과 진행 기록 Audit를 확인했다. 제공 서비스 응답은 HTTP 대역이며 상세 근거는 [스텝 44](../../learning/junhyun/steps/step-44-order-creation-progress.md)에 있다.

## O-01 생성 Idempotency-Key (2026-10-15)

### 처리 과정

1. 생성 진행 기록 작업 32개 파일을 39f704a에 커밋했다. 사용자의 멱등키 적용 요청을 ADR 0008에 기록했다.
2. 지문·도메인 테스트부터 작성하고 키·요청 해시·최초 응답 스냅샷과 V4를 추가했다.
3. Controller의 필수 헤더를 Service에 연결했다. 저장된 요청 재사용, DB UNIQUE로 최초 실행 선점, 충돌 트랜잭션 종료 후 재조회를 구현했다.
4. 실제 PostgreSQL·HTTP·Gateway로 같은 키 재요청과 동시 INSERT 경쟁을 검증했다. API 계약·실패 처리·타 서비스 인계를 갱신했다.

### 핵심

- 외부 키는 클라이언트가 처음부터 알아야 응답 유실 뒤에도 같은 주문 제출을 식별할 수 있다. 내부 I-09는 계속 선발급 orderId로 멱등성을 지킨다.
- 사용자·키 UNIQUE는 조회와 INSERT 사이의 경쟁을 막는다. 패자는 롤백 뒤 새 트랜잭션에서 기존 기록을 확인하고 배송을 호출하지 않는다.
- 파싱한 값으로 지문을 계산해 JSON 표현 차이는 무시하고, 같은 키의 다른 주문 본문은 거부한다.
- 최초 응답을 주문·COMPLETED와 같은 커밋으로 저장한다. 주문 수정·취소 이후에도 생성 재요청에는 같은 결과를 반환한다.
- 키를 자동 만료하지 않고 삭제 이력도 유지한다. 처리 중·실패·복구 대기에서 같은 키의 주문을 자동 재실행하지 않는다.

### 검증

55개를 추가했고 `./gradlew build --console=plain`이 통과했다. 주문 347개·전체 XML 445개, 실패·오류·skip 0이다.
실제 DB 유니크 경쟁·JSONB 왕복·키 범위·삭제 이력·V3→V4 기존 데이터 보존을 검증했다. 격리 Gateway·JWT·Feign·PostgreSQL에서 재요청 201과 충돌·진행 상태별 409, 원래 응답·배송 1회를 확인했다.
상세 실행 근거와 재현은 [스텝 45](../../learning/junhyun/steps/step-45-order-idempotency-key.md)에 있다. 외부 서비스는 HTTP 대역이며 실제 Slack 메시지는 보내지 않았다.

### 확인 질문

- 같은 키의 본문 비교 없이 성공 응답만 재사용하면 수량 변경을 어떻게 놓치는가?
- 조회 후 INSERT와 DB 유니크 제약은 경쟁 요청을 어디서 다르게 처리하는가?
- 생성 재요청의 응답과 현재 주문 조회의 응답이 달라도 되는 이유는 무엇인가?

### 메모

멱등키 변경은 후속 사용자 승인으로 `ed9f8d0`에 커밋했다. 기존 V1~V3과 다른 서비스 소스는 유지했다. 진행 조회·자동 복구 API와 DELIVERY-002의 지연 생성 방지는 후속 범위다.

## O-06 주문 삭제·기본 API 마무리 (2026-10-15)

### 처리 과정

1. 기본 명세에서 O-06만 남았음을 확인했다. 배송 삭제 후 주문 커밋 실패 시 I-10이 404라 삭제 조건을 잃는 문제를 ADR 0009로 제안했다.
2. 사용자가 삭제 기록을 포함해 구현·검증·최종 커밋까지 승인했다. 멱등키 작업 36개 파일을 ed9f8d0에 커밋하고 삭제 도메인 테스트의 미구현 실패를 확인했다.
3. OrderDeletion·V5·허가 근거를 추가하고 I-10·MASTER Controller·트랜잭션·재요청 흐름을 연결했다. 같은 주문 잠금과 기록으로 삭제·취소 충돌을 막았다.
4. PostgreSQL과 HTTP/Feign·Gateway에서 정상·실패·재요청을 검증했다. I-13의 204 이외 2xx를 성공으로 오인하는 기존 void 클라이언트도 보강했다.
5. 주문 서비스만 새 이미지로 반영하고 SA·연동 계약·예외 흐름·학습 기록을 정리했다.

### 핵심

- 원격 삭제 전에 삭제 허가 근거를 따로 커밋한다. 원격 삭제 뒤 로컬 롤백에도 같은 삭제를 이어갈 수 있다.
- 최초 I-10의 404는 허가가 아니다. 이미 확인한 진행 기록이 있는 재요청만 GET 없이 처리한다.
- 삭제는 SA 7.5에 따라 I-13 동안 주문 잠금을 유지한다. I-13은 요청당 1회로 한정하고 생성 보상의 재시도 루프를 중첩하지 않는다.
- 로컬 삭제·COMPLETED를 같은 커밋에 저장하고 예외 뒤 실제 결과를 확인한다. 완료 기록을 복구 대기로 덮지 않는다.
- 생성 멱등키·최초 응답과 과거 취소 이력은 보존한다. 삭제는 Slack을 발행하지 않는다.

### 검증과 확인 질문

검증 명령·정확한 건수·실제 Gateway 시나리오는 [스텝 46](../../learning/junhyun/steps/step-46-order-deletion.md)에 있다. 외부 서비스는 HTTP 대역이며 실제 팀 서비스 업무 연동은 남아 있다.

- 주문의 삭제 트랜잭션이 롤백돼도 배송 삭제는 왜 남을 수 있는가?
- 처음 받은 배송 404와 삭제 재요청에서 예상하는 배송 404를 왜 구분해야 하는가?
- 202를 삭제 완료로 취급하면 어떤 데이터 불일치가 생기는가?

## O-01 비동기 접수와 시간 예산 (2026-10-19, 이슈 #16)

### 처리 과정

- `OrderController.create` → `OrderService.accept`: 같은 키 재요청 판정(`OrderWriter.findAcceptance`) → 업체·상품 조회·권한(8초 마감 확인) → PROCESSING 커밋 → `OrderCreationExecutor.submit` → 202.
- 별도 스레드: `OrderService.run` → `process`(I-09 → 주문 저장 → 실패 시 보상). 모든 실패 경로가 진행 기록(ABORTED의 `failure_code`·`failure_message`, RECOVERY_REQUIRED의 `failure_reason`)에 남기므로 `run`은 로그만 남기고 삼킨다.
- `OrderCreationQueryService.getProgress`가 O-07로 진행 기록을 보여 준다. 완료는 접수 시점 최초 스냅샷이다.
- `OrderService.create`(동기 실행)는 접수·처리를 한 스레드에서 이어 실행하고 기존 응답·예외를 그대로 돌려준다. 요청 경로는 쓰지 않고 기존 테스트가 처리 단계의 보상 규칙을 검증하는 데 쓴다.

### 핵심

- 접수와 처리를 나누면 요청 스레드·DB 연결 점유가 접수 단계(조회 3건 + 기록 1건)로 줄고, 처리 단계의 느린 원격 호출은 유한한 풀이 흡수한다. 풀(스레드 4·대기열 50)이 가득 차면 쌓지 않고 빠르게 503이다.
- 접수 단계의 마감은 호출 사이마다 확인한다. Feign 읽기 타임아웃은 진행 중인 호출을 끊지 못하는 마감이므로, 최악 = 마감 + 호출 1건이다.
- 실패 사유를 응답으로 줄 수 없으니 기록에 남겨야 한다(V6). 하위 서비스 4xx의 코드·메시지를 그대로 보존해 프런트가 같은 문구를 보여 준다.
- 처리 단계에서 order가 I-09를 먼저 끊고 보상하더라도 늦게 도착한 I-09는 delivery 종료 표시가 거절한다(이슈 #14). 이 보장이 없으면 시간 예산을 줄일수록 고아 배송이 늘어난다.
- 서버가 처리 중 종료되면 PROCESSING이 남는다. 종료 시 최대 30초 기다리고, 그래도 남은 시도는 시간만으로 해제하지 않는다.
- 테스트의 직접 실행기(`DirectCreationExecutorConfig`)는 처리 단계를 요청 스레드에서 실행해 호출 횟수·DB 상태 단언을 결정적으로 만든다. 실제 스레드풀 동작(접수 후 지연, 포화)은 `OrderCreationAsyncIntegrationTest`가 검증한다.

### 확인 질문

- 202로 접수한 뒤 서버가 죽으면 사용자는 무엇을 보고 어떻게 판단해야 하는가?
- 접수 단계의 마감을 호출 전에 확인하는 이유와, 이 방식으로는 최악 시간이 마감보다 길어지는 이유는?
- 같은 키가 처리 중일 때 409 대신 202를 돌려주는 것이 멱등성에 더 맞는 이유는?

### 메모

시간 예산의 숫자는 설정에서 계산한 상한이며 실제 지연 주입 측정이 아니다. 취소·삭제·알림 호출의 예산은 바꾸지 않았다.
