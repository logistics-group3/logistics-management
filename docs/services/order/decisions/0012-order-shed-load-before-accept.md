# 0012. 실행기 포화 시 접수 전 조기 거절

- 상태: 채택 (주문 담당자)
- 날짜: 2026-10-19
- 결정자: Junhyun An, 포트폴리오용 부하 측정([측정 보고서](../../../reviews/2026-10-19-order-load-test.md))에서 확인한 낭비를 개선

## 맥락

ADR 0010은 처리 실행기(스레드 4·대기열 50)가 가득 차면 503으로 빠르게 실패하게 했다. 그러나 거절은 접수 단계의 맨 끝(`submit`)에서 일어났다.
거절될 요청도 그 전에 업체·상품 조회 3건(Feign)과 진행 기록 INSERT, 거절 뒤 ABORTED UPDATE를 했다.

측정에서 오프셔드 부하(초당 1,000건) 때 order → company 호출이 2,860/s까지 늘었는데 배송 생성은 222/s뿐이었다.
거절된 요청이 만든 `p_order_creations` 기록이 정상 주문의 약 3배(24.8만 대 7.5만)였다.

## 결정

1. 접수 단계에서 같은 키 재요청 판정 직후, 업체·상품 조회 전에 `OrderCreationExecutor.hasCapacity()`를 확인한다. 여유가 없으면 조회·기록 없이 503이다.
2. 이 경우 진행 기록을 남기지 않는다. 같은 멱등키로 여유가 생긴 뒤 다시 접수할 수 있다(이전에는 ABORTED 기록 때문에 같은 키가 409였다).
3. 확인과 제출 사이에 다른 요청이 끼어들 수 있으므로 기존 `submit` 거절 처리(ABORTED 기록, 503)는 마지막 방어선으로 남긴다.
4. `order.creation.executor.shed-before-accept`(기본 true)로 끌 수 있다. 같은 이미지로 켬·끔을 비교하려는 용도이며, 운영 설정으로 쓰지 않는다.

## 결과와 한계

- 같은 이미지에서 켬·끔을 번갈아 4쌍 비교했을 때 모든 쌍에서 켬이 접수 처리량이 높았고(480/s 구간 +9~39%, 640/s 구간 +24~25%) 접수 p95는 15~19ms 대 42~229ms였다. 실행마다 변동이 커서(약 ±15%) 비율은 근사치다.
- 처리량의 절대값은 로컬 PC·Docker·k6 동거 환경의 하한이고 운영 용량이 아니다. 측정 시간이 길어질수록 같은 설정의 처리량이 떨어지는 흐름이 있어(원인은 병목 분석 참고, 확정하지 못함) 절대값 비교는 같은 시간대 짝으로만 한다.
- 거절된 요청의 기록이 없어져 "왜 거절됐는지"를 DB에서 추적할 수 없다. 로그(`주문 생성 실행기에 여유가 없어 접수 전에 거절한다`)와 503 지표로 본다.
