# 0008. 사용자별 주문 생성 멱등키와 최초 응답 재사용

- 상태: 채택 (주문 담당자)
- 날짜: 2026-10-15
- 결정자: Junhyun An, O-01에 Idempotency-Key를 적용해 재요청 중복 주문을 막도록 요청

## 맥락

생성 진행 기록은 한 시도의 결과를 추적하지만 외부 POST마다 새 orderId가 생겼다. 응답을 못 받은 클라이언트의 재요청을 같은 시도로 식별해야 한다.
조회·생성 사이의 동시 요청도 보호해야 하며, 완료 뒤 요청사항이나 주문 상태가 바뀌어도 재요청에는 최초 생성 결과를 돌려줘야 한다.

## 결정

- O-01의 Idempotency-Key 헤더는 필수다. 1~128자의 영문 대소문자·숫자·`.`·`_`·`:`·`-`를 허용하며 UUID를 권장한다. 키의 대소문자는 구분한다.
- 키 범위는 인증 사용자 ID와 O-01이다. 다른 사용자가 같은 키를 사용해도 독립된 요청이다. 인증은 매 요청 Gateway에서 수행한다.
- 입력을 바인딩한 뒤 공급업체·수령업체·상품 UUID, 수량, 요청사항으로 v1 SHA-256 지문을 만든다. JSON 필드 순서·공백은 영향을 주지 않고 null 요청사항과 빈 문자열은 구분한다.
- p_order_creations에 키·지문·최초 응답 JSONB를 V4로 추가하고 `(orderer_id, idempotency_key)`를 UNIQUE로 보호한다. 키는 자동 만료·해제하지 않는다.
- 성공한 같은 요청은 회사·배송 호출 없이 최초 OrderResult 스냅샷으로 201을 재응답한다. Order의 현재 값은 O-03에서 조회한다.

| 기존 기록과 요청 | 처리 |
|---|---|
| 같은 사용자·키, 다른 지문 | 409 ORDER_IDEMPOTENCY_KEY_CONFLICT |
| 같은 지문, COMPLETED | 최초 생성 응답 재사용, 새 주문·배송·이벤트 없음 |
| 같은 지문, PROCESSING | 409 ORDER_CREATION_IN_PROGRESS |
| 같은 지문, ABORTED | 409 ORDER_CREATION_ABORTED, 같은 키로 재실행하지 않음 |
| 같은 지문, RECOVERY_REQUIRED 또는 기록 논리 삭제 | 409 ORDER_CREATION_RECOVERY_REQUIRED |

키가 아직 없으면 기존 업체·상품·권한 검증 후 생성 기록을 저장한다. 형식·권한·조회 실패는 키를 소비하지 않는다.
이미 저장된 키는 원격 조회 전에 확인해, 원래 성공한 주문을 상품 삭제나 가격 변경 때문에 다시 처리하지 않게 한다.

동시에 처음 들어온 요청은 DB 유니크 제약으로 한 요청만 생성 기록을 커밋한다. 유니크 충돌 트랜잭션을 롤백한 후 새 트랜잭션에서 기존 기록을 읽는다.
실패한 트랜잭션 안에서 조회를 계속하지 않는다. 충돌한 요청은 원격 배송 생성 단계에 진입하지 않는다.

최초 응답은 주문·COMPLETED와 같은 트랜잭션으로 저장한다. JSONB에는 도메인의 불변 스냅샷을 저장하고 application은 OrderResult로 변환한다.
기존 키 없는 기록은 그대로 남긴다. 키 UNIQUE는 논리 삭제된 기록도 포함해 삭제로 키가 재사용되지 않게 한다.

## 검토한 대안

- 키를 선택으로 받기: 키를 빠뜨린 재요청이 계속 중복 생성될 수 있어 이번 API에서는 필수로 정한다.
- 메모리·조회 후 저장만으로 보호: 재시작·여러 서버·동시 요청을 DB에서 막지 못한다.
- 현재 Order를 다시 조회해 응답하기: 수정·취소 후 재요청의 결과가 최초 생성 응답과 달라진다.
- 실패 시 같은 키를 자동 재실행하기: 기존 배송의 삭제 이력과 지연 작업을 확인하지 못한 상태에서 다시 생성할 위험이 있다.
- 자동 TTL: 만료 후 오래된 요청이 새 주문으로 실행될 수 있다. 보관·재사용 정책은 별도 변경으로 결정한다.

## 결과

클라이언트는 새 주문마다 새 키를 만들고 네트워크 재시도에는 같은 키와 본문을 사용한다. 이미 저장된 키의 본문을 바꿔 쓰지 않는다.
ABORTED는 확인된 실패이므로 조건을 해결한 새 주문에는 새 키를 사용할 수 있다. PROCESSING·RECOVERY_REQUIRED에서는 새 키로 우회하지 않고 기존 결과를 확인한다.
진행 상태 조회·자동 복구 API는 별도 범위다. 같은 키의 처리 중 요청을 기다리게 하지 않고 409로 반환한다.

## 근거

- 기존 PostgreSQL 유니크 제약·트랜잭션 패턴과 주문 ADR 0007을 따른다.
- 응답 스냅샷은 Hibernate의 명시적 JSON 매핑을 사용한다([Hibernate 6.6 JSON mapping](https://docs.hibernate.org/orm/6.6/userguide/html_single/Hibernate_User_Guide.html#basic-mapping-json)). 실제 프로젝트 버전 6.6.53.Final에서 PostgreSQL 왕복·최초 응답 재사용을 검증했다.
- 신규 55개를 포함해 주문 347개·전체 XML 445개와 전체 build를 통과했다. 실제 DB 동시 INSERT 경쟁, V3→V4 기존 행 보존, Gateway의 필수 헤더 전달·201 재응답·상태별 409를 확인했다([스텝 45](../../../learning/junhyun/steps/step-45-order-idempotency-key.md)).
