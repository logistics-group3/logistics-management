# 0007. 주문 생성 진행 기록과 커밋 결과 재확인

- 상태: 채택 (주문 담당자)
- 날짜: 2026-10-15
- 결정자: Junhyun An, "O-01 주문 생성의 커밋 결과 재확인과 생성 진행 기록부터 구현" 요청

## 맥락

기존 OrderService는 주문 저장 예외가 나면 배송 삭제(I-13)를 호출했다. DB가 커밋한 뒤 응답만 유실되면 정상 주문의 배송을 삭제할 수 있다.
생성 실패에는 주문 행 자체가 없을 수 있어, 주문과 별도로 원격 호출 전부터 남는 진행 기록이 필요하다.

## 결정

V3으로 p_order_creations를 추가한다. 생성 시도 ID·선발급 orderId·주문자 ID·확인된 배송 ID·진행 상태·복구 사유·Audit를 보관한다.
생성 요청의 전체 본문이나 가격 스냅샷을 재실행용으로 저장하지 않는다. 이번 기록은 실행 결과 확인과 배송 정리에 사용하며, 실패한 요청을 자동으로 다시 생성하지 않는다.

| 상태 | 의미 |
|---|---|
| PROCESSING | 읽기 검증을 통과하고 원격 배송 생성 전 기록 커밋 |
| COMPLETED | 주문 행과 완료 기록을 같은 트랜잭션으로 커밋 |
| ABORTED | 명확한 배송 거절 또는 확인된 미저장·삭제 보상으로 종료 |
| RECOVERY_REQUIRED | 배송 결과·주문 커밋 결과·배송 삭제 결과의 추가 확인 필요 |

1. 업체·상품 조회와 주문 권한을 검증한 뒤 진행 기록을 독립 트랜잭션으로 저장한다.
2. DB 트랜잭션 밖에서 I-09를 호출한다. 기존 orderId 멱등·통신 실패 재시도 정책을 유지한다.
3. OrderWriter.save는 진행 기록을 잠근 뒤 주문 INSERT·진행 기록 COMPLETED·생성 이벤트를 한 트랜잭션에서 처리한다.
4. 저장 예외 시 새 트랜잭션에서 진행 기록을 먼저 잠근다. 이전 저장 트랜잭션이 끝난 뒤 주문과 기록을 함께 확인한다.
5. 주문과 COMPLETED 기록이 일치하면 저장된 결과를 반환하고 배송 삭제·이벤트 재발행을 하지 않는다.
6. PROCESSING과 주문 없음이 확인되면 기존 I-13 보상을 수행한다. 성공은 ABORTED, 실패는 RECOVERY_REQUIRED다.
7. DB 조회 실패·상태 불일치는 RECOVERY_REQUIRED로 남기며 주문이 저장되지 않았다고 추측해서 삭제하지 않는다.
8. I-09 결과가 불확실하면 SA 7.1의 I-13 보상 시도는 유지한다. 삭제 204 이후에도 지연 생성이 끝났다는 보장은 없으므로 RECOVERY_REQUIRED를 유지한다.

order_id는 UNIQUE다. 진행 기록은 주문보다 먼저 저장되므로 p_orders로 물리 FK를 만들지 않는다. 다른 서비스 ID도 UUID 논리 참조다.
기존 V1·V2는 변경하지 않는다. 공개 주문 생성 요청·응답·금액 계약도 유지한다.

## 검토한 대안

- 예외마다 무조건 I-13: 실제 커밋된 주문의 배송을 삭제할 수 있다.
- 주문 행만 재조회: 주문이 없는 실패·중단을 기록할 곳이 없고, 트랜잭션 완료 확인에 쓸 잠금 대상도 없다.
- 생성·취소를 한 범용 Saga 엔진으로 추상화: 수명주기와 FK 전제가 다르므로 현재는 각 흐름을 명시한다.
- 외부 멱등키·전체 요청 저장·자동 재실행 동시 도입: 사용자가 요청한 첫 보강 범위를 넘어가므로 후속 단계로 남긴다.

## 결과

확인된 커밋을 보호하고, 주문이 없는 실패도 조회할 수 있다. 커밋 재확인은 같은 DB에서 진행 기록을 잠그는 방식을 사용한다.
외부 POST 재요청은 아직 새 orderId를 발급한다. 생성 진행 기록만으로 사용자 재시도의 중복 주문을 막는다고 설명하지 않는다.
지연된 I-09와 I-13의 역전 문제는 delivery 측 종료 표시·시도 토큰 계약이 필요하며, 협업 문서에 미확정 사항으로 남긴다.
커밋 결과를 다시 확인할 때 Slack 이벤트를 재발행하지 않는다. 커밋 응답 유실 시 알림 유실 가능성은 기존 메모리 이벤트의 한계이며 Outbox는 후속 검토 대상이다.

## 검증

신규 40개·주문 292개 테스트와 전체 build가 통과했다. 실제 DB 커밋 뒤 transaction advice 바깥에서 예외를 주입해 저장 결과 반환·배송 보존·알림 재발행 없음을 확인했다.
PostgreSQL 잠금 대기 후 커밋·롤백 구분, 완료 기록 실패 시 원자적 롤백, I-13 선행 후 지연 I-09 완료에도 복구 기록 유지를 검증했다. 실제 커밋 응답 패킷 유실·프로세스 강제 종료는 미실행이다.
별도 Gateway·JWT·Feign·PostgreSQL에서 201·400·401·500·503과 진행 기록 Audit를 확인했고 로컬 V3 반영도 확인했다. 제공 서비스는 HTTP 대역이며 실제 팀 서비스 검증은 협업 로그에 남긴 후속 작업이다.
