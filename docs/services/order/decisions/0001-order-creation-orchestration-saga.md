# 0001. 주문 생성: 오케스트레이션 Saga + 보상

- 상태: 제안
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-09, 원문 상태 "확정". 본문은 원문 문장을 그대로 옮겼다
- SA v2.0과의 차이: 오케스트레이션 Saga, 역순 보상, orderId 선발급은 SA 7.1과 같다. 원문은 재고 차감(I-05)과 복원(I-06) 단계를 더했고, SA v2.0 7.1에는 재고 단계가 없다.

## 맥락
- 주문 하나가 hub(재고), delivery(배송·담당자), order(주문) 세 DB를 바꿉니다. 서비스마다 DB가 다르므로 @Transactional은 각자의 로컬 트랜잭션일 뿐입니다.
- 중간에 실패하면 "재고는 줄었는데 주문은 없는" 상태가 남습니다.
- SA와 다른 부분은 서비스 담당자가 채택 여부를 결정한다.

## 결정
order-service가 순서를 지휘하는 오케스트레이션 Saga입니다. orderId를 저장 전에 미리 발급해 모든 하위 호출의 멱등키로 쓰고, 실패하면 앞에서 성공한 단계를 거꾸로 되돌립니다.

### 흐름
1. orderId를 미리 발급합니다.
2. 업체·상품을 조회·검증합니다(I-07, I-08). 상품이 공급업체 것인지, 주문자가 요청업체 관리자인지, 두 업체가 다른지 확인합니다. 쓰기가 없으므로 실패해도 보상이 필요 없습니다.
3. 공급업체 허브 재고를 차감합니다(I-05). 부족하면 409 STOCK_INSUFFICIENT이고 남는 데이터가 없습니다.
4. 배송을 생성하고 담당자를 배정합니다(I-09). 실패하면(담당자 없음 404 포함) 배송 삭제(I-13)와 재고 복원(I-06)으로 보상합니다.
5. 주문을 저장합니다. 실패하면 4번과 같은 보상을 합니다.
6. 커밋 후 Slack 알림을 비동기로 보냅니다(ADR-14). 실패해도 주문은 유지됩니다.
보상 호출이 실패하면 최대 3회 재시도하고, 그래도 실패하면 orderId와 함께 ERROR 로그를 남겨 수동으로 처리합니다. 응답은 실패한 단계에 맞는 에러 코드 하나입니다.
(원문 Notion의 다이어그램 참고)
재고 부족(409)은 쓰기 전에 끝나고, 배송 생성 이후의 실패만 역순 보상을 탑니다.

## 검토한 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| 2PC / XA | 강한 일관성 | 코디네이터가 단일 장애점, 락을 오래 잡음, HTTP 서비스 간에는 현실적으로 불가 |
| **오케스트레이션 Saga (채택)** | 흐름이 한 클래스에 보임, 동기 Feign과 잘 맞음 | order가 다른 서비스를 많이 앎 |
| 코레오그래피 Saga | 서비스 간 결합 낮음 | 메시지 브로커 필요, 흐름이 여러 서비스에 흩어짐 (Kafka 고도화) |

## 결과
### 이유
- **orderId 선발급**: 타임아웃이 나면 상대가 처리했는지 알 수 없습니다. orderId가 있으면 "이 주문의 차감을 되돌려라"고 안전하게 요청할 수 있고, 처리된 적이 없으면 아무 일도 하지 않습니다(no-op).
- **재고 차감을 배송 생성 앞에**: 가장 자주 실패하는 단계(재고 부족)를 앞에 두면, 실패해도 되돌릴 것이 없습니다. 배송 생성은 담당자 배정까지 포함해 무겁고 보상도 복잡합니다.
- **주문 저장을 마지막에**: 모든 하위 단계가 성공한 뒤에만 주문이 보이므로, 사용자가 보는 주문은 항상 재고와 배송이 준비된 주문입니다.
- **오케스트레이션**: 동기 Feign 환경에서는 호출하는 쪽이 결과를 바로 알기 때문에, 그 자리에서 보상을 결정하는 것이 자연스럽습니다.

### 트레이드오프
- 주문이 마지막에 저장되므로, Saga 도중에 order-service가 죽으면 "진행 중이던 Saga"의 기록이 없습니다. 재고·배송만 남을 수 있고 자동으로 복구되지 않습니다. 개선안은 주문을 PENDING으로 먼저 저장하고 끝나면 ORDERED로 바꾸며, 오래 멈춘 PENDING을 스케줄러가 보상하는 방식입니다(고도화).
- 최종 일관성이라, 보상이 끝날 때까지 잠깐 재고가 줄어 보이는 순간이 있습니다.
- 보상 실패는 로그에 의존합니다. 운영에서는 실패 테이블이나 아웃박스로 남겨 재처리해야 합니다.

## 면접 답변
> "서비스마다 DB가 달라 하나의 트랜잭션으로 묶을 수 없어서, order가 순서를 지휘하고 실패하면 앞 단계를 거꾸로 되돌리는 Saga를 썼습니다. 핵심은 orderId를 미리 발급해 모든 호출을 멱등하게 만든 것이고, 그래서 타임아웃에도 보상과 재시도를 안전하게 할 수 있습니다."
- **Q. 보상까지 실패하면요?** 멱등하므로 3회까지 재시도하고, 그래도 실패하면 orderId와 함께 ERROR 로그로 남겨 수동 처리합니다. 자동 복구는 아웃박스와 스케줄러가 다음 단계입니다.
- **Q. 왜 코레오그래피가 아닌가요?** 코레오그래피는 메시지 브로커가 전제이고 흐름이 여러 서비스에 흩어져 추적이 어렵습니다. 동기 통신을 고른 이번 범위에서는 오케스트레이션이 더 단순합니다.
