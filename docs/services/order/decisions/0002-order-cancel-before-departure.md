# 0002. 주문 취소: HUB_WAITING일 때만, 재고 복원은 재시도

- 상태: 제안
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-10, 원문 상태 "확정". 본문은 원문 문장을 그대로 옮겼다
- SA v2.0과의 차이: 원문은 배송이 HUB_WAITING일 때만 취소하고 재고를 복원한다. SA v2.0은 집하 시작 전(PICKUP_WAITING)에만 취소하고 재고 복원 단계가 없다(7.2). 배송 취소(I-11) → 주문 저장 → 실패 시 원복(I-12) 순서는 같다.

## 맥락
- 물건이 출발한 뒤에 취소하면 반송 물류가 생기는데, 이번 범위에는 반송이 없습니다.
- 취소도 세 서비스(delivery, order, hub)를 바꾸므로, 주문 생성처럼 순서와 보상을 정해야 합니다.
- SA와 다른 부분은 서비스 담당자가 채택 여부를 결정한다.

## 결정
주문자 본인 또는 MASTER만, 배송이 출발 전(HUB_WAITING)일 때만 취소할 수 있습니다. 순서는 배송 취소 → 주문 취소 → 재고 복원이고, 재고 복원이 실패해도 취소는 성공(200)으로 응답하고 복원을 재시도합니다.

## 검토한 대안
### 선택지 (단계 순서)
| 순서 | 장점 | 단점 |
|---|---|---|
| **배송 취소 → 주문 취소 → 재고 복원 (채택)** | "출발 전"인지를 가장 먼저 확정, 마지막 단계는 실패해도 재시도로 해결 | 복원 실패 시 잠시 재고가 적게 보임 |
| 재고 복원 → 배송 취소 → 주문 취소 | 재고가 가장 빨리 돌아옴 | 배송이 이미 출발했으면 복원을 다시 차감해야 하는데, 그 사이 다른 주문이 가져가면 차감 실패 |

## 결과
### 이유
- **모든 배송은 HUB_WAITING으로 시작**하므로(ADR-11), "출발 전"인지를 상태값 하나로 판단합니다. 같은 허브 주문과 다른 허브 주문에 규칙이 하나입니다.
- **배송 취소를 가장 먼저**: 출발 여부는 delivery가 알고, 취소와 출발 처리가 동시에 와도 delivery 로컬 트랜잭션에서 한쪽만 성공합니다. 여기서 실패하면(409) 아무것도 바뀜 적이 없습니다.
- **주문 저장 실패 시 배송 취소 원복(I-12)**: 주문은 살아 있는데 배송만 취소된 상태를 막고 500을 응답합니다.
- **재고 복원은 롤백하지 않고 재시도**: 복원은 더하기라 업무적으로 실패할 이유가 없고, orderId로 멱등합니다. 실패 원인은 장애뿐이라 재시도가 맞고, 최악의 경우에도 재고가 적게 보여 "덜 팔리는" 쪽이지 "더 팔리는" 쪽이 아닙니다.
- 상품이 삭제(판매 중지)돼 있어도 복원합니다. 취소된 물건은 허브에 실제로 남기 때문입니다(ADR-13).

### 트레이드오프
- 3회 재시도가 모두 실패하면 ERROR 로그를 보고 사람이 처리해야 합니다. 그동안 재고가 실제보다 적게 보입니다.
- 출발 후 취소(반송)는 지원하지 않습니다.

## 면접 답변
> "취소 가능 여부를 아는 delivery를 가장 먼저 부르고, 재고 복원을 마지막에 둡니다. 복원은 멱등한 더하기라 실패해도 재시도하면 되고, 순서를 반대로 하면 되돌리기 위한 차감이 실패할 수 있기 때문입니다."
- **Q. 취소 요청과 배송 출발이 동시에 오면요?** 둘 다 delivery의 같은 행을 HUB_WAITING에서 바꾸려는 요청입니다. 상태 조건을 건 UPDATE나 낙관적 락으로 한쪽만 성공하고, 다른 쪽은 409를 받습니다.
