# 0006. 주문 취소 진행 기록으로 중복 실행과 미확정 결과를 보호

- 상태: 채택 (주문 담당자)
- 날짜: 2026-10-15
- 결정자: Junhyun An, 2026-10-15 "진행 기록 추가 적용" 승인

## 맥락

SA 7.2는 배송 취소(I-11) → 주문 CANCELED 저장 → 저장 실패 시 배송 취소 원복(I-12) 순서다.
SA 3.5와 Feign 규칙에 따라 I-11은 자동 재시도하지 않는다. 요청 결과를 받지 못했다고 배송 취소가 실패한 것은 아니다.

단순히 주문 저장 구간만 잠그면 두 취소 요청의 원격 호출과 보상이 겹칠 수 있다.
예를 들어 A의 배송 취소가 성공하고 주문 저장이 실패한 사이 B가 주문 취소를 완료하면, A의 원복이 B의 정상 취소를 되돌릴 수 있다.

## 결정

외부 O-05 계약과 주문 상태 ORDERED·CANCELED를 유지하고, order_schema에 내부 취소 진행 기록 테이블을 추가한다.
이 테이블은 기존 SA 5.5에 없으므로 적용 전에 주문 담당자의 확인을 받았다. V2 마이그레이션으로 추가하고 기존 V1은 변경하지 않는다.

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| PROCESSING | 주문별 취소 실행권을 확보함 | I-11 한 번 호출 |
| COMPLETED | 배송 취소와 주문 CANCELED 커밋 완료 | 종료 |
| ABORTED | 명확한 거절 또는 확인된 보상으로 종료 | 새 시도 가능 |
| RECOVERY_REQUIRED | 원격 처리 결과·커밋 결과·보상 결과가 불확실함 | 자동 재실행을 막고 수동 확인 |

진행 기록은 시도 UUID, 주문 ID, 배송 ID, 상태, 복구 필요 사유, Audit를 갖는다.
같은 주문의 PROCESSING·RECOVERY_REQUIRED 기록은 하나만 허용하는 부분 유니크 인덱스로 서버 인스턴스 수와 무관하게 중복 실행을 막는다.
기록 생성과 주문 상태 검증은 주문 행 잠금을 잡은 짧은 트랜잭션에서 수행한다. 원격 호출 시에는 DB 트랜잭션을 유지하지 않는다.

1. 주문 조회·본인 또는 MASTER 확인·ORDERED 확인·진행 기록 생성 후 커밋한다.
2. 트랜잭션 밖에서 I-11을 한 번 호출한다. 집하 시작 여부는 delivery가 취소와 함께 원자적으로 판단한다.
3. 정상 응답이면 주문을 다시 잠그고 CANCELED 전이와 진행 기록 COMPLETED를 같은 로컬 트랜잭션으로 커밋한다.
4. 명확한 4xx 거절은 ABORTED로 종료한다. 주문 상태는 그대로다.
5. 주문 저장이 확실히 롤백됐다면 I-12로 보상한다. 보상 성공이면 ABORTED, 실패하면 RECOVERY_REQUIRED다.
6. I-11 타임아웃·5xx·잘못된 성공 응답은 RECOVERY_REQUIRED로 남긴다. 원격 요청이 늦게 완료될 수 있어 무조건 원복 성공으로 단정하지 않는다.
7. 프로세스 종료로 남은 PROCESSING도 자동 만료시키지 않는다. 늦은 원격 처리와 새 시도가 겹치지 않도록 확인 후 복구한다.

실행권 획득 실패나 복구 대기 상태는 기존 409 INVALID_STATUS_TRANSITION으로 응답하되 로그에 orderId·attemptId를 남긴다.
사용자에게 내부 예외·원격 응답 본문을 노출하지 않는다. 별도 복구 API나 자동 복구 작업은 이번 범위에 추가하지 않는다.

## 검토한 대안

- 주문 행 잠금을 원격 호출·보상 내내 유지: 테이블 추가는 없지만 DB 연결과 트랜잭션을 오래 점유한다. 원격 처리의 지연 완료 문제는 남는다.
- 애플리케이션 메모리 잠금: 단일 서버에서는 중복 요청을 막지만 다른 인스턴스·재시작을 보호하지 못한다.
- 주문 저장만 잠그기: 원격 취소·보상의 실행 순서를 보호하지 못한다.
- 취소·원복에 시도 토큰과 fencing 계약 추가: 지연 완료까지 더 강하게 제어할 수 있으나 delivery 계약 변경과 팀 합의가 필요하다.

## 검증

- 같은 주문에 동시에 취소 요청을 보내도 I-11은 한 시도만 호출한다.
- 다른 주문은 독립적으로 취소한다.
- 배송 409이면 주문이 ORDERED이고 보상 호출은 없다.
- 주문 flush·커밋 실패 시 롤백 후 I-12를 호출한다. 정상 취소가 완료된 주문은 원복하지 않는다.
- 타임아웃 뒤 배송 응답이 늦게 도착해도 자동으로 새 시도를 허용하지 않는다.
- 실패 또는 프로세스 중단 후 진행 기록으로 사람이 복구 대상을 찾을 수 있다.

신규 61개·주문 252개 테스트와 전체 build, 격리 Gateway·JWT·PostgreSQL 검증을 통과했다. 실제 DB 제약·커밋 실패, 중복 실행·요청사항 보존, I-11 지연 완료와 I-12 재시도 횟수를 확인했다.
진행 기록은 독립 트랜잭션 사이에 유지됨을 확인했다. 프로세스 강제 종료·다중 JVM 동시 요청·커밋 응답 패킷 유실을 실제로 주입한 시험은 아직 수행하지 않았다.

## 결과

기본 주문 상태와 응답을 유지하며 중복 보상 경쟁을 막는다. 추가 테이블과 실패 기록을 확인하는 운영 절차가 필요하다.
배송 API에는 시도별 fencing 계약이 없으므로 네트워크 단절을 자동으로 완전 복구한다고 약속하지 않는다. 수동 확인과 자동 처리의 경계를 명시한다.
