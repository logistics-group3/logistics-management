# 0002. 재고 동시성: 조건부 UPDATE

- 상태: 제안
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-08, 원문 상태 "제안". 본문은 원문 문장을 그대로 옮겼다
- SA v2.0과의 차이: SA v2.0에서 재고 동시성은 고도화 범위(7.4)이고, 여러 허브 재고를 hub_id 순서로 `FOR UPDATE` 잠그는 방식이다. 원문은 공급업체 허브 1곳 재고를 조건부 UPDATE로 차감한다. 원문 상태도 "제안"이며 비관적 락과의 최종 선택을 팀 확인 항목으로 남겼다.

## 맥락
- 같은 상품에 주문이 동시에 들어오면, "읽고 → 빼고 → 저장"하는 동안 다른 요청이 끼어들어 차감이 사라집니다(갱신 손실). 재고 10개에 주문 2건이 8개씩 동시에 성공할 수 있습니다.
- 주문 1건이 다루는 재고 행은 1개입니다(ADR-06). 그래서 여러 행을 잠글 때의 교착은 생기지 않습니다.
- SA와 다른 부분은 서비스 담당자가 채택 여부를 결정한다.

## 결정
재고 차감은 `UPDATE p_hub_stocks SET quantity = quantity - :q WHERE hub_id = :h AND product_id = :p AND deleted_at IS NULL AND quantity >= :q` 한 문장으로 합니다. 영향 행이 0이면 재고 부족(409)입니다. 비관적 락은 대안으로 두고, 팀 최종 확인이 필요합니다.

## 검토한 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| **조건부 UPDATE (채택 제안)** | 원자적, 락을 문장 하나 동안만 잡음, 재시도 불필요 | 규칙(수량 ≥ 요청)이 엔티티가 아닌 SQL에 있음, 영속성 컨텍스트 우회 |
| 비관적 락 (SELECT … FOR UPDATE) | 도메인 로직을 엔티티에 둘 수 있음 | 트랜잭션 끝까지 락 유지, 인기 상품에서 대기 증가 |
| 낙관적 락 (@Version) | 충돌 적을 때 빠름 | 충돌이 잦으면 재시도 폭주, 재시도 코드 필요 |
| Redis 분산 락 | 여러 DB·서비스에 걸친 자원도 보호 | Redis 도입, 재고가 한 DB에 있어 과함 |

## 결과
### 이유
- 재고는 hub의 한 DB, 한 행에만 있습니다. DB가 제공하는 행 단위 원자성만으로 충분하고, 분산 락까지 필요하지 않습니다.
- "확인"과 "차감"을 한 문장으로 합치면 두 사이에 끼어들 틈이 없습니다. 락도 그 문장이 실행되는 동안만 잡혀 대기가 가장 짧습니다.
- 멱등과 함께 동작하도록 한 로컬 트랜잭션에서 순서를 정했습니다.
	1. DECREASE 이력을 INSERT합니다. `(재고 ID, orderId, DECREASE)` 유니크 위반이면 이미 처리된 요청이므로 성공으로 응답합니다.
	2. 조건부 UPDATE를 실행합니다. 영향 행이 0이면 예외를 던져 이력 INSERT까지 롤백하고 409를 응답합니다.
	3. 바뀜 수량을 이력의 quantity_after에 기록합니다.
- DB에도 `CHECK (quantity >= 0)`을 두어, 코드 실수가 있어도 음수 재고는 생기지 않게 합니다.

### 트레이드오프
- `@Modifying` JPQL은 영속성 컨텍스트를 거치지 않아, 같은 트랜잭션에서 엔티티를 다시 읽으면 옛날 값이 보일 수 있습니다. `clearAutomatically = true`로 막습니다.
- 재고 규칙이 도메인 엔티티 밖(SQL)에 있게 됩니다. 규칙이 복잡해지면 비관적 락으로 바꿀 수 있고, 행이 하나라 그때도 교착은 없습니다.
- 복원(+)과 입고(+)는 조건이 필요 없는 `quantity = quantity + :q`입니다.

## 면접 답변
> "재고가 한 DB의 한 행에 있어서, 확인과 차감을 조건부 UPDATE 한 문장으로 합쳐 DB의 행 락으로 동시성을 막았습니다. 낙관적 락은 인기 상품에서 재시도가 폭주하고, 분산 락은 자원이 여러 곳에 있을 때 필요한 도구라 고르지 않았습니다."
- **Q. 같은 차감 요청이 두 번 오면요?** 이력의 유니크 제약이 두 번째 INSERT를 막아, 재고는 한 번만 줄고 두 번째 요청은 성공으로 응답합니다.
- **Q. 어떻게 검증하나요?** ExecutorService와 CountDownLatch로 재고 N개에 N+α건을 동시에 보내, 성공 건수가 정확히 N이고 최종 수량이 0인지 확인하는 테스트를 둡니다.
