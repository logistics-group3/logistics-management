# 0003. 배송 구간·상태 모델: SA v2.0의 3구간, PICKUP_WAITING에서 시작

- 상태: 채택
- 날짜: 2026-10-15
- 결정자: 한얼 (delivery 담당)
- 대체: [0001](0001-delivery-legs-and-status.md) (2구간, 모두 HUB_WAITING에서 시작)

## 맥락
- 0001(최승근 ADR-11 이관)은 재고 도입을 전제로 했다. 물건이 이미 허브에 있으므로 집하 구간이 필요 없고, 주문 배송은 허브 이동과 업체 배송 2구간이라는 결정이었다.
- SA v2.0(2026-10-13, 멘토 피드백 반영)은 재고 관리 전체를 고도화로 옮겼다. 공급업체가 항상 직접 출고하므로 물건은 주문 시점에 공급업체에 있다. 0001의 전제가 사라졌다.
- SA v2.0은 배송을 집하·허브 이동·업체 배송 3구간으로 다시 설계했다(설계 결정 10, 2.5, 5.6). 0001은 SA와 다른 결정이라 서비스 담당자가 채택 여부를 정해야 했다.

## 결정
SA v2.0을 그대로 따른다.

- **구간**: `PICKUP`(공급업체 → 공급업체 허브), `HUB_TRANSFER`(공급업체 허브 → 요청업체 허브), `LAST_MILE`(요청업체 허브 → 요청업체). 두 업체가 같은 허브 소속이면 `HUB_TRANSFER`를 만들지 않고 `PICKUP`(1), `LAST_MILE`(2) 두 구간만 만든다. 주문 1건 = 배송 1건.
- **구간 상태**: `WAITING` → `MOVING` → `ARRIVED`, 주문 취소 시 `CANCELED`. 앞 구간이 `ARRIVED`여야 다음 구간이 `MOVING`이 될 수 있다.
- **배송 상태**: 구간 상태가 바뀔 때 따라 바뀐다. 배송 상태를 직접 바꾸는 API는 없다.

| 구간 변경 | 배송 상태 |
|---|---|
| (생성) | `PICKUP_WAITING` |
| 집하 `MOVING` | `PICKING_UP` |
| 집하 `ARRIVED` | `HUB_WAITING`, 같은 허브면 `DEST_HUB_ARRIVED` |
| 허브 이동 `MOVING` | `HUB_MOVING` |
| 허브 이동 `ARRIVED` | `DEST_HUB_ARRIVED` |
| 업체 배송 `MOVING` | `OUT_FOR_DELIVERY` |
| 업체 배송 `ARRIVED` | `DELIVERED` |
| 주문 취소(I-11) | `CANCELED`. `PICKUP_WAITING`에서만 가능 |

- **컬럼**: `pickup_address`(공급업체 주소)를 둔다. 예상 거리·시간은 `HUB_TRANSFER`에만 `p_hub_routes` 값으로 채운다.
- **구간 담당 허브**: 구간 출발지를 관리하는 허브다. `PICKUP`은 `arrival_hub_id`(공급업체 허브), `HUB_TRANSFER`·`LAST_MILE`은 `departure_hub_id`.

## 검토한 대안
- 0001의 2구간, 모두 `HUB_WAITING` 시작: 재고가 허브에 있다는 전제 위에서만 맞는다. 재고가 고도화로 빠진 지금은 공급업체에서 허브까지의 이동을 추적하지 못한다.
- 같은 허브일 때도 `HUB_TRANSFER`를 0km 구간으로 만든다: 구간 수가 항상 3이라 코드는 단순하지만, 담당자를 배정할 필요가 없는 가짜 구간이 생기고 담당 건수 계산이 왜곡된다.

## 결과
- 0001에서 이어받는 것: 배송 상태를 구간 상태에서 계산해 두 값이 어긋나지 않게 하는 방식, 상태 전이를 Delivery 애그리거트 안에서만 처리하는 방식, 취소를 시작 상태 하나(`PICKUP_WAITING`)로 판단하는 방식.
- 감수하는 것: 구간이 2개 또는 3개라서, "다음 구간"과 "집하 도착 후 배송 상태"를 같은 허브 여부에 따라 다르게 계산해야 한다. 상태 전이 단위 테스트를 3구간·2구간 두 경로 모두로 작성한다.
- 후속 작업: T01에서 V1 마이그레이션과 엔티티를 이 모델로 만든다. 도메인 설명은 `delivery-service/docs/domain/delivery.md` 3절이다.
