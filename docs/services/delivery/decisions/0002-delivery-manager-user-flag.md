# 0002. 배송담당자: 유저 플래그 + 소속 허브 규칙

- 상태: 제안
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-12, 원문 상태 "확정". 본문은 원문 문장을 그대로 옮겼다
- SA v2.0과의 차이: 대체로 같다(USER의 배송담당자 플래그와 소속 허브, 담당 건수가 가장 적은 담당자 자동 배정, 없으면 404, MASTER 재배정). 원문 규칙에는 집하 구간이 없다(delivery 0001과 같은 이유).

## 맥락
- 담당자에게 필요한 정보는 "어느 허브 소속인가"와 "담당자 자격이 있는가"뿐입니다. 로그인·Slack ID 등은 이미 USER에 있습니다.
- 권한은 MASTER / USER 2단계입니다.

## 결정
배송담당자는 별도 서비스나 엔티티 없이, USER의 `is_delivery_manager` + `hub_id`로만 표현합니다. 한 사람이 허브 간 이동과 업체 배송을 모두 맡을 수 있지만, 허브 간 이동은 공급업체 허브 소속, 업체 배송은 요청업체 허브 소속 담당자가 맡습니다.

## 검토한 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| 별도 delivery-manager 서비스·엔티티 | 담당자 전용 속성(차량, 구역 등)을 늘리기 쉬움 | 서비스·호출·동기화가 늘고, USER와 정보가 중복 |
| 별도 역할(DELIVERY_MANAGER) | 권한 체계가 단순해 보임 | 업체 소속 등 USER 역할과 겹치면 표현할 수 없음 |
| **USER 속성(플래그 + hub_id) (채택)** | 추가 서비스 없음, Gateway가 X-Delivery-Manager 헤더로 전달 | 담당자 속성이 늘면 USER가 비대해짐 |

## 결과
### 이유
- 담당자는 "하는 일이 다른 사용자"이지 별도 생명주기를 가진 개념이 아닙니다. 엔티티를 나누면 가입·탈퇴 때 두 서비스를 맞춰야 합니다.
- 소속 허브 규칙을 두면 구간의 출발 허브에 있는 사람이 그 구간을 맡습니다. 물건과 사람이 같은 곳에서 출발하는 현실 운영과 맞습니다.
- **자동 배정**: 구간 담당 허브 소속 담당자 중 진행 중(WAITING·MOVING) 구간이 가장 적은 사람, 동점이면 userId 순입니다. 예측 가능하고 테스트하기 쉽습니다.
- 담당자가 없으면 404 DELIVERY_MANAGER_NOT_FOUND로 주문을 실패시킵니다. 담당자 없는 배송을 만들면 아무도 움직이지 않는 주문이 남기 때문입니다. MASTER는 진행 전 구간의 담당자를 같은 허브 소속으로 재배정할 수 있습니다(D-04).

### 트레이드오프
- "최소 담당 건수"는 거리·동선을 보지 않습니다. 배차 최적화는 범위 밖입니다.
- 동시에 여러 주문이 같은 담당자를 고를 수 있어 분배가 조금 한쪽으로 쏠릴 수 있습니다. 정확한 균등이 목표가 아니라 락을 걸지 않았습니다.
- 배송 생성 때마다 delivery → user 호출로 담당자 목록을 가져옵니다.

## 면접 답변
> "배송담당자는 별도 생명주기가 없는 '역할이 다른 사용자'라서 USER의 속성으로 두었습니다. 배정은 구간 출발 허브 소속 중 담당 건수가 가장 적은 사람으로, 단순하고 예측 가능하게 했습니다."
- **Q. 담당자에게 차량·근무 시간 같은 정보가 필요해지면요?** 그때는 담당자 프로필을 별도 테이블이나 서비스로 분리합니다. 지금은 필요한 속성이 두 개뿐이라 분리 비용이 더 큽니다.
