# 0001. 배송 구간·상태 모델: 2구간, 모두 HUB_WAITING에서 시작

- 상태: 대체됨 (0003). 재고가 고도화로 빠져 전제가 사라졌다. 아래 본문은 원문 그대로 둔다
- 날짜: 2026-10-14
- 결정자: 최승근 (원문 작성). 팀 승인 기록 없음
- 원문: Notion "스파르타물류 기술 결정 문서 (ADR)" ADR-11, 원문 상태 "확정". 본문은 원문 문장을 그대로 옮겼다
- SA v2.0과의 차이: 원문은 허브 간 이동(HUB_TRANSFER)과 업체 배송(LAST_MILE) 2구간이고 모두 HUB_WAITING에서 시작하며 집하 구간과 pickup_address가 없다. SA v2.0은 집하·허브 이동·업체 배송 3구간이고 PICKUP_WAITING에서 시작한다(설계 결정 10, 2.5).

## 맥락
- 원본 SA는 주문마다 집하(업체 → 허브)부터 3구간을 기록했습니다. 재고를 도입하면 물건은 이미 허브에 있으므로 집하 구간이 의미가 없습니다.
- 물건 이동은 업체 → 허브(입고), 허브 ↔ 허브, 허브 → 업체 세 가지이고, 이 중 입고는 주문과 별개입니다(ADR-06). "입고"는 재고 추가에만 쓰는 용어로 고정했습니다.
- 허브 17곳의 모든 쌍(272개)에 직행 경로가 있어, 허브 간 이동은 한 번입니다.
- SA와 다른 부분은 서비스 담당자가 채택 여부를 결정한다.

## 결정
주문 배송은 허브 간 이동(HUB_TRANSFER)과 업체 배송(LAST_MILE) 2구간입니다. 같은 허브면 업체 배송 1구간입니다. 모든 배송은 HUB_WAITING으로 시작하고, 배송 상태는 구간 상태에서 정해집니다. 집하지 컬럼(pickup_address)은 없앱니다.

### 상태 전이
- 구간 상태: WAITING → MOVING → ARRIVED (취소 시 CANCELED). 앞 구간이 ARRIVED여야 다음 구간이 MOVING이 될 수 있습니다.
- 다른 허브: HUB_WAITING → HUB_MOVING → DEST_HUB_ARRIVED → OUT_FOR_DELIVERY → DELIVERED
- 같은 허브: HUB_WAITING → OUT_FOR_DELIVERY → DELIVERED
- 취소: HUB_WAITING → CANCELED (이 상태에서만 가능)
(원문 Notion의 다이어그램 참고)
두 경로 모두 HUB_WAITING에서 시작하므로, 취소 규칙은 이 상태 하나만 보면 됩니다.

## 검토한 대안
| 선택지 | 장점 | 단점 |
|---|---|---|
| 주문마다 3구간 (원본) | 업체 출발부터 추적 | 재고 모델과 모순(허브에 있는 물건을 다시 집하) |
| **2구간 (채택)** | 물건의 실제 흐름과 일치 | 입고 운송은 추적하지 않음 |
| 여러 허브 경유 (최단 경로) | 현실적인 간선 물류 | 구간 수가 가변, 경로 계산·배차가 범위 밖 |

| 초기 상태 | 장점 | 단점 |
|---|---|---|
| 같은 허브는 바로 업체 배송 대기 상태로 | 상태 의미가 구체적 | 취소 규칙이 두 가지가 됨 |
| **모두 HUB_WAITING (채택)** | "출발 전 = HUB_WAITING" 하나로 취소 판단 | 같은 허브 배송도 "허브 대기"라는 이름을 거침 |

## 결과
### 이유
- 담당자는 구간을 움직이고, 고객은 배송 상태를 봅니다. 배송 상태를 구간 상태에서 계산하면 두 값이 어긋날 수 없습니다. 상태 전이는 Delivery 애그리거트 안에서만 일어납니다.
- 초기 상태를 하나로 맞추면 취소 규칙이 "HUB_WAITING일 때만" 한 줄이 됩니다(ADR-10).
- 주문 배송은 공급업체 허브에서 출발하므로 공급업체 주소가 필요 없어 pickup_address를 뺐습니다. supplier_company_id는 참조용으로 남깁니다.
- 예상 거리·시간은 허브 간 경로(Haversine × 1.3, 평균 70km/h)가 있는 HUB_TRANSFER에만 저장합니다.

### 트레이드오프
- 업체가 허브로 입고하는 운송은 배송으로 추적하지 않고, 재고 이력(INBOUND)으로만 남습니다.
- 실제 간선 물류처럼 여러 허브를 거치는 경로는 고도화입니다. 구간을 sequence로 관리하므로 구간 수가 늘어도 구조는 유지됩니다.

## 면접 답변
> "재고가 이미 허브에 있으므로 주문 배송은 허브 간 이동과 업체 배송 2구간입니다. 초기 상태를 모두 HUB_WAITING으로 맞춰, '출발 전에만 취소'라는 규칙을 상태값 하나로 판단할 수 있게 했습니다."
- **Q. 배송 상태와 구간 상태를 둘 다 저장하면 어긋나지 않나요?** 구간 상태를 바꿀 때 같은 트랜잭션에서 배송 상태를 다시 계산합니다. 둘 다 Delivery 애그리거트 안에 있어 로컬 트랜잭션으로 보장됩니다.
