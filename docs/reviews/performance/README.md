# 캐시 도입 성능 측정 기록

캐시 후보 A, B, C를 하나씩 적용하며 같은 조건에서 비교한 기록이다. 측정 방법과 명령은 [성능 측정 가이드](../../guides/performance-test.md)에 있다.
회차별 보고서(`<회차>.md`)와 아래 목록은 `script/perf.sh run`이 만든다. 원본(k6 요약 JSON, Prometheus 응답)은 Git에서 제외된 `.local/perf/results/<회차>/`에만 있다.

## 범위
2026-10-19 팀 회의에서 D(배송담당자 목록 캐시)는 기각됐다. A, B, C만 측정한다.

| 항목 | 대상 | 주 지표 | 보조 지표 |
|---|---|---|---|
| A | Gateway 권한 재확인(I-01) | 권한 변경 반영 시간, 요청당 I-01 호출 수 | 응답 시간 p95 |
| B | 허브·허브 경로 조회(I-02, I-03, H-01·H-03) | 요청당 I-03 호출 수와 지연, S3 p95·처리량 | 주문 생성 p95 |
| C | 업체·상품 조회(company 내부 API) | company 내부 API p95, 주문 생성 p95·처리량 | company CPU·DB 커넥션 |

## 조건
| 조건 | 시나리오 | 바꾸는 것 | 비교 대상 |
|---|---|---|---|
| A0 | S1 | Gateway 권한 캐시 TTL 0s(캐시 없음) | - |
| A1 | S1 | TTL 60s(현재 Caffeine 로컬 캐시) | A0 |
| A2 | S1 | Redis 권한 캐시, 권한 변경·탈퇴 시 키 삭제 | A1 |
| BC0 | S2, S3 | 캐시 없음(Gateway TTL 60s 고정) | - |
| B1-local | S2, S3 | 허브·경로 로컬 캐시(Caffeine) | BC0 |
| B1-redis | S2, S3 | 허브·경로 Redis 캐시 | BC0, B1-local |
| C1 | S2 | company-service 내부 조회 API Redis 캐시, 수정·삭제 시 키 삭제 | 채택한 B1 |

- S2는 Gateway를 거치므로 B, C를 재는 동안 Gateway TTL은 60s로 고정한다.
- B와 C는 같은 S2에 영향을 준다. C1은 B의 채택안을 적용한 상태를 기준으로 비교한다.
- C의 캐시 위치는 "코드 수정 범위가 가장 작은 곳"으로 정했다(2026-10-19 kmh). company-service 한 곳에서 조회 캐시와 삭제를 함께 처리한다. 이 위치는 company의 DB 조회를 줄이며 order → company HTTP 호출 수는 그대로다. 그래서 C의 주 지표는 호출 수가 아니라 company 내부 API 지연이다.
- 회차 이름은 `조건-시나리오-회차`다. 예: `A0-s1-r1`. 같은 조건을 3회 측정하고 중앙값으로 비교한다.

## 판정 기준
- 개선 폭이 같은 조건 3회의 편차보다 작으면 "차이 없음"으로 본다.
- 나빠진 지표도 함께 적는다. 예: Redis 왕복으로 늘어난 응답 시간.
- 로컬 Docker(Windows, 컨테이너당 1 CPU·768MB) 기준의 상대 비교다. 절대 수치는 운영 환경 성능을 뜻하지 않는다.
