# #15 업체 삭제와 상품 생성 경쟁 수정안

- 상태: 2026-10-19 사용자가 확인하고 같은 브랜치에서 수정·PR 생성을 요청했다. 구현·검증은 [결과 기록](2026-10-19-issue-15-verification.md)을 따른다.
- 이슈: [#15](https://github.com/logistics-group3/logistics-management/issues/15).

## 현재 문제

ProductService.create는 업체가 활성인지 읽은 뒤 상품을 저장한다. CompanyService.delete는 당시 보이는 상품을 조회해 삭제하고 업체를 논리 삭제한다. 둘이 겹치면 업체 삭제가 먼저 끝나고 상품 저장이 나중에 커밋될 수 있다.

업체의 물리 행은 남으므로 FK는 이 상품 저장을 거절하지 않는다. 같은 업체에 대한 확인과 변경을 하나의 순서로 처리해야 한다.

## 수정할 위치

| 파일 | 변경 |
|---|---|
| company-service/src/main/java/com/sparta/logistics/company/domain/CompanyRepository.java | Optional<Company> findByIdForUpdate(UUID id)를 선언한다. |
| company-service/src/main/java/com/sparta/logistics/company/infrastructure/persistence/CompanyJpaRepository.java | 위 조회를 @Lock(PESSIMISTIC_WRITE)와 ID 조건 JPQL로 구현한다. |
| company-service/src/main/java/com/sparta/logistics/company/application/CompanyService.java | delete가 일반 findById 대신 위 잠금 조회로 업체를 얻고, 권한 확인 → 소속 상품 조회·삭제 → 업체 삭제 순서로 처리한다. |
| company-service/src/main/java/com/sparta/logistics/company/application/ProductService.java | create가 같은 업체 잠금 조회 → 활성 업체·권한 확인 → 상품 저장 순서로 처리한다. |

일반 검색·상세 조회를 전부 잠그지 않는다. create와 delete의 기존 트랜잭션이 업체 잠금을 커밋까지 유지하게 한다. 잠금·권한 확인의 순서는 두 경로에서 일치시킨다.

## 예상 동작

1. 상품 생성이 업체 잠금을 먼저 얻으면 삭제는 기다린다. 상품 생성 커밋 후 삭제가 새 상품까지 읽어 함께 논리 삭제한다.
2. 업체 삭제가 잠금을 먼저 얻으면 상품 생성은 기다린다. 삭제 커밋 후 활성 업체가 조회되지 않아 기존 COMPANY_NOT_FOUND(404)로 거절된다.
3. 서로 다른 업체의 작업은 서로 다른 행을 잠그므로 독립 진행한다.

Entity·DB 컬럼·요청/응답 DTO는 추가하지 않는다. 같은 업체에 대한 상품 생성은 직렬화되므로 동시 생성 처리량의 비용이 생긴다. 이번 범위에서는 구현과 검증이 단순한 행 잠금을 제안한다.

## 테스트와 완료 기준

- 실제 PostgreSQL에서 생성 선행·삭제 선행 두 순서를 제어해 위 결과를 각각 확인한다.
- 삭제된 업체 아래 활성 상품이 0건인지 DB에서 확인한다.
- 다른 업체의 생성이 해당 업체 잠금에 묶이지 않는지도 확인한다.
- 기존 생성·삭제 권한과 없는 업체 오류를 회귀 검증한다.
- 단위 테스트의 저장소 대역을 새 잠금 조회에 맞추고, company 테스트·전체 Gradle build·문서 검사 결과를 기록한다.
- SA 7.5·company 계약·구현 노트와 progress에 잠금 경계와 이유를 적는다.

이 문서는 사용자 확인을 받은 사전 계획이다. #13과 함께 현재 브랜치에서 PR을 만들되 관련 없는 기존 미커밋 파일은 보존한다.
