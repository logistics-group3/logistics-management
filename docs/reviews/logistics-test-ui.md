## 실행 환경

`logistics-ui-test` 프로젝트로 PostgreSQL·Config·Eureka·Gateway·업무 서비스 5개를 실행했다. 기존 개발 프로젝트와 별도 이미지·네트워크·볼륨을 사용한다.
실제 매핑은 Gateway `127.0.0.1:18080`, PostgreSQL `127.0.0.1:15432`, Config `18888`, Eureka `18761`이었다. Vite는 `127.0.0.1:5174`에서 실행한다.
공개 API로 테스트 사용자·업체·상품·주문을 만들었다. 테스트 주문 서비스의 Webhook 값은 비어 있음을 검사했고 실제 Slack 발송은 하지 않았다.

실행 확인 버전: Node 24.13.0, npm 11.6.2, React 19.2.8, Vite 8.3.4, TypeScript 6.0.2, TanStack Query 5.104.3, Tailwind CSS 4.3.3, Playwright 1.64.1, Vitest 5.0.4. 정확한 패키지 그래프는 lockfile을 따른다.

## 브라우저 시나리오

1. 잘못된 로그인 오류, 로그인 성공, 전체 메뉴 조회, 업체 검색과 빈 결과를 확인했다.
2. 실제 주문 생성 → 요청사항 수정 → 취소 → MASTER 삭제를 수행했다.
3. 같은 허브의 2구간 배송에서 집하 출발·도착 → 업체 배송 출발·도착을 수행했다. 집하 시작 후 주문 취소가 실제 409로 거절되고 배송 완료 후 삭제되는 것을 확인했다.
4. 실제 POST가 201로 주문을 만든 뒤 브라우저 응답만 유실시켰다. 새로고침·재로그인 후 같은 키·본문을 재전송해 같은 orderId를 받았다. 이 시나리오의 서버·DB는 대역이 아니다.
5. USER의 본인 주문·프로필, 삭제 버튼 미노출, 타인 주문 상세의 실제 403을 확인했다.
6. 390×844 모바일 메뉴·표·등록 폼, 키보드 초점 유지·Escape 닫기·복귀를 확인했다. 모달을 연 뒤에도 문서 폭이 viewport를 넘지 않는지 검사했다.
7. 주문 페이지 이동·취소 필터·없는 주문의 실제 404를 확인했다. 조회 503은 브라우저 응답 대역으로 주입하고, 재조회 시 실제 API로 복구되는 것을 확인했다.
8. 실제 배송담당자로 배정 구간 4회 상태 변경을 수행했다. 이후 401 응답 대역으로 세션 만료·로그인 화면 전환을 확인했다.

9. 회원가입의 빈 입력·비밀번호 불일치·실제 중복 아이디 409를 확인했다. 새 USER 가입 201 → 로그인 → 본인 프로필과 미연결 업체 안내까지 수행했다. 검증용 신규 계정은 마지막에 MASTER API로 논리 삭제했다.
10. 390px 모바일 회원가입의 입력 배치·수평 넘침·접근성을 확인했다.

11. 신규 USER가 회원가입 → 본인 담당 업체 2곳 등록 → 업체 주소 수정 → 상품 등록 → 주문 생성까지 화면으로 수행했다. 등록한 상품 단가 `9007199254740993`을 JSON 정수 그대로 보내고 주문 상세에서도 정확히 표시했다.
12. MASTER가 업체 담당자를 신규 사용자로 변경했다. 새 담당자로 실제 주문이 생성되고, 다른 USER의 관리자 변경 요청은 실제 403이었다.
13. 새 사용자에게 다른 허브의 배송담당자를 지정했다. 그 허브의 신규 배송이 실제로 해당 사용자에게 자동 배정됐고, 담당자 로그인으로 2구간 출발·도착을 처리했다. 지정 해제 요청에는 hubId·role을 보내지 않고 USER 역할을 유지했다.
14. 모바일 업체 등록·담당자 선택의 표시, 수평 넘침과 axe 검사를 통과했다.

신규 검증은 자신이 만든 사용자·업체·상품·주문의 ID만 기록해 마지막에 기존 API로 정리한다. 기존 시드와 사용자가 만든 데이터는 정리 대상으로 삼지 않는다.
대시보드와 모바일 주문 폼·회원가입·업체 등록 화면의 axe WCAG A·AA 검사 결과는 위반 0개다. 전체 화면·모든 보조기기 접근성을 인증했다는 뜻은 아니다.
1440px 데스크톱 대시보드·로그인·주문 상세·배송 상세와 390px 모바일 화면의 캡처를 직접 읽어 한글, 표·금액 정렬, 패널, 버튼 노출을 확인했다. 중첩 확인창에서 돌아가기 후 원래 버튼으로 초점이 복귀하고, 접힌 모바일 메뉴가 키보드 탐색에서 제외되는 것도 회귀 검사했다.
초기 검증에서 발견한 라벨·알림·대비 문제는 [TS-018](../troubleshooting.md#ts-018-운영-ui의-입력-라벨모달-알림텍스트-대비-오류)에 기록했다.

## 보존 확인

- 원래 `logistics-management` 컨테이너 9개의 ID·StartedAt와 `.env` SHA-256이 작업 시작 값과 같다.
- 기존 학습 문서의 변경·다른 검토 worktree·stash를 보존했다. 학습 README에는 이번 Slack 질문 노트 링크 한 줄만 추가했으며 이전 미커밋 3개 항목은 유지했다.
- 로컬 브랜치는 main·dev·codex/logistics-test-ui다. 원격 브랜치, 커밋·푸시는 변경하지 않았다.
- 초기 브랜치 정리의 Git bundle·미커밋 자료는 progress 파일에 기록한 별도 백업에 남아 있다.

## 검증 경계

- cross-hub 생성은 hub I-03 미구현으로 실행하지 않았다. UI에서 같은 허브 테스트 범위를 안내한다.
- 실제 Slack 전송, 운영 배포, 실제 물류 운송, 자동 복구·Outbox를 검증한 것이 아니다.
- 기존 배송 취소·출발 동시성 검토 사항은 그대로 남는다. 이번 UI의 직렬 E2E 통과가 동시성 안전성을 증명하지 않는다.
- 브라우저 응답 대역은 응답 유실·503·401 상황을 만들기 위해서만 썼다. 정상 흐름, 권한 403, 상태 거절 409는 실제 서버 응답이다.

스크린샷과 상세 HTML 보고서는 Git에서 제외한 `frontend/test-results/`, `frontend/playwright-report/`에 있다. 사용자가 테스트를 실행하면 이전 결과가 교체될 수 있다.
