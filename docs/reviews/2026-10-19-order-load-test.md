# 주문 생성(O-01) 부하 측정과 접수 단계 개선

측정일 2026-10-19. 포트폴리오용으로 주문 생성의 처리량(TPS)과 한계 지점을 재고, 찾은 낭비 하나를 고쳐 전후를 비교했다. 결정은 [order ADR 0012](../services/order/decisions/0012-order-shed-load-before-accept.md)다.

## 상황 (Situation)

주문 생성은 #16으로 접수(202)와 처리(별도 스레드)로 나뉘었고, ADR 0010의 시간 예산과 실행기 크기(스레드 4·대기열 50)는 "설정에서 계산한 상한이며 실측이 아니다"라고 적혀 있었다. 실제 처리량과 한계, 과부하 때의 동작을 숫자로 확인한 적이 없었다.

## 과제 (Task)

- 접수 TPS와 완료 TPS를 따로 측정하고 한계 지점을 찾는다.
- 과부하에서 낭비되는 작업이 있으면 고치고 같은 방법으로 전후를 비교한다.
- 범위 밖: 운영 용량 산정, 서비스 인스턴스 증설, 다른 API 부하.

## 행동 (Action)

### 측정 환경과 방법

| 항목 | 내용 |
|---|---|
| 환경 | 개인 PC(macOS, 12코어, Docker VM 메모리 7.6GiB). 전용 스택 `logistics-ui-test`(서비스당 인스턴스 1개), PostgreSQL 16 한 대 |
| 부하 도구 | k6 v2.3.0(Docker). 같은 PC에서 돌아 서비스와 CPU를 나눠 쓴다 |
| 모델 | 열린 모델(`constant-arrival-rate`). 서버가 느려져도 요청 수가 줄지 않는다 |
| 시나리오 | `POST /api/v1/orders`(접수, 202) 후 `GET /orders/creations/{orderId}`를 0.5초 간격으로 폴링해 `COMPLETED`까지 |
| 단계 | 초당 접수 40~1,000건, 단계당 45초. 단계 사이에 k6가 만든 데이터를 지우고 시작([reset-order-data.sh](../../load-test/reset-order-data.sh)) |
| 스크립트 | [order-e2e.js](../../load-test/k6/order-e2e.js), [order-steps.sh](../../load-test/order-steps.sh) |

- **접수 TPS** = 202를 받은 초당 건수, **완료 TPS** = `COMPLETED`를 확인한 초당 건수다.
- 완료 지연의 최솟값은 폴링 간격(0.5초)이라 완료 p95 약 510ms는 사실상 "폴링 한 번 안에 끝남"을 뜻한다.

### 발견 1: 단계를 이어서 재면 앞 측정이 뒤 측정을 오염시킨다

처음에는 데이터를 지우지 않고 단계를 이어서 쟀다. 접수 처리량이 229/s로 나왔지만 이는 데이터 누적 때문이었다. 부하 데이터의 배송 구간이 모두 `WAITING`으로 쌓이면 담당자별 활성 구간 집계(`countActiveRoutes`)가 데이터 양에 비례해 느려진다. 단계마다 k6 데이터를 지운 뒤 다시 재자 같은 설정의 한계가 약 320~350/s로 올라갔다.

### 발견 2: 거절될 요청이 비싼 일을 먼저 한다

기준선 [캡처 01](assets/2026-10-19-order-load-test/01-baseline-overview.jpg)의 주문 생성 응답은 202 48,950건·503 87,651건이었고, [캡처 02](assets/2026-10-19-order-load-test/02-baseline-feign.jpg)에서 order → company 호출은 최대 3,000/s였다. 배송 생성 48,950건에 업체·상품 조회가 273,202건으로 약 5.6배였다(데이터를 지우기 전 측정). 거절된 요청도 업체·상품 조회 3건과 진행 기록 INSERT·UPDATE를 하고서야 거절됐다. 그래서 `p_order_creations`가 24.8만 건인데 주문은 7.5만 건이었다.

### 변경

접수 맨 앞(같은 키 재요청 판정 직후)에서 실행기 여유를 확인해 없으면 조회·기록 없이 503이다. 기록이 없으므로 같은 멱등키로 다시 시도할 수 있다. 같은 이미지에서 `order.creation.executor.shed-before-accept`로 켬·끔을 바꿀 수 있어 A/B 비교에 썼다.

|---|---|---|---|---|---|
| 40/s | 40.0 | 40.0 | 0 | 8ms | 513ms |
| 160/s | 160.0 | 160.0 | 0 | 6ms | 512ms |
| 240/s | 240.0 | 240.0 | 0 | 8ms | 514ms |
| 320/s | 318.9 | 318.9 | 50 | 8ms | 512ms |
| 480/s | 352.8 | 352.8 | 5,726 | 11ms | 515ms |
| 640/s | 334.1 | 334.1 | 13,766 | 17ms | 519ms |
| 1,000/s | 230.6 | 230.6 | 34,624 | 832ms | 1,203ms |

- **한계는 접수 약 320~350 TPS**(이 PC, 서비스 1개씩). 그 아래에서는 실패 0, 접수 p95 한 자릿수 ms다.
- 한계를 넘기면 처리량이 늘지 않고, 1,000/s에서는 오히려 230/s로 떨어진다(과부하 시 처리량 붕괴). 캡처: [03](assets/2026-10-19-order-load-test/03-baseline-clean-overview.jpg), [04](assets/2026-10-19-order-load-test/04-baseline-clean-feign.jpg).

### 2) 조기 거절의 효과: 같은 이미지에서 켬·끔을 번갈아 비교(4쌍)

| 부하 | 조기 거절 끔(접수 TPS, p95) | 조기 거절 켬(접수 TPS, p95) |
|---|---|---|
| 480/s | 252.0 / 246.2 (48ms / 42ms) | 274.6 / 341.0 (17ms / 15ms) |
| 640/s | 219.8 / 207.1 (82ms / 229ms) | 273.2 / 257.8 (18ms / 19ms) |

- 모든 쌍에서 켬이 처리량이 높았다(480/s +9~39%, 640/s +24~25%). 접수 p95도 낮았다.
- 별도 실행에서 320/s 단계의 거절이 50건에서 0건이 됐다(한 번 측정).
- 같은 설정의 반복 값이 ±15% 정도 흔들려 비율은 근사치다.

### 3) 확인하지 못한 것

- **실행기 크기의 첫 비교들은 무효였다.** 데이터를 지우지 않은 첫 비교는 오염됐고, 깨끗한 방법으로 다시 잰 4회는 접수 p95가 2~5초로 무너졌다. 처음에는 호스트 CPU 경쟁(사용자가 짚은 웹캠 포함)을 의심했지만 **직접 원인은 측정 스크립트의 버그였다.** zsh가 `for cfg in "16 200"`의 변수를 단어로 나누지 않아 스레드 수 환경 변수가 `16 200`, `4 50`으로 들어갔고, Spring이 공백을 지워 **16,200개와 450개**로 해석했다(컨테이너 안에서 `order-creation-` 스레드 450개 확인). 스레드 수를 측정 전에 검증하도록 고치고 다시 쟀다(부록 D). 카메라가 영향을 줬는지는 확인하지 않았다.
- **고친 뒤에도 같은 설정의 반복 변동이 크다**(부록 D·E: 같은 16/200 설정의 400/s 접수가 400.0/s와 304.5/s). 한 번의 전후 비교로는 결론을 내지 않는다.
- 절대 TPS는 운영 용량이 아니다. k6가 같은 PC에서 돌고 폴링 요청이 부하에 더해지며, 같은 PC의 다른 프로세스(브라우저, 카메라 등)와 CPU를 나눈다.
- 같은 설정의 높은 부하 처리량이 시간대에 따라 크게 달랐다(조기 거절 끔: 기준선 353/s → A/B 시간대 252/s). 원인은 미확인이고(아래 병목 분석에서 DB 실행 계획 변동을 후보로 본다), 그래서 절대값은 같은 시간대의 짝으로만 비교했다.
- 160/s 재확인 단계에서 실패(ABORTED 등) 3건이 있었는데 원인을 확인하지 못했다(직후 데이터를 지워 기록이 없다).

## 리뷰 포인트

- 조기 거절은 "거절 기록이 없다"는 점이 ADR 0010과 다르다. 같은 키 재시도가 가능해진 대신 거절 이력을 DB에서 볼 수 없다.
- 다음 후보: 실행기 크기를 안정된 환경에서 다시 재기, 업체·상품 조회(요청당 3건)의 캐시 여부와 일관성 위험 검토, 장애 주입.

## 병목 분석(1차)

한계가 접수 약 320~350 TPS에서 꺾이는 원인을 자원 사용률로 좁혔다. 부하 중 컨테이너별 CPU를 샘플링([sample-resources.py](../../load-test/sample-resources.py), [analyze-resources.py](../../load-test/analyze-resources.py))하고 `pg_stat_activity`를 0.2초 간격으로 읽었다.

| 관측 | 값 | 해석 |
|---|---|---|
| PostgreSQL CPU | 평균 145~336%, 최대 660% (코어 하나 = 100%) | 모든 단계에서 컨테이너 중 1위. order(평균 85~190)·gateway(75~120)·delivery(45~80)보다 높다 |
| k6 컨테이너 CPU | 평균 30~50% | 부하 도구는 병목이 아니다 |
| Docker VM | 12코어 | 컨테이너 합계가 약 700% 안팎이라 VM 전체가 포화된 것은 아니다(macOS 호스트 간섭은 직접 재지 않았다) |
| DB 활성 쿼리 1위 | 담당자별 활성 구간 집계(`select manager_id, count(...) from p_delivery_routes ...`) | 활성 샘플의 21%(359개 중 75개) |
| 해당 테이블 | 순차 스캔 9,027회, 읽은 행 9,878만 개(삽입 2만 건) | 인덱스가 있어도 `WAITING`이 대부분이라 순차 스캔이 선택된다. 2.1만 행에서 6ms |

해석과 한계:

- 배송을 만들 때마다 담당자의 활성 구간 수를 센다(`DeliveryQueryRepositoryImpl.countActiveRoutes`). 비용이 활성 구간 수에 비례한다.
- **이 병목은 테스트 데이터의 영향이 크다.** 시드 담당자가 서울 허브에 2명뿐이고 배송이 끝나지 않아 `WAITING` 구간이 계속 쌓인다. 실제 운영에서는 담당자가 더 많고 구간이 완료돼 활성 수가 제한된다. 이 비용이 실제로 얼마나 문제인지는 현실적인 데이터로 다시 재야 안다.
- 인덱스 A/B(부록 E)는 일관되지 않았다. 켬 2라운드는 DB CPU가 절반이고 성능이 가장 좋았지만 켬 1라운드는 오히려 나빴다. 같은 인덱스인데 결과가 갈린 이유는 미확인이다. 후보는 실행 계획 변동(통계, 가시성 맵 상태에 따라 인덱스 전용 스캔 여부가 달라짐)이다. 확인하려면 각 구간의 `EXPLAIN`과 `pg_stat_user_tables`를 같이 기록해야 한다.
- 멱등키 조회(`p_order_creations`)는 유니크 인덱스를 정상 사용한다. 측정 중 보인 순차 스캔 카운트는 데이터를 지운 직후 통계가 낡은 시점의 영향으로 보이며 별도 확인은 하지 않았다.
- 정리(1차): PostgreSQL이 병목 후보 1순위이고 활성 구간 집계가 유력하다고 봤다. **2차 분석에서 이 판단이 일부 틀렸음이 드러났다(다음 절).**

## 병목 분석(2차). 병목처럼 보이게 만든 것은 측정 조건이었다

1차의 의심(활성 구간 집계)을 개입으로 검증하다가 더 큰 원인을 찾았다.

### 1) 현실적인 데이터로 다시 재기

시드 담당자가 서울 허브에 2~3명뿐이고 구간이 끝나지 않는 조건(A)과, 담당자 23명에 구간이 생성 5초 뒤 `ARRIVED`로 완료되는 조건(B)을 같은 프로세스(스레드 16·대기열 200, 예열 1회)에서 번갈아 두 라운드 쟀다([perf-data.sh](../../load-test/perf-data.sh)). 매 단계 직후 활성 구간 집계의 실행 계획을 기록했다.

| 조건 | 요청/s | 접수 TPS | 접수 p95 | 거절 | 활성 구간 수 | 집계 쿼리 계획 | 실행 시간 |
|---|---|---|---|---|---|---|---|
| A 1회 | 400 | 252.8 | 471ms | 5,891 | 20,024 | 순차 스캔 | 3.5ms |
| A 1회 | 640 | 279.0 | 240ms | 14,439 | 22,224 | 순차 스캔 | 3.8ms |
| B 1회 | 400 | 357.4 | 68ms | 1,707 | 3,466 | 인덱스 스캔(status) | 0.75ms |
| B 1회 | 640 | 272.1 | 724ms | 14,718 | 2,798 | 인덱스 스캔(status) | 0.56ms |
| B 2회 | 400 | 352.9 | 103ms | 1,887 | 3,678 | 인덱스 스캔(status) | 0.74ms |
| B 2회 | 640 | 336.9 | 180ms | 12,126 | 4,892 | 인덱스 스캔(status) | 0.93ms |
| A 2회 | 400 | 327.7 | 393ms | 2,839 | 26,178 | 순차 스캔 | 5.7ms |
| A 2회 | 640 | 300.9 | 208ms | 13,567 | 23,990 | 순차 스캔 | 4.2ms |

- 활성 구간이 전체의 약 10%로 줄면(B) 플래너가 인덱스 스캔으로 바꿔 쿼리가 5~7배 빨라진다. 활성이 대부분이면(A) 순차 스캔이다. 지난번 인덱스 A/B가 일관되지 않은 이유 중 하나로 보인다(그때는 실행 계획을 기록하지 않아 확정하지 못한다).
- **그런데 PostgreSQL CPU는 두 조건에서 비슷했다**(평균 179~311%). 이 쿼리는 DB CPU의 주된 원인이 아니다. 1차의 "활성 구간 집계가 병목"은 주된 원인으로는 지지되지 않는다.

### 2) 주문 한 건이 DB에 시키는 일

250/s, 7,501건 기준(조건 B)으로 `pg_stat_database`와 `pg_stat_user_tables`의 증가량을 주문 수로 나눴다.

| 항목 | 주문 1건당 |
|---|---|
| 커밋(읽기 전용 트랜잭션 포함) | 13.0 |
| INSERT / UPDATE 행 | 5.0 / 2.7 |
| WAL 레코드 / 바이트 | 55.9 / 약 6KB |
| **읽은 행(tup_returned)** | **약 30,390** |

쓰기량은 작은데 읽은 행이 3만 개다. 테이블별로 쪼개면 대부분이 몇 개 테이블의 **순차 스캔**이다.

| 테이블 | 순차 스캔 횟수 | 주문 1건당 순차로 읽은 행 | 인덱스 |
|---|---|---|---|
| `p_order_creations` | 23,130 | 9,430 | `(orderer_id, idempotency_key)` 유니크 있음 |
| `p_deliveries` | 23,175 | 9,373 | `order_id` 유니크 있음 |
| `p_orders` | 5,823 | 2,385 | 있음 |
| `p_delivery_routes` | 42 | 54 | (인덱스 스캔으로 2,513) |

인덱스가 있는 조회가 순차 스캔이 되고 있었다. 원인 가설은 **낡은 통계**다. 단계 사이에 데이터를 지우고 `VACUUM ANALYZE`를 하면 통계가 "0행"이 된다. 단계 40초 동안 자동 통계 갱신(autoanalyze, 약 1분 주기)이 따라오지 못해 플래너가 "작은 테이블이니 순차 스캔이 싸다"고 판단한다. 측정 방법이 만든 인공물이다.

### 3) 개입으로 검증: 통계를 2초마다 갱신(F) 대 기존(S)

같은 조건(B 데이터)에서 `ANALYZE`를 2초마다 돌리는 것만 켬·끔으로 번갈아 두 라운드 쟀다.

| 라운드 | 통계 | 요청/s | 접수 TPS | 접수 p95 | 거절 | 순차 스캔(3개 테이블 합) | PostgreSQL CPU |
|---|---|---|---|---|---|---|---|
| 1 | 낡음(S) | 400 | 400.0 | 20ms | 0 | 33,066 | 144% |

### 5) 해석과 한계

- 이전에 "한계 약 320~350 TPS"라고 한 값은 측정 조건(구간이 쌓이는 데이터, 낡은 통계)에 크게 좌우됐다. 두 조건을 현실적으로 바꾸자 약 690 TPS가 됐다. 이전 한계는 "시스템의 한계"가 아니라 "그 조건에서의 한계"였다.
- 같은 조건(B 데이터, 낡은 통계)인데 20:20 측정(접수 357/272~337)과 20:41 측정(400/553~585)이 크게 다르다. 그 사이 Docker Desktop이 업데이트돼 데몬이 재시작됐고, 앞쪽은 직후의 백그라운드 부하가 있었을 수 있다(미확인). 그래서 절대값은 같은 세션 안의 짝으로만 비교한다.
- 실제 서비스에서 통계가 낡을 수 있는 경우는 대량 적재 직후다. 운영에서는 자동 통계 갱신이 주기적으로 돌므로 이 인공물은 측정 환경의 문제에 가깝다. 다만 빠르게 늘어나는 테이블의 `autovacuum_analyze_scale_factor` 조정은 검토할 만한 후속이다(이번에 변경하지 않았다).
- 조기 거절(ADR 0012)의 효과 수치(+9~39%)는 낡은 통계·구간이 쌓이는 조건에서 쟀다. 현실적인 조건에서 다시 재지는 않았다.

### 얻은 교훈

- **병목처럼 보이는 것이 측정 조건일 수 있다.** 쌓이는 데이터와 낡은 통계가 DB를 가장 바쁜 곳으로 만들었다. 병목을 고치기 전에 측정 조건을 현실에 맞춘다.
- **의심한 쿼리를 개입으로 검증한다.** 활성 구간 집계는 실제로 5~7배 빨라졌지만 CPU가 그대로여서 주범이 아니었다. 쿼리가 느리다는 것과 병목이라는 것은 다르다.
- **한 지표에서 멈추지 않는다.** CPU 1위 → 쿼리 1위 → 주문당 읽은 행 → 테이블별 순차 스캔으로 좁혀 가며 원인에 닿았다.
- **측정 상태를 맞춘다.** 단계마다 데이터를 지우고 JVM을 예열한다. 이어서 재면 설정의 효과와 데이터 누적의 효과가 섞인다.
- **한 번의 전후 비교를 믿지 않는다.** 같은 설정의 반복 변동이 ±15%이고 시간 경과에 따른 저하도 있다. 켬·끔을 번갈아 짝으로 비교한다.
- **적용된 설정값을 실제로 확인한다.** 환경 변수를 넣었다는 것과 앱이 그 값으로 동작한다는 것은 다르다. 스레드 풀 크기를 `/proc`에서 센 뒤에야 측정한다. 쉘마다 변수 분리 규칙이 달라(zsh는 따옴표 없는 변수를 단어로 나누지 않는다) 측정 스크립트는 `bash`로 명시한다.
- **이상 징후의 원인을 추정으로 확정하지 않는다.** "환경이 나빠졌다"는 그럴듯했지만 실제 원인은 내 스크립트였다. 호스트 부하는 별도로 `uptime`과 상위 프로세스로 기록하되, 그것을 설명으로 쓰기 전에 설정과 코드를 먼저 의심한다.
- **무효 측정도 남긴다.** 결론을 못 낸 실험을 지우면 "스레드를 늘리면 나아진다/나빠진다"는 근거 없는 주장이 남는다.

- 2라운드에서는 16/200이 4/50과 비슷하거나 낮다. 같은 설정의 변동이 이 정도라 "16이 최적"이라고 결론내지 않는다. 스레드를 늘려도 DB가 같이 포화되면(병목 분석) 이득이 없고 대기만 길어진다는 방향성만 읽는다.
